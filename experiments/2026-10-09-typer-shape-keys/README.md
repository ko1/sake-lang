# 実体化のキーを容器の形にする（2026-10-09）

問い: v0 の typer は関数を実引数の型の組ごとに具体化し、容器の型は生成地点なので、行の配列を読むだけの関数が「行の配列を作った場所」の数だけ
歩かれる（`Functions.call` は 284 回。`../2026-10-09-typer-rewrite-estimate/`）。本体が読むだけで、書き込まず、外へ逃がさない引数なら、
生成地点ではなく中身（要素型）だけが結果を決める。そういう引数を要素型の形でキーにすると、報告を変えずにどれだけ速くなるか。

## 方法

`lib/sake/typer_shape.rb`（v0 への追加。`SAKE_TYPER_SHAPE=0` で切れる）。

1. 構文の事前走査（`ParamScan`）で、関数ごとに各引数が「逃げるか」（返す・格納・`Any` を取る組み込みへ・dispatch へ・yield へ・自分を返す組み込みの主語で値が外へ出る）、
   「書かれるか」（`Array.push` などの主語、`x[k] = v` の受け手）を見る。`x = param` の別名は追う。他の関数の引数にそのまま渡した分は、渡し先の性質を引き継ぐ（不動点）。
2. `call_user` で、逃げず書かれない引数の型に含まれる容器の原子（Array / Hash / Set）を `[:array_shape, 要素型, 宣言型]` などの記述に置き換えてキーを作る。
   記述は集合（重複を除いて整列）。要素の中にさらに容器か不明が入る型、Queue / Thread は元のまま（呼び出し元のサイトが結果に入りうる）。
3. 本体の評価は実引数のまま。読んだサイトは呼び出し元の読み取り集合に入るので、中身が変わればキーも作り直される。本体の中で作る容器は実体化（キー）ごと。
4. 付随して `SAKE_TYPER_DEFER=1`: 値がまだ無い（⊥）引数での呼び出しを評価しない（値が来てから）。既定では切ってある。

比較は `diffshape.rb MAIN`（切替の前後で検査の集合と到達関数を比べ、実体化数と時間を出す）、`diffdefer.rb`（後回しの同じ比較）、
`shapekeys.rb MAIN FN`（ある関数の実体化のキーを表示。重複を除く前の失敗を見つけた道具）、壁時計は `../2026-10-09-typer2/bench.sh` と同じ形で 3 回交互。
対象は P10 の SQL エンジン 2 本の段階 6。環境は `../2026-10-09-typer2/README.md` と同じ（Ryzen 9 5900HX、Ruby 4.0.2、YJIT、load 0.4〜0.5）。

## 結果

**報告は変わらない**: 2 本とも、検査の集合（2,092・2,600 件）も到達関数（0・0）も切替の前後で同一。サンプル 151 本は 1 本（`message_length`）だけ、
警告の中の型の表示（配列サイトの番号と並び）が変わった。診断の行・操作・判定は同一で、期待出力を更新した。

| | sake-1 | sake-2 |
|---|---|---|
| 形でキーにできる引数 | 518 / 651 | 475 / 651 |
| 実体化: v0 → 形 → 形＋後回し | 4,481 → 1,837 → 1,637 | 1,864 → 1,470 → 1,324 |
| pass | 8 → 7 → 7 | 8 → 7 → 7 |
| typer だけの時間（diffshape） | 4.0 → 2.3 s | 3.2 → 1.9 s |
| `--strict=2 -c` 壁時計、3 回: v0 | 4.41 / 4.41 / 4.58 s | 3.92 / 3.70 / 3.58 s |
| 同、形 | 2.99 / 2.89 / 3.04 s | 2.82 / 2.78 / 2.70 s |
| 同、形＋後回し | 2.95 / 2.97 / 2.94 s | 2.66 / 2.73 / 2.72 s |
| 最大常駐メモリ: v0 → 形 | 147 → 103 MB | 141 → 113 MB |

壁時計には起動と名前解決（約 0.6 秒）が含まれる。後回しは実体化を 1 割減らすが、壁時計では差が出なかったので既定では切ってある。

## 分かったこと

- **1.5 倍（sake-1）、1.35 倍（sake-2）。見積もり（2.4 倍・1.2 倍の実体化減）どおりの向き。** 残りは本体が型を見る引数ごとの歩きで、これは表現を変えないと減らない。
- 最初の版は記述を型の原子ごとに作っていて、同じ要素型のサイトが 26 個並ぶ union が 26 個の同じ記述になり、サイトが増えるたびに別のキーになって
  実体化が倍増し、pass が上限の 30 まで回った（`Eval.logic_and` が 150 実体化）。記述を集合にして解消。見積もりの射影は最初から集合だったので、見積もりは正しかった。
- 形のキーは Typer2（`../2026-10-09-typer2/`）には入れていない。Typer2 の評価の核は別なので、入れるなら同じ `call_user` の 1 か所。

## 結論

既定で有効にした（`SAKE_TYPER_SHAPE=0` で以前の挙動）。4,400 行の検査が 4.5 秒 → 3 秒。
