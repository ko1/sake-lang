# Specification issues found while writing the stage 1 tests

SQLite 3.46.1 via `harness/sql_oracle.py`. No kept test depends on any point below.

## SQLite disagrees with the specification

1. **Ordinal in the ORDER BY range error (1.7).** `CREATE TABLE t (a INTEGER); INSERT INTO t VALUES (1);`
   `SELECT a FROM t ORDER BY a, 5;` gives SQLite `Error: 2nd ORDER BY term out of range - should be between 1 and 1`.
   `SELECT a FROM t ORDER BY 0;` gives `1st ...`. SQLite's ordinal is the term's position in the
   ORDER BY list. The spec writes `<k-th>` right after "a term that is an integer literal `k`", so it reads
   as the ordinal of the literal's value (`5th`, `0th`). The tests only use cases where position = k.
2. **An alias inside an ORDER BY expression (1.7 "Names").** With `t(a, b)` = (1,30), (2,20), (3,10),
   `SELECT b AS a FROM t ORDER BY a + 0;` gives SQLite 30, 20, 10, which means it used the table column `a`.
   The spec says "In ORDER BY, a name that is a result column's alias means that result column", which
   gives 10, 20, 30. (When the term is the bare name `a`, SQLite uses the alias, as the spec says.) Either
   the spec should limit the alias rule to a term that is only a name, or SQLite is not a usable oracle here.
3. **Double-quoted name that matches no column (1.2).** `CREATE TABLE t (a INTEGER); INSERT INTO t VALUES (1);`
   `SELECT "nope" FROM t;` gives SQLite `nope`, because it falls back to a string literal. The spec says this
   is an identifier, so the answer is `Error: no such column: nope`.
4. **Characters and literals the spec calls syntax errors.** `SELECT 1 & 3, 1 | 2, ~1, 1 << 2;` gives SQLite
   `1|3|-2|4`, and `SELECT 0x10;` gives `16`. Under 1.2 all of these are `Error: syntax error`.
5. **Identifiers that are SQLite keywords but not in the spec's list.** `SELECT a FROM t WHERE nothing = 1;`
   gives SQLite `Error: syntax error`. Under the spec `nothing` is an identifier, so the answer is
   `Error: no such column: nothing`. (Other SQLite-only keywords may act the same way.)
6. **Functions SQLite has and the spec does not.** `SELECT concat('a');` gives SQLite `a`, and
   `SELECT substr(1);` gives `wrong number of arguments to function substr()`. Under 1.11 both are
   `no such function: <name>`.
7. **Rows of different lengths in one VALUES list (1.6).** `INSERT INTO t VALUES (1), (1, 2);` gives SQLite
   `all VALUES must have the same number of terms`, which is not in the catalogue. The spec says a row with a
   different count is `table <t> has <n> columns but <m> values were supplied`, but it does not say which
   row's `<m>` to report.
8. **Bad type names (1.4).** `CREATE TABLE q (a INTEGER b TEXT);` gives SQLite (STRICT) `unknown datatype for
   q.a: "INTEGER b TEXT"`, because SQLite accepts multi-word types. Under the grammar this is a syntax error.
   `CREATE TABLE q (a BLOB)` and `CREATE TABLE q (a)` also give SQLite errors that are not in the catalogue.

## Unclear or ambiguous in the specification

9. **Error-message spelling of a quoted name (1.4).** "Spelled as the statement wrote it": for
   `SELECT "My Col" FROM t;`, is the message `no such column: My Col` or `no such column: "My Col"`?
   SQLite prints it without quotes, but because of item 3 the oracle cannot show this.
10. **Affinity of `(col)` and `+col` (1.9).** "An expression that is a column reference" leaves this open.
    SQLite keeps the affinity for `(s) = 10` (true when `s` is `'10'`) and drops it for `+s = 10` (false).
11. **Quoted keywords.** 1.2 says "a quoted identifier may be a keyword", and the next sentence says tests do
    not use keywords as names. So the rule can never be tested.
12. **`.` in stage 1.** 1.2 lists `.` as punctuation, but no stage 1 grammar uses it. Qualified names
    `t.c` arrive only in stage 4. Is `SELECT t.a FROM t` a syntax error in stage 1?
13. **LIMIT/OFFSET that are not integers (1.7).** "Integer expressions" does not say what happens with
    `LIMIT 1.5` or `LIMIT 'x'`. SQLite gives `datatype mismatch`, which is not in the catalogue.
14. **Two duplicate column names in one CREATE TABLE (1.4).** "The second occurrence" does not say which
    duplicate to report when there are several, for example `(x, y, y, x)`. The tests use one duplicate per
    statement.
15. **Precedence traps.** Because `||` binds tighter than `*` `/` `%`, `enter / 60 || ':' || enter % 60`
    parses as `enter / ((60 || ':') || enter) % 60`. This is consistent and SQLite agrees. It is listed only
    because it surprises readers. Some scenario tests use it on purpose.
