# Specification issues found while writing the stage 4 tests

SQLite 3.46.1 through `harness/sql_oracle.py` (STRICT tables). No test depends on a disputed or
unclear point below; tests were changed to avoid each one.

## Disagreements between SQLite and the specification

### 1. `NULL IN ( select )` with an empty subquery

```
CREATE TABLE t (a INTEGER);
SELECT NULL IN (SELECT a FROM t), NULL NOT IN (SELECT a FROM t);
```

SQLite: `0|1`. Spec 4.3 says `x IN ( select )` follows the IN-list rule of 2.3 ("1 if `x = ei` for some
i; else NULL if x is NULL or some ei is NULL; else 0"), which gives `NULL|NULL`. SQLite returns
false for an empty set whatever x is. (2.3's IN list can't be empty, so this case only comes up
with a subquery.)

### 2. A scalar subquery has its column's affinity

```
CREATE TABLE t (a INTEGER);
INSERT INTO t VALUES (12);
SELECT (SELECT a FROM t) = '12', (SELECT a + 0 FROM t) = '12';
```

SQLite: `1|0`. Spec 1.9 says only a column reference (and, from stage 2, `CAST`) has affinity and
"any other expression has no affinity", so both comparisons are rule 3 (nothing converted) and
give `0|0`. SQLite gives `( select )` the affinity of its result column when that column is a plain
column reference. That is the rule 4.3 already states for `IN ( select )`, but 4.3 doesn't say it
for scalar subqueries.

### 3. An enclosing query's result-column alias is visible inside a subquery

```
CREATE TABLE t (a INTEGER, b TEXT);
CREATE TABLE u (a INTEGER, c TEXT);
INSERT INTO t VALUES (1, 'p'), (2, 'y');
INSERT INTO u VALUES (1, 'p'), (3, 'q');
SELECT b AS x FROM t WHERE EXISTS (SELECT 1 FROM u WHERE u.c = x);
SELECT a + 10 AS x FROM t WHERE (SELECT x) > 11;
```

SQLite prints `p`, then `12`. Spec 4.2 says an unqualified name is looked up in the innermost
query's sources, then "the result column aliases where 1.7 and 3.3 allow them, then the enclosing
queries' sources (4.3)". So the enclosing queries' aliases are not searched, and both statements
should be `Error: no such column: x`. SQLite searches the aliases of each enclosing query too
(and in this test the outer alias is reached from a subquery in the outer `WHERE`, where 1.7
allows aliases).

### 4. A multi-column scalar subquery used in a comparison: `row value misused`

```
CREATE TABLE pair (x INTEGER, y INTEGER);
SELECT 1 = (SELECT x, y FROM pair);       -- also <> < <= > >= IS, IS NOT
SELECT 1 BETWEEN (SELECT x, y FROM pair) AND 3;
SELECT CASE (SELECT x, y FROM pair) WHEN 1 THEN 1 END;
```

SQLite: `Error: row value misused`. That message isn't in the spec's catalogue. Spec 4.3 says a
scalar subquery "must have exactly one result column, else `sub-select returns <n> columns -
expected 1`". SQLite gives that message in the other positions (`(SELECT x, y FROM pair) + 1`, a
function argument, `IS NULL`, `LIKE`, `CASE ... WHEN (SELECT x, y ...)`, `x IN (SELECT x, y ...)`,
ORDER BY, a result column, INSERT values). The tests use multi-column subqueries only in those
positions. (The oracle rejected two of my tests on this: 029 and 055 of the public set.)

## Unclear or ambiguous rules

### 5. The affinity of a subquery source's columns

1.9 gives "a column reference" its column's type affinity. 4.1 defines a subquery source's columns
but gives them no type. SQLite passes a plain column's affinity through and gives other columns
none. With `CREATE TABLE t (a INTEGER)` holding 12:

- `SELECT s.a = '12' FROM (SELECT a FROM t) s` gives 1.
- `SELECT s.j = '12' FROM (SELECT a + 0 AS j FROM t) s` gives 0.

The tests don't compare a subquery-source column with a value of the other kind (text against
number).

### 6. Ambiguity when USING merges only some of the copies of a name

```
SELECT a FROM t JOIN u ON t.a = u.a JOIN v USING (a);
```

SQLite: `ambiguous column name: a`. Here `t.a` and `v.a` are one column, but `u.a` is separate. 4.2
says "a column named in USING is one column", which can also be read as "not ambiguous". The tests
avoid it. `*` in that query prints `t.a`, `u.a` and not `v.a`, as 4.2 says.

### 7. An aggregate whose argument uses only an enclosing query's columns

`SELECT (SELECT sum(t.a) FROM u) FROM t` makes SQLite treat `sum` as an aggregate of the outer query.
The outer query becomes an aggregate query and prints one row. 3.3 and 4.3 don't say which query
such an aggregate belongs to. The tests avoid it: every aggregate inside a subquery refers to that
subquery's own sources.

### 8. Correlated subqueries in UPDATE and DELETE

4.2 and 4.3 talk about "enclosing queries' sources", but UPDATE and DELETE (2.2) have no FROM. The
spec doesn't say whether the target table is a source that a subquery can name, for example:

```
UPDATE stock SET qty = qty - (SELECT sum(qty) FROM moves WHERE moves.pno = stock.pno);
```

SQLite allows it. One public scenario (054-scenario-warehouse) relies on the natural reading: the
target table is an enclosing source named by its table name.

A related gap: 2.2 says SET expressions see the row "as it was before this statement changed it",
but not what a subquery that reads the table being changed sees. The tests use such subqueries only
where every reading gives the same result:

- an UPDATE that changes one row;
- a condition that the rows being changed don't affect.

### 9. Precedence of `NOT EXISTS`

The grammar writes `[NOT] EXISTS ( select )` as one form, but 1.8 makes prefix `NOT` looser than `=`.
SQLite parses `NOT EXISTS (SELECT 1) = 2` as `NOT (EXISTS (SELECT 1) = 2)` = 1. Reading
`NOT EXISTS` as one unit gives `(NOT EXISTS ...) = 2` = 0. The tests use `NOT EXISTS` only where both
readings agree.

### 10. Smaller points the spec leaves open (not tested)

- `USING (a, a)` (a column listed twice): SQLite accepts it.
- `LEFT JOIN` without `ON`/`USING`: 4.1 says it always has one, but doesn't say whether leaving it out
  is a syntax error. SQLite accepts it as a cross join with NULL extension.
- The spec doesn't say what the columns of `(SELECT a, a FROM t) s` are called (duplicate names).
