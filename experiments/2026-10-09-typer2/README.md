# Typer2: 双方向（署名ベース）で typer を書き直して時間を測る（2026-10-09）

問い: v0 の typer（`lib/sake/typer*.rb`、前向きの抽象解釈。関数を実引数の型の組ごとに具体化し、プログラム全体を pass で回す）を、
「関数ごとの局所解析で当たりをつけ、必要なところだけ全体解析する」双方向・署名ベースの推論に書き直すと、同じ報告を保ったまま速くなるか。
着手前の見積もり（`../2026-10-09-typer-rewrite-estimate/`）は「本体を歩く回数は 1〜19% しか減らない」だったが、ko1 の判断で作って測った。

## 方法

`lib/sake/typer2.rb`（約 800 行）。`Sake::Typer2 < Typer` で、**型の格子（intern した union）、組み込みの結果の表、検査の記録、環境と絞り込みはそのまま使い、評価の核だけを替えた**。
`SAKE_TYPER=2` で CLI（`--strict`、`-c`、`--types`）が使う（`cli.rb` の `typer_class`）。`SAKE_TYPER2_NOPOLY=1` で型変数を切り、worklist だけにする。

1. **署名が先（局所）**。関数は引数ごとの「型変数 α か具体型か」のパターンで 1 回解析する。パターンの初期値は構文の走査で決める:
   本体が型を見る引数（条件・演算子・添字・フィールド・dispatch の主語・スカラー以外を取る組み込み・表示・格納）は具体、
   他の関数の引数にそのまま渡す引数は、渡し先が具体なら具体（不動点）、残りは α。走査が見落とした「見る」操作に α が届いたら、
   その解析を捨てて（`throw`）その引数を具体にし、やり直す（`abandoned attempts`）。
   α への要求（組み込みの照合）は効果として記録し、呼び出しごとに実引数を代入して照合する。多相な本体が作った容器は template で、呼び出しごとに複製する。
2. **全体は必要なところだけ**。フィールド・容器・実体化の返り値はセル。読んだセルが変わった実体化は dirty、その呼び出し元の連鎖は「影」（cone）。
   1 周ごとに main から辿り、dirty なものは呼ばれたときに再評価、影の中のものは効果に記録した呼び出しを出し直すだけ（visit）、他は結果を返すだけ。
   もう呼ばれないものは評価しない（v0 が毎 pass main から辿ることで自然に得ている性質）。
3. **報告は最後に組む**。評価中は効果（検査・結果・呼び出し）を記録するだけで、終わったら main から効果を再生し、α を代入しながら v0 と同じ `add_check` に流す。

比較は P10 の SQL エンジン 2 本の段階 6（`../2026-10-05-ai-writability/runs/p10-sake-{1,2}/stage-6/code/main.sake`）と、`test/samples` 151 本。

- `diffchecks.rb MAIN`: 両方の typer を同じプログラムに動かし、検査の集合（file, line, column, op, arg, verdict）と到達しなかった関数を比べる（これが一致の根拠）。
- `compare.rb A B`: `--types` の出力を、サイトのラベル（`Array@L64#2`）を除いて比べる。union 内の順序や複製の数で見かけが違うので、`diffchecks.rb` のほうが確か。
- `bench.sh`: `--strict=2 -c` の壁時計を 3 回ずつ交互に（v0 / Typer2 / Typer2 で型変数なし）。
- `prof2.rb MAIN`（`T=1` で v0）: stackprof。`estimate3.rb`: 見積もりの一部（引数が逃げるか・書かれるか）。
- `out/`: 最終版の `--types` の出力と `compare.rb` の結果。

環境: AMD Ryzen 9 5900HX、Ruby 4.0.2 +PRISM、YJIT（`bin/sake` が有効にする）、load 0.1〜0.8 で他の重いジョブなし。v0 は commit `463a6174` 時点（`ON_DIRTY` の hook を 1 行足した以外は同じ）。

## 分かったこと

- **速くならなかった。** v0 と同じか、sake-2 で 1 割遅い。見積もりどおり、多相で済む実体化は 1〜5% で、残りは本体が引数の型を見るので型ごとに歩く。
  型変数の仕組み（代入・複製・効果の再生）は sake-2 で 0.3 秒の上乗せ。worklist だけなら v0 と同じ。
- **worklist は pass と同じ量の仕事をする。** 影の中だけ辿る形にして、評価回数は v0 の pass とほぼ同数（8,048 対 8,600、4,452 対 4,813）。
  v0 は有効な実体化の効果を毎 pass 再生する分があり、Typer2 は最後に 1 回で済むが、差は測れるほどではなかった。
- 途中で踏んだこと（記録）:
  - 「読んだセルが変わったら即再評価」は v0 の 2 倍の評価になった（細かすぎる）。1 周 1 回に束ねて v0 と同数。
  - 孤立した再評価は、もう呼ばれない古い引数の組（ごみ）まで評価し、そこから新しい組を生む（実体化 8,001 対 4,481）。main から辿る形に戻して解消。
  - v0 が再帰の歯止めとして関数全体で共有するサイトを、多相の実体化の template と誤って印を付け、別の実体化が返したときに複製されず漏れた。
  - 具体化のやり直し（throw）で巻き戻るとき、ブロック評価のスタックと、間に挟まる具体の実体化の再評価の印を戻していなかった。
  - 影の印を評価では消していなかったため、古い印で親への伝播が止まり、不動点が早く終わっていた（検査 18 件・関数 7 つが欠けた）。
- **真の原因は向きではなく表現。** 実体化を増やしているのは、本体が引数の型を見ることと、容器の型が生成地点ごとに別なこと（見積もりで、要素型で見れば実体化は 3.3 倍・2 倍減る）。
  そちらは型の格子の変更で、この書き直しの範囲外。

## 結論

現状の仕様（束縛に型を書かない、nil は union、容器は生成地点）のままでは、推論の向きを変えても検査は速くならない。
Typer2 は v0 と同じ報告を出す別実装として残す（`SAKE_TYPER=2`）。既定は v0 のまま。
