# Stage 5 specification issues (found while writing the stage 5 tests)

SQLite 3.46.1 through `harness/sql_oracle.py`. No test depends on any point below except where noted
("tests assume").

## Disagreements between SQLite and the spec

1. **Compound ORDER BY: a name found only in a later simple-select is accepted** (5.1).
   `CREATE TABLE t (a INTEGER); CREATE TABLE u (b INTEGER); INSERT INTO t VALUES (1), (3); INSERT INTO u VALUES (2);
   SELECT a FROM t UNION SELECT b AS z FROM u ORDER BY z;` SQLite prints `1`, `2`, `3`.
   The spec says a name must be an alias or column name of the **first** simple-select, otherwise
   `1st ORDER BY term does not match any column in the result set`.
2. **Compound ORDER BY: an expression equal to a result expression is accepted** (5.1).
   `SELECT a + 1 FROM t UNION SELECT 0 ORDER BY a + 1;` SQLite prints `0`, `2`, `4`. The spec says any
   term that is not an integer literal or a name is the "does not match" error.
3. **A cte that names itself without RECURSIVE** (5.2). SQLite treats it as recursive:
   `CREATE TABLE c (n INTEGER); INSERT INTO c VALUES (100); WITH c(n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM c WHERE n < 3) SELECT n FROM c ORDER BY n;`
   prints `1`, `2`, `3`; and `WITH items AS (SELECT name, qty FROM items WHERE qty > 0) ...` (with a
   table `items`) is `Error: circular reference: items`. The spec says recursion needs `WITH RECURSIVE`
   and a cte is visible only in the ctes **after** it, so `c` / `items` inside should be the table.
4. **A cte may refer to a later cte** (5.2). `WITH b AS (SELECT y FROM a), a AS (SELECT 1 AS y) SELECT * FROM b;`
   prints `1` in SQLite; the spec ("visible in the ctes after it") implies `no such table: a`. When
   the later cte refers back to the earlier one, SQLite says `circular reference: <name>` (not in the
   catalogue).
5. **ADD COLUMN NOT NULL without a default succeeds on an empty table** (5.6).
   `CREATE TABLE t (a INTEGER); ALTER TABLE t ADD COLUMN b INTEGER NOT NULL;` gives no error in SQLite
   (also with `DEFAULT NULL`); the error appears only when the table has rows. The spec makes it an
   error unconditionally. Tests use this error only on tables that have rows.
6. **Spelling of the name in three view errors** (1.4 "a name the statement wrote is spelled as the
   statement wrote it", 5.3). SQLite prints the name as created, not as written:
   `CREATE TABLE t (a INTEGER); CREATE VIEW v AS SELECT 1; DROP VIEW T; DROP TABLE V; INSERT INTO V VALUES (1);`
   prints `use DROP TABLE to delete table t`, `use DROP VIEW to delete view v`,
   `cannot modify v because it is a view`. The other stage 5 messages (`view V already exists`,
   `no such view: X`, `index I already exists`, `there is already a table named T`, ...) use the
   written spelling. Tests write these names in their created case.
7. **A table or view may not take an index's name** (5.7). `CREATE TABLE t (a INTEGER); CREATE INDEX i ON t (a); CREATE TABLE i (x INTEGER);`
   is `Error: there is already an index named i` in SQLite (same for `CREATE VIEW i`); that message is
   not in the catalogue, and 5.7 ("index names have their own name space, except that an index may not
   take a table's name") suggests the statement succeeds.

## Rules that are unclear or not specified (tests avoid them unless noted)

8. `ALTER TABLE t RENAME TO <an index's name>`: SQLite gives
   `there is already another table or index with this name: <name>`; 5.6 says only "a taken name",
   and 5.7 says index names are a separate name space.
9. `ALTER TABLE t RENAME TO T` (its own name in another case): SQLite gives the "already another table"
   error; the spec does not say whether a table's own name is "taken".
10. `CREATE INDEX` on an unknown table: SQLite prints `no such table: main.<name>` (with `main.`);
    on an unknown column: `no such column: <name>`. The spec gives no error for either.
11. `CREATE INDEX x ON <view> (...)`: SQLite `views may not be indexed`; `CREATE INDEX v ON t (a)` where
    `v` is a view: `there is already a table named v`. Not specified (is a view "a table's name"?).
12. `ALTER TABLE <view> ADD COLUMN ...`: SQLite `Cannot add a column to a view`; the spec only defines
    `no such table` for an unknown table.
13. `IF EXISTS` / `IF NOT EXISTS` across kinds: `DROP VIEW IF EXISTS <table>` and `DROP TABLE IF EXISTS <view>`
    are still the "use DROP ..." errors in SQLite; `CREATE VIEW IF NOT EXISTS <table name>` and
    `CREATE TABLE IF NOT EXISTS <view name>` silently do nothing. The spec does not say.
14. Errors in a view's select are reported when the view is **used**, not by `CREATE VIEW`:
    `CREATE VIEW v AS SELECT nosuchcol;` and `CREATE VIEW v AS SELECT 1 UNION SELECT 1, 2;` succeed; a
    later `SELECT * FROM v` gets the error (a duplicate WITH name is reported at creation). A view's
    column-list count mismatch has a message outside the catalogue. Not specified.
15. Affinity of columns of views, ctes, subquery sources and compound selects: SQLite keeps the
    underlying column's affinity (`CREATE VIEW v AS SELECT a FROM t` with `a INTEGER`: `v.a = '5'` is
    true for 5), even for a compound whose first select gives a literal there
    (`SELECT 7 AS a UNION SELECT a FROM t`). 1.9 gives affinity only to column references of tables.
16. Existing rows after `ADD COLUMN ... DEFAULT v`: 5.6 says they "get its DEFAULT value"; SQLite
    converts it to the column's type (`TEXT DEFAULT 7` gives `'7'`, `REAL DEFAULT 1` gives `1.0`,
    `INTEGER DEFAULT '12'` gives `12`), as 2.1 does for INSERT. **Tests assume** this conversion
    (public 046, hidden 046).
17. SQLite also accepts `WITH ... UPDATE` and `WITH ... DELETE`; the spec defines only `WITH ... INSERT`.
    Tests use only the INSERT form.
18. SQLite treats some words that are not in the spec's keyword list as keywords (e.g.
    `ALTER TABLE nothing ...` is a syntax error). Tests avoid such names.
