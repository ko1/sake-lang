# Stage 3 specification issues (found while writing the stage 3 tests)

SQLite 3.46.1 through `harness/sql_oracle.py` (STRICT tables). Table used below unless stated:
`CREATE TABLE t (a INTEGER, b INTEGER, s TEXT); INSERT INTO t VALUES (1, 10, 'x'), (1, 20, 'y'), (2, 30, NULL);`
No test depends on any point below.

## Disagreements between SQLite and the spec

1. **Aggregate call only in ORDER BY.** `SELECT a FROM t ORDER BY count(*);`
   SQLite: `Error: misuse of aggregate: count()` (a message outside the catalogue).
   Spec 3.3: "A query is an aggregate query if it has GROUP BY, or an aggregate call in its result
   columns, HAVING or ORDER BY", so this should be an aggregate query printing one row (a bare `a`).
   (With GROUP BY, or with another aggregate in the result columns, SQLite agrees with the spec.)

2. **Aggregate call only in HAVING, no GROUP BY.** `SELECT 1 FROM t HAVING count(*) > 2;`
   SQLite: `Error: HAVING clause on a non-aggregate query`.
   Spec 3.1/3.3: an aggregate call in HAVING makes it an aggregate query, so HAVING is allowed and the
   query prints `1`. (`SELECT count(*) FROM t HAVING count(*) > 2;` works in both.)

3. **WHERE naming an alias of an aggregate.** `SELECT count(*) AS n FROM t WHERE n > 1;`
   SQLite: `Error: misuse of aggregate: count()`.
   Spec 1.7 (a WHERE name may be a result column's alias, standing for its expression) + 3.3 (an
   aggregate call in WHERE is `misuse of aggregate function <name>()`): the spec's message would be
   `misuse of aggregate function count()`.

4. **sum() of TEXT that looks like an integer.** `SELECT sum('3'), typeof(sum('3')) FROM t;`
   SQLite: `9|integer`.
   Spec 3.2: sum is INTEGER only "if every non-NULL x is an INTEGER"; TEXT is "read by numeric prefix
   as REAL", so the spec gives `9.0|real`. SQLite treats text that is an integer literal as an INTEGER
   (`sum('2.5')`, `sum('abc')`, `sum(' 2x')` agree with the spec: REAL). Same for a TEXT column
   holding `'3'`.

5. **max/min with DISTINCT and two arguments.** `SELECT max(DISTINCT a, b) FROM t;`
   SQLite: the scalar max per row (`10`, `20`, `30`), no error.
   Spec 3.2: "With DISTINCT, a call must have exactly one argument, else the error is
   `DISTINCT aggregates must have exactly one argument`" (but also: max/min with two or more
   arguments "stay the scalar functions"; which rule wins is not said).

6. **count/sum with DISTINCT and two arguments.** `SELECT count(DISTINCT a, b) FROM t;` and
   `SELECT sum(DISTINCT a, b) FROM t;`
   SQLite: `Error: wrong number of arguments to function count()` / `... sum()`.
   Spec 3.2 gives `DISTINCT aggregates must have exactly one argument` for any DISTINCT call with
   more than one argument. SQLite gives that message only for `group_concat(DISTINCT x, sep)`, the
   one aggregate that accepts two arguments. Tests only use the group_concat form.

7. **GROUP BY with a negative integer.** `SELECT a FROM t GROUP BY -1;`
   SQLite: `Error: 1st GROUP BY term out of range - should be between 1 and 1`.
   Spec 1.2 says `-1` is unary minus applied to `1`, and 3.3 makes only "an integer literal k" a
   column number, so by the spec `-1` is a constant expression (one group).

## Unclear or untestable rules

8. **`integer overflow`** (3.2, 3.5) is in the error catalogue, but 3.2 says tests do not reach it and
   the brief requires integers far from 64-bit limits; so it has no test.

9. **group_concat with a NULL separator.** `SELECT group_concat(s, NULL) FROM t;` SQLite: `xy`
   (NULL taken as ''). The spec says only "joined by sep's text form"; 1.11's "a NULL argument gives
   NULL" would give NULL. Not tested.

10. **Bare column in an aggregate query without GROUP BY over no rows.**
    `SELECT a, count(*) FROM t WHERE 0;` SQLite: `NULL|0`. 3.3 says a bare column "takes its value from
    one row of the group", but the group has no rows. Not tested.

11. **`count()` with no arguments.** SQLite accepts it as `count(*)`; the spec lists only `count(*)`
    and `count(x)`, so a zero-argument `count()` is presumably `wrong number of arguments`. Not tested.

12. **"exactly one aggregate call" for the min/max bare-column rule** does not say whether calls in
    HAVING and ORDER BY count. SQLite counts them (`SELECT name, club FROM r GROUP BY club HAVING
    max(secs) > 0` takes `name` from the max row), and the tests rely on that reading (public 033).
