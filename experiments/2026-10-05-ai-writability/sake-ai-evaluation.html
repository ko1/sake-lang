AI 向け言語 Sake の評価

2026-10-06〜07 ・ Claude Sonnet 5.5 に Sake と Ruby で、書かせ、直させ、読ませた結果（P1〜P6、解く側 190 体。P6 は 2,500 行のインタプリタ）

  1. 正しさは、どの作業でも Ruby と同じ。事前学習で一度も見ていない言語なのに、新しく書く・既存のコードを変える・読んで出力を当てる・誤りを直す、のすべてで Ruby と同じ正答率に届いた。
  2. コストの上乗せは、書くときと大きなコードを変えるときに大きく、読むときに小さい。出力トークンで Sake は Ruby に対して次の倍率になった。
    • 小さい題を書くと 1.6 倍（実行せずに書くと 2.4 倍）、変えると 1.4 倍。
    • 読んで当てると 1.4 倍、誤りを直すと 1.1 倍。
    • 2,500 行のインタプリタでは、一から書くと 1.4 倍、仕様を変えると 1.8〜2.1 倍。時間は 5〜13 倍かかった。
  3. その上乗せは、見える誤りには出てこない。存在しない API はほぼ書かず、検査に止められるのは 10 試行に 1 回程度で、止められても次で直る。上乗せは書く直前の思考に集中している。モデルは Sake の書き方を書く前に確かめていると読める（推定）。
  4. 型を操作に書く利点は、正しさの差としてはまだ観測できない。
    • 2,500 行の仕様変更で初めて、検査器が「変更の届くべき箇所」（新しい構文木の型を入れ忘れた場所）を指した。
    • ただ、Ruby 側も読んで同じ箇所を見つけ、正答率はどの作業でも同じ天井に張り付いた。
  5. 大きなコードでは、処理系の側に課題が見えた。
    • 2,500 行の検査に 3〜24 秒かかり、書き方で 7.5 倍違う。Ruby から移した形が遅い。
    • 誤りを含むコードでは、検査が何も報告しないまま 10〜15 分以上走ることがある。
    • Sake の時間のかかり方の大半は、この処理系の側から来ている。

何を確かめたか

Sake は Ruby の構文で、すべての操作に型を書く言語（String.upcase(s)）。変数や引数に型は書かず、実行前に検査器が型を追う。問いは「AI にとって、書きやすく、直しやすく、読みやすいか」。比べる相手は Ruby で、同じ題を同じモデルに同じ指示で解かせた。

もし Sake の上乗せが「迷って誤る」ことの表れなら、どこかの数字に Sake 側の誤りが積み上がるはず。新しく書く題（P3）で、解答と試行の記録だけから数えた。

  • 検査に止められても、次の試行で直る（6 回とも）。理由の半分は Ruby の書き方の持ち込みだった（値へのメソッド呼び出し c.abs、Array.slice）。試行の回数も両言語でほぼ同じ。

結果 5: 型検査は正しさを上げなかった

型を操作に書く利点として期待していたのは、検査器が誤りを先に捕まえることだった。どの作業でも、それは正答率に表れなかった。

  • 新しく書く題: 検査が止めたのは主に Sake の書き方の誤りだった。本物の型の誤りも捕まえたが、Ruby 側では同種の誤りが公開例の実行で見つかっていて、最終的な正答率に差は出なかった。
  • 検査のせいで落とした解: 実行すれば正しい解を検査が止めて落とした例が、一発で書く条件に 2 件ある。試せる条件では 0 件（P2〜P4 の Sake の全 180 件）。
    • P1 の 1 件は、配列を含むタプルの比較についての検査の誤報で、修正済み。
    • P2 の 1 件は、1 つの配列に整数と文字列を混ぜて記録として使った書き方で、検査は「位置ごとに型を保つならタプルにせよ」と止めた。実行せずに書く条件なので、直す機会がなかった。

    前の版では「P2 以降、検査のせいで落とした例はない」と書いていたが、誤りだった（P2 に 1 件あった）。

  • 既存のコードを変える題（P4）: 値の型が変わる変更要求で、直し忘れを検査器が指すかを見た。
    • 止めたのは 47 試行中 2 回で、どちらも直し忘れではなかった。新しく書いたコードでタプルを Array.fetch に渡したもので、タプルと配列を区別する Sake の摩擦である。
    • 落ちたケースの大半は、変わらないはずの振る舞いの崩れ（Ruby 5 件中 4、Sake 4 件中 3）で、型では捕まらない。
  • 読む作業（P5）: 型が書いてあることで読むのが速く・正確になる、ということもなかった（どちらも天井）。ただ、邪魔にもなっていない。

結果 6: 2,500 行のインタプリタでも天井、コストは処理系で膨らむ

小さい題では、変更の行き先を見落とす余地がなかった。そこで、全体を一度に読めない規模の題材を作った。小さな動的型付き言語 Mini のインタプリタで、トークン・構文木・値・環境がファイルをまたいで流れる。

  • 題材: 言語仕様（628 行）とテスト 298 本の上に、インタプリタを 3 つ用意した。3 つとも全テストに通る。
    • Ruby 版: 14 ファイル・2,540 行。
    • Sake 移植版: 2,571 行。ファイル・型・関数を Ruby と 1 対 1 に移したもの。
    • Sake スクラッチ版: 2,451 行。仕様だけを見て Sake らしく書いたもの。
  • 仕様変更 8 題（各題に 3 つのコードベース分の参照の修正と、テスト 314〜325 本を付けた）:
    • 型や形が変わるもの 4: 小数を足す、エラー位置を範囲に、map のキーを広げる、実行時エラーに関数名。
    • 構文の追加 2: a..b、a?.b。
    • 振る舞いだけ 2: 割り算の丸め、repr の書き方。

一から書く（ゴールを揃えて、各言語 2 体）

同じ仕様とテストで、全テスト通過までを比べた。4 体とも 2,000〜2,500 行・15 ファイルで書き上げた。Sake は出力 1.37 倍（84〜86k 対 56〜68k）、時間 2.2 倍（31〜33 分対 12〜18 分）。小さい題（1.62 倍）より比が小さい。Sake の 2 体がつまずいたのは、--strict=2 に通すための型の絞り込みだった。

移植の知見（Ruby → Sake）

  • 行数はほぼ同じ（1.01 倍）。1 対 1 に移せなかった箇所はどれも局所的だった。
    • 予約名との衝突（Index）
    • 定数は関数に
    • private がない
    • 配列のパターンがない
    • case/in の else nil
    • 値へのメソッド呼び出しの書き換え
  • --strict=2 に通すための絞り込みが 18〜26 か所要った。
  • 移した形のまま使うと、上の検査時間の問題に当たる。

どう読むか

学べる言語にはなっている。事前学習ゼロで、書く・変える・読む・直すのすべてで Ruby と同じ正しさに届く。Ruby の構文と Ruby の名前（String.upcase）を借りた設計が効いていると考えられる。存在しない API をほとんど書かないのも、名前が Ruby と同じだからだろう。

コストは「書く」に集中している。読む・直すでは上乗せが 1.1〜1.4 倍に縮み、新しく書くと 1.6 倍、実行せずに書くと 2.4 倍に膨らむ。モデルは Sake を読むときは Ruby とほぼ同じように読めるが、書くときは毎回「どの型の何という操作か、それはあるか」を組み立てている。AI にとって Sake は、読むのは安く、書くのが高い言語である。

大きなコードでは、言語より処理系がコストを決める。2,500 行の仕様変更では、出力は 1.8〜2.1 倍だが、時間は 5〜13 倍になった。時間の大半は検査の遅さと打ち切りで、どちらも処理系の性能と不具合である。書き方（移植版かスクラッチ版か）でも大きく変わる。AI に書かせる言語として使うなら、まず検査器を大きなプログラムで速く、確実に止まるようにする必要がある。

型を書く利点は、正しさの差としてはまだ観測できていない。どの作業でも型は正答率を上げなかった。落ちる原因は仕様の読み違いや振る舞いの崩れで、型の誤りではなかった。2,500 行では、検査器が変更の届くべき箇所を指す場面が実際にあった。ただ、Ruby 側も読んで見つけられる規模だった。利点が正しさの差として出るとすれば、次の場面だろう。

  • 書き手が行き先を見落とすほど大きなコード（1 万行以上）
  • 書き手より弱いモデル
  • もっと難しい読む作業（例を渡さずに誤りを探す、長い入力を追う）

書くコストを減らす手がかりは、モデルが書く前に迷う点そのもので、見える誤りから少し拾える。

  • 値へのメソッド呼び出し（Ruby の癖）
  • タプルと配列の区別
  • あるはずと思われる操作（slice）

ただし、どれも 10 試行に 1 回程度の頻度で、上乗せの大部分を説明する量ではない。

限界

  • モデルは Sonnet 5.5 だけ。題は中規模（40〜150 行）の 20 題とその派生、および 2,500 行のインタプリタ 1 つ。API ではなくサブエージェントで回したので、温度やトークン計上は細かく揃えていない。
  • P6 の各セルは 2 反復（一から書くのは各言語 2 体）。大きなコードの題材は 1 つで、変更要求も含めて AI が作った。
  • P6 の時間は、同時に走る他のエージェントの負荷を含む。比は同じ条件で取っているが、絶対値は参考値。
  • P6 で「参照が触れた関数を、解答が触れなかった数」を直し忘れの指標にしようとしたが、使えなかった。参照と違う関数を書き換えて同じ結果に達する解（隠しテスト全通過）が多く、設計の違いを数えてしまう。正しさは隠しテストで見た。
  • 変える・読む・直すの題は易しく、正答率が天井に近い（9 割以上）。正しさの差が出ないのは、差がないからとは限らない。
  • Ruby は事前学習で知っている言語なので、この比較は「新しい言語」と「慣れた言語」の比較でもある。
  • 題・変更要求・誤りは AI が書いた。仕様の曖昧さは、どの言語にも同じように効いている。
  • 出力トークンは題ごとには分けられない（エージェントが複数の題をまとめて読み書きするため）。エージェント単位で数え、題数で割っている。
  • 逸脱:
    • 読む作業で「何も実行しない」と指示したが、出力の予測では多くのエージェントが、答えの表の列幅をそろえるのにシェルの printf や Python の書式を使った（両言語とも）。
      • 記録を洗い出した範囲では、値そのものを計算した形跡はない。
      • こうした題を除いても結論は変わらない（Sake 39/44、Ruby 34/42）。
    • 変える作業では Ruby の 2 体が、編集をスクリプトで当てた。

次に測ること

思考の中身を見る。書く前に「使う操作と型、迷った点」を短く書き出させる条件を足して比べる。

取り下げた（P3 の設計時）。書き出させると、測りたい「書く過程」そのものが変わる。代わりに、見える結果だけを数える形にした（結果 4）。

  • 天井を外す。
    • 誤りの修正では、例を渡さず仕様と誤ったプログラムだけにする。誤りも複数の箇所にまたがるものにする。
    • 出力の予測は、長いプログラムと長い入力にする。
  • 処理系を直してから測り直す。大きなプログラムでの検査の遅さ（型の和を作る処理）と、誤ったコードでの打ち切りを直す。そのうえで P6 の変更を流し直す。時間の比のうち、どれだけが言語でどれだけが処理系かを分けられる。
  • さらに大きく。2,500 行でも天井だった。1 万行・数十ファイルで、直し忘れが実際に起きるかを見る。
  • モデルを替える。小さいモデルほど新しい言語の差が出て、検査器の出番も増えるはず。
