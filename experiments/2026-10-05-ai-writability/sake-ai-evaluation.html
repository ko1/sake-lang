AI 向け言語 Sake の評価

2026-10-06〜07 ・ Claude Sonnet 5.5 に Sake と Ruby で、書かせ、直させ、読ませた結果（P1〜P6、解く側 190 体。P6 は 2,500 行のインタプリタ）。小さいモデル Claude Haiku 4.5 でも、新しく書く題を流した（P7h・P9h、44 体）。検査器を直したあと、大きなコードの仕様変更も流し直した（P6f、24 体）。2026-10-08 には、SQL エンジンを 6 段階で 3,000〜4,000 行まで育てさせた（P10、24 体）。同じ課題を Java・Haskell・Scheme・Steep 付き Ruby でも流した（P10b、48 体）

結論（2026-10-08）: 型を操作に書くことは、AI にとっての書きやすさを上げなかった。評価と Sake の開発はここで終える。

  • 正しさに差が出ない。Sonnet では、どの作業でも Ruby と同じ。SQL エンジンでは 6 言語・12 系列が同じ点に並び、どの言語でも、型検査が防いだと言える誤りはなかった。
  • 費用は Sake が最も高い。出力トークンは Ruby の 1.71 倍。型を全部書かせる Steep 付き Ruby でも 1.48 倍。処理系を速くしても、Ruby を下回る筋は見えない。
  • 小さいモデルでは負ける。Haiku では隠しテストの通過率が 26% 対 77%。
  • 覆る条件: Sonnet 級が天井から明確に落ちる題で、静的な型検査（言語を問わない）が、動的型の解では残る誤りを止めることが観測されたとき。
  • 測っていない問い: 人間にとって読みやすいか（AI が生成したコードを人がレビューする場面など）。このページで読ませたのは AI だけである。測るなら、誤りを仕込んだ同じ変更を Ruby 版と Sake 版で人にレビューしてもらい、見つけた数と時間を比べる。

以下は、結論に至るまでの各段階の結果（v12 までの本文をそのまま残している）。

  1. Sonnet では、正しさはどの作業でも Ruby と同じ。事前学習で一度も見ていない言語なのに、新しく書く・既存のコードを変える・読んで出力を当てる・誤りを直す、のすべてで Ruby と同じ正答率に届いた。
  2. 小さいモデル（Haiku 4.5）では、Sake は Ruby に大きく負ける。新しく書く題の隠しテストの通過率は、2 反復で、試せる条件で Sake 26% 対 Ruby 77%、一発で 1% 対 52%。Sake の一発の解答は 40 本中 36 本が検査に止められた。資料をチートシートに替えても、「書く前に使う操作を全部引け」と指示しても縮まなかった。「資料を読めば書ける」は Sonnet では成り立つが、Haiku では成り立たない（結果 7）。
  3. 出力トークンの上乗せは、書くときと大きなコードを変えるときに大きく、読むときに小さい。1 題あたりの出力トークンで、Sake は Ruby に対して次の倍率になった。
    • 小さい題を書くと 1.6 倍（実行せずに書くと 2.4 倍）、変えると 1.4 倍。
    • 読んで当てると 1.4 倍、誤りを直すと 1.1 倍。
    • 2,500 行のインタプリタでは、一から書くと 1.4 倍、仕様を変えると 1.8〜2.1 倍。仕様を変える作業時間は 5〜13 倍かかった（検査器を直したあとは 3.7〜6.4 倍）。
  4. その上乗せは、見える誤りには出てこない（Sonnet）。存在しない API はほぼ書かず、検査に止められるのは 10 試行に 1 回程度で、止められても次で直る。上乗せは書く直前の思考に集中している。モデルは Sake の書き方を書く前に確かめていると読める（推定）。
  5. 型を操作に書く利点は、正しさの差としてはまだ観測できない。
    • 2,500 行の仕様変更で初めて、検査器が「変更の届くべき箇所」（新しい構文木の型を入れ忘れた場所）を指した。
    • ただ、Ruby 側も読んで同じ箇所を見つけ、正答率はどの作業でも同じ天井に張り付いた。
  6. SQL エンジンを 6 段階で育てさせても、正しさは同じ（P10）。Ruby・Sake 各 2 系列が 3,000〜4,000 行まで育て、隠しテスト 369 本で 366〜368 本。落ちた 3 種類のうち 2 種類は両言語に共通で、型が防いだ誤りはなかった。Sake は出力トークン 1.7 倍、作業時間 3.5 倍、行数 1.25 倍。新しい検査器の不具合（止まらない型の計算）を 1 つ見つけた（結果 8）。
  7. 同じ SQL エンジンを Java・Haskell・Scheme・Steep 付き Ruby で書かせても、正しさは同じ（P10b）。出力トークンは Ruby を 1 として Java 1.06、Haskell 1.18、Scheme 1.22、Steep 1.48、Sake 1.71 倍。型を全部書かせる Steep は、検査に止められた回数が Sake とほぼ同じで、出力トークンは Sake の 86%。Sake の上乗せのうち、型を書くことによる分と、Sake 固有の分を分ける手がかりになる（結果 9）。
  8. 大きなコードでは、処理系の側に課題が見えた。
    • 2,500 行のプログラムの検査時間は 1 回 3〜24 秒で、書き方で 7.5 倍違う。Ruby から移した形が遅い。
    • 誤りを含むコードでは、検査が何も報告しないまま 10〜15 分以上走ることがある（その後、検査器を直した。「次に測ること」）。
    • 大きなコードを変えるときの、Sake の作業時間の上乗せの大半は、この処理系の側から来ている。
    • 検査器を直して流し直すと（P6f）、検査が止まらなくなる例は消え、作業時間の比は 13.1 倍 → 6.4 倍（移植版）に縮んだ。残りの大半は、テストを流すたびに 2,500 行のプログラムを読み込み直す起動の時間（1 本 0.3 秒、Ruby の約 5 倍）である。

何を確かめたか

Sake は Ruby の構文で、すべての操作に型を書く言語（String.upcase(s)）。変数や引数に型は書かず、実行前に検査器が型を追う。問いは「AI にとって、書きやすく、直しやすく、読みやすいか」。比べる相手は Ruby で、同じ題を同じモデルに同じ指示で解かせた。

このページで使う量と単位

  • 出力トークン: モデルが生成したトークンの数。次の 3 つを含む。
    • 思考（記録には量だけが残り、中身は残らない）
    • 本文（返答の文章）
    • 道具への入力（ファイルに書いたコード、シェルのコマンドなど）
    Claude Code の記録にある各呼び出しの output_tokens を、エージェント 1 体の全呼び出しで足した。「1 題あたり」は、それを担当した題の数で割った値。k は 1,000 トークン。
  • 作業時間: エージェント 1 体の記録の最初から最後までの壁時計時間。モデルが生成する時間に加えて、道具の実行（Sake では検査器 --strict=2 -c とテストの実行）を待つ時間も含む。
  • 検査時間: Sake の検査器 bin/sake --strict=2 -c を 1 回走らせて終わるまでの時間。
  • X 倍: 特に断りがなければ、同じ作業・同じ条件での「Sake の値 ÷ Ruby の値」。
  • 上乗せ: Sake の出力トークンが Ruby より多い分。作業時間の差は「作業時間」と書いて分ける。
  • 思考トークン: 呼び出しごとの「出力トークン − 見えている出力（本文と道具への入力）のトークン」。見えている出力は Claude 2 世代のトークナイザで数えた近似。

結果 5: 型検査は正しさを上げなかった

型を操作に書く利点として期待していたのは、検査器が誤りを先に捕まえることだった。どの作業でも、それは正答率に表れなかった。

  • 新しく書く題: 検査が止めたのは主に Sake の書き方の誤りだった。本物の型の誤りも捕まえたが、Ruby 側では同種の誤りが公開例の実行で見つかっていて、最終的な正答率に差は出なかった。
  • 検査のせいで落とした解: 実行すれば正しい解を検査が止めて落とした例が、一発で書く条件に 2 件ある。試せる条件では 0 件（P2〜P4 の Sake の全 180 件）。
    • P1 の 1 件は、配列を含むタプルの比較についての検査の誤報で、修正済み。
    • P2 の 1 件は、1 つの配列に整数と文字列を混ぜて記録として使った書き方で、検査は「位置ごとに型を保つならタプルにせよ」と止めた。実行せずに書く条件なので、直す機会がなかった。

    前の版では「P2 以降、検査のせいで落とした例はない」と書いていたが、誤りだった（P2 に 1 件あった）。

  • 既存のコードを変える題（P4）: 値の型が変わる変更要求で、直し忘れを検査器が指すかを見た。
    • 止めたのは 47 試行中 2 回で、どちらも直し忘れではなかった。新しく書いたコードでタプルを Array.fetch に渡したもので、タプルと配列を区別する Sake の摩擦である。
    • 落ちたケースの大半は、変わらないはずの振る舞いの崩れ（Ruby 5 件中 4、Sake 4 件中 3）で、型では捕まらない。
  • 読む作業（P5）: 型が書いてあることで読むのが速く・正確になる、ということもなかった（どちらも天井）。ただ、邪魔にもなっていない。

結果 6: 2,500 行のインタプリタでも正しさは天井、作業時間は処理系で膨らむ

小さい題では、変更の行き先を見落とす余地がなかった。そこで、全体を一度に読めない規模の題材を作った。小さな動的型付き言語 Mini のインタプリタで、トークン・構文木・値・環境がファイルをまたいで流れる。

  • 題材: 言語仕様（628 行）とテスト 298 本の上に、インタプリタを 3 つ用意した。3 つとも全テストに通る。
    • Ruby 版: 14 ファイル・2,540 行。
    • Sake 移植版: 2,571 行。ファイル・型・関数を Ruby と 1 対 1 に移したもの。
    • Sake スクラッチ版: 2,451 行。仕様だけを見て Sake らしく書いたもの。
  • 仕様変更 8 題（各題に 3 つのコードベース分の参照の修正と、テスト 314〜325 本を付けた）:
    • 型や形が変わるもの 4: 小数を足す、エラー位置を範囲に、map のキーを広げる、実行時エラーに関数名。
    • 構文の追加 2: a..b、a?.b。
    • 振る舞いだけ 2: 割り算の丸め、repr の書き方。

どう読むか

Sonnet にとっては、学べる言語になっている。事前学習ゼロで、書く・変える・読む・直すのすべてで Ruby と同じ正しさに届く。Ruby の構文と Ruby の名前（String.upcase）を借りた設計が効いていると考えられる。存在しない API をほとんど書かないのも、名前が Ruby と同じだからだろう。ただし Haiku では成り立たない（結果 7）。資料を読んで書き方を確かめる力がモデルに要り、それがないモデルには、Sake は Ruby よりはっきり書きにくい。

出力トークンの上乗せは「書く」に集中している。1 題あたりの出力トークンの比は、読む・直すでは 1.1〜1.4 倍に縮み、新しく書くと 1.6 倍、実行せずに書くと 2.4 倍に膨らむ。モデルは Sake を読むときは Ruby とほぼ同じように読めるが、書くときは毎回「どの型の何という操作か、それはあるか」を組み立てている。AI にとって Sake は、読むのは安く、書くのが高い言語である。

大きなコードでは、作業時間は言語より処理系で決まる。2,500 行の仕様変更では、1 体あたりの出力トークンは 1.8〜2.1 倍だったが、作業時間は 5〜13 倍になった。作業時間の上乗せの大半は検査の遅さと打ち切りで、どちらも処理系の性能と不具合である。検査器を直すと 3.7〜6.4 倍に縮み、残りの多くはテストのたびの起動の時間だった（P6f）。出力トークンの上乗せも、小さい題とは中身が違う（結果 6 の「出力トークンの中身」）。変更を考えて書く呼び出しの思考は Ruby と同じくらいで、増えたのはコードを読み解く思考と、検査に止められて試し直す・待つまわりだった。書き方（移植版かスクラッチ版か）でも大きく変わる。AI に書かせる言語として使うなら、まず検査器を大きなプログラムで速く、確実に止まるようにする必要がある。

型を書く利点は、正しさの差としてはまだ観測できていない。どの作業でも型は正答率を上げなかった。落ちる原因は仕様の読み違いや振る舞いの崩れで、型の誤りではなかった。2,500 行では、検査器が変更の届くべき箇所を指す場面が実際にあった。ただ、Ruby 側も読んで見つけられる規模だった。利点が正しさの差として出るとすれば、次の場面だろう。

  • 書き手が行き先を見落とすほど大きなコード（1 万行以上。P10 では 4,000 行まで育てても差は出ず、共通の見落としは両言語に同じように出た。結果 8。Java・Haskell・Steep でも同じだった。結果 9）
  • 書き手より弱いモデル（Haiku で試した。検査は誤ったプログラムを止めたが、止められたものを正しく直すところまでは届かず、正答は増えなかった。結果 7）
  • もっと難しい読む作業（例を渡さずに誤りを探す、長い入力を追う）

書くときの出力トークンを減らす手がかりは、モデルが書く前に迷う点そのもので、見える誤りから少し拾える。

  • 値へのメソッド呼び出し（Ruby の癖）
  • タプルと配列の区別
  • あるはずと思われる操作（slice）

ただし、どれも 10 試行に 1 回程度の頻度で、出力トークンの上乗せの大部分を説明する量ではない。

限界

  • モデルは主に Sonnet 5.5。Haiku 4.5 は新しく書く題だけ（各条件 2 反復、手を加えた条件は 1 反復）。題は中規模（40〜150 行）の 20 題とその派生、および 2,500 行のインタプリタ 1 つ。API ではなくサブエージェントで回したので、温度やトークン計上は細かく揃えていない。
  • P6 の各セルは 2 反復（一から書くのは各言語 2 体）。大きなコードの題材は 1 つで、変更要求も含めて AI が作った。P10 も各言語 2 系列で、仕様は SQLite の挙動を 1 つずつ確かめて書いたが、テストの作成と検証は AI が行った。
  • P6 の作業時間は、同時に走る他のエージェントの負荷を含む。比は同じ条件で取っているが、絶対値は参考値。
  • P6 で「参照が触れた関数を、解答が触れなかった数」を直し忘れの指標にしようとしたが、使えなかった。参照と違う関数を書き換えて同じ結果に達する解（隠しテスト全通過）が多く、設計の違いを数えてしまう。正しさは隠しテストで見た。
  • 変える・読む・直すの題は易しく、正答率が天井に近い（9 割以上）。正しさの差が出ないのは、差がないからとは限らない。
  • Ruby は事前学習で知っている言語なので、この比較は「新しい言語」と「慣れた言語」の比較でもある。結果 9 で Java・Haskell・Scheme・Steep 付き Ruby を足したが、どれも事前学習で知っている言語で、「知らない言語」の対照にはなっていない。
  • P10b の Haskell は他の言語より後に、2 系列だけで流した（GHC を入れたのが後だったため）。
  • 結果 9 の v11 では Scheme の出力トークンを 233k・1.21 倍と書いていた。2 系列平均 233,502 を四捨五入すると 234k、比は 1.216 で 1.22。v12 で直した。
  • 題・変更要求・誤りは AI が書いた。仕様の曖昧さは、どの言語にも同じように効いている。
  • 出力トークンは題ごとには分けられない（エージェントが複数の題をまとめて読み書きするため）。エージェント単位で数え、題数で割っている。
  • 逸脱:
    • 読む作業で「何も実行しない」と指示したが、出力の予測では多くのエージェントが、答えの表の列幅をそろえるのにシェルの printf や Python の書式を使った（両言語とも）。
      • 記録を洗い出した範囲では、値そのものを計算した形跡はない。
      • こうした題を除いても結論は変わらない（Sake 39/44、Ruby 34/42）。
    • 変える作業では Ruby の 2 体が、編集をスクリプトで当てた。

次に測ること

2026-10-08 に評価を終えたので、以下は終了時点で残っていた候補の記録である。どれも投入していない。

思考の中身を見る。書く前に「使う操作と型、迷った点」を短く書き出させる条件を足して比べる。

取り下げた（P3 の設計時）。書き出させると、測りたい「書く過程」そのものが変わる。代わりに、見える結果だけを数える形にした（結果 4）。

  • 天井を外す。
    • 誤りの修正では、例を渡さず仕様と誤ったプログラムだけにする。誤りも複数の箇所にまたがるものにする。
    • 出力の予測は、長いプログラムと長い入力にする。
  • 処理系を直してから測り直す。大きなプログラムでの検査の遅さ（型の和を作る処理）と、誤ったコードでの打ち切りを直す。そのうえで P6 の変更を流し直す。作業時間の比のうち、どれだけが言語でどれだけが処理系かを分けられる。
    • 検査器は 2026-10-07 に直した。型の和を覚えておくことで、移植版の検査は 23.4 秒 → 8.2 秒（手元の計算機、5 回）。比較の要素の型の組が 5 万を超えたら、その比較の要素の検査をやめて警告を出すようにした。止まらなかった 7 本は 9〜13 秒で終わり、隠れていた本物の型の誤りを 2〜5 件ずつ報告した。
    • P6f で流し直した（結果 6）。作業時間の比は 13.1 → 6.4 倍（移植版）、4.9 → 3.7 倍（スクラッチ版）。次は起動の時間（テスト 1 本 0.3 秒）を減らす。
  • さらに大きく。2,500 行でも天井だった。P10 で SQL エンジンを 6 段階で育てさせたが、3,000〜4,000 行で止まり、正しさは同じだった（結果 8）。1 万行に届かせるには段階を足す必要がある。
  • 検査器の止まらない型の計算を直す。互いに呼び合う関数の Array + Array（結果 8）。直したら、P10 の Sake 系列の待ち時間を測り直す。
  • 小さいモデルで、どこで止まるかを見る。反復を足し、チートシートと「書く前に引け」を試したが縮まなかった（結果 7）。次は、検査に止められたあとの直し方を見る。止められた誤りの種類（型・構文・名前）ごとに、次の試行で直ったかを数える。
