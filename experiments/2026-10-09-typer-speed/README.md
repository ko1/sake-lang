`bin/sake --strict=2 -c` が 4,400 行のプログラムで 190 秒かかっていた（P10 の SQL エンジン。
`experiments/2026-10-05-ai-writability/README.md` の「検査が遅い件」）。Ruby のまま直した。
対象 commit: この README と同じ commit の `lib/sake/typer*.rb`。

  （別のエージェントが書いた SQL エンジン。stage-6 は 4,400 行）。

### 結果は同じか

- `--types` の報告（全検査の判定と、全サイトの要素型）を直す前（`baseline/`、HEAD の素のコードで取った）と後（`after/`）で比べた。

- stage-6（2 本）: 検査の集合（判定・行・操作・引数）は**同一**（sake-1: 15 行、sake-2: 390 行。proven/partial/unknown の数も同じ）。
  報告の文面は変わる: 配列サイトの番号（`Array@L30#7` の `#7`）と、サイトの一覧。理由は下の「収束しなかった」。
- `test/` の 201 件は全部通る。

## 何が遅かったか

stackprof（cpu）で見た。

1. **型（ネストした配列）を値でハッシュしていた。** 型の和 `Typer.union` の memo、関数の実体化の表 `@done` / `@returns` のキー `[fn, args]`
   （`fn` は Struct で、`Struct#hash` は本体の AST まで辿る）、`compared_groups` の `seen`。`Array#hash` だけで 19%。
2. **`struct_hooks` を組み込み呼び出しごとに全部やり直していた。** 引数の型から到達できる Struct 型を、フィールド・要素・Tuple の位置を辿って集める
   歩きで、呼び出しのたびに同じ歩きを繰り返していた（累積 46〜58%）。
3. **固定点が収束しなかった（stage-6 だけ）。** 上限の 30 回まで回り、1 回 3.3 秒。毎回、配列サイトが 122 個、実体化が 219 個増えていた。
   原因: コンテナのサイトは「作る場所 × その関数の実体化（引数の型）」ごとに作る。引数が、この関数自身が作ったコンテナを含むときは共有する
   （再帰の歯止め）が、f が作った配列を g に渡し、g が作った配列を f に渡す、という往復は止まらず、毎回新しいサイトを作っていた。
   stage-6 では 2 つの場所がそれぞれ 882 個のサイトを持っていた（`compound.sake` の `unique(rows)` のあたり。
   `Query.compute` → 複合 SELECT → `unique` → `Query.compute` …）。

## 直したこと（`lib/sake/typer.rb`、`typer_eval.rb`、`typer_ext.rb`）

1. **型をインターンする。** 正規形（整列・frozen）1 つにつきオブジェクト 1 つ（`Typer.intern`、`CANON`）。等しい型は同一オブジェクトになり、
   同一性で比べられる。和の memo（2 引数は `UNION2`、それ以上は id の列）、実体化の表（`inst_key`: 関数と型の id）、
   `compared_groups` の `seen`、`@instantiated` などを同一性キーにした。単一原子の型は `one(a)`、原子の集まりは `of_atoms(atoms)`、
   Tuple は要素の id で memo、サイトの型は `site_type(kind, id)` で 1 つにする。
2. **`struct_hooks` を memo する。** キーは引数の型の id。歩きが読んだコンテナ（サイトの要素型・フィールドの表）と、そのとき持っていた型を
   `deps` として覚え、どれも同一（identity）なら再利用する。書き込みの世代 `GEN`（変化した書き込みだけ数える）が memo のときと同じなら
   deps も見ない。型ごとに固定な部分（Struct 原子、Tuple・Record の各位置の型）は `shape_of` で型ごとに 1 回だけ計算する。
3. **`add_check` の判定の合成を数で持つ。** 経路ごとの判定を毎回 reduce していたのを、判定ごとの件数から最悪を取る形にした。
   検査のキー（行・列・操作・引数・ファイル）はノードごとに 1 回作る。
4. **再帰の歯止めを「作った関数」から「文脈の連鎖の関数」に広げる。** サイトごとに、それを作った関数と、作ったときの実体化の引数が
   含んでいたコンテナの作り手（`makers`）を覚える。引数のコンテナの makers にこの関数が入っていれば共有サイトにする
   （`makers_of_args`）。往復（f→g→f）がここで止まり、連鎖の長さは関数の数で抑えられる。
   stage-6 は 8 回で収束（サイト 5,887 → 1,880）。検査の判定は変わらなかった（上の「結果は同じか」）。
   **README の Known issues にあった「`Array + Array` を使う相互再帰で止まらない」例もこれで止まる**（0.18 秒、答えは 6）。
5. 細かいこと: 和の正規化で原子の `inspect` を原子オブジェクトごとに 1 回にする（`SORT_KEYS`）。

- 直す前の `--types` 報告（`baseline/`）は、作業用のコードを読み込んだ可能性のある 1 本を捨て、`git archive HEAD` で取り出した素のコードで
  取り直した。
- 読み込み量の指標（P11）と同じく、最初は `ruby -wc` を複数ファイルに渡して最初の 1 本しか検査していなかった。構文エラーを 1 回見逃した。
- 同時に走らせた背景のジョブ（テスト、stage-6 × 2）があるときは、同じコードで 2.5 倍遅く出た（user 時間も）。表の数字は全部止めてから
  1 本ずつ測り直したもの。

## 2 回目（同日、commit 7158823 の後）

### 結果（`--strict=2 -c`、同じマシン状態で交互に測った A/B。別セッションのビルドが 1 コア使っていて、絶対値は 1 回目の表より 1 割ほど遅い）

| プログラム | 行数 | 7158823 | 2 回目 | 倍率 |
|---|---|---|---|---|
| sake-1 stage-4 | 2,960 | 2.33 s | 1.95 s | 1.2 |
| sake-1 stage-6 | 4,433 | 7.9 s / 85 MB | 5.75 s / 134 MB | 1.4 |
| sake-2 stage-6 | 4,409 | 8.0 s（1 回目の表では 6.8 s） | 4.6 s / 130 MB | 1.7 |

stage-2・3・4・sake-1 stage-6 の `--types` 報告は `after/` とバイト単位で同一。sake-2 stage-6 は Struct 1 つ（Snapshot）のフィールド一覧 3 行の
位置が変わるだけで、検査の集合・件数は同一。テスト 201 件は通る。最初から通算すると stage-6 は 190 秒 → 5.7 秒（33 倍）。

### 直したこと

1. **Struct 型ごとの部分歩きを memo する**（`struct_groups`）。フィールドから直接届く型のグループと、その歩きの deps と、途中で会った Struct 型を
   Struct 型ごとに覚える。会った Struct 型は memo を使うときに（それぞれの memo を通して）歩く。1 回の歩きで各 Struct 型は 1 度だけ。
   stage-6 で歩いた型の数は 896k → 59k。グループの出る順は「Struct ごと」になるが、同じ Struct の集合を `uniq` してから使うので、
   呼ぶ `<=>` / `==` の実体化は同じ。
2. **検査のキーと経路を同一性で引く**。(場所, 操作, 引数) ごとにキーのオブジェクトを 1 つ作り、`@checks` と `@check_ctx` は同一性キーにした。
   同じ場所にある別ノード（paste の複製）は同じキーを共有する（最初これを忘れて、検査が 2 つに割れた）。呼び出し経路は `@callers` の配列を
   毎回ハッシュする代わりに、経路ごとに 1 つの `Path` オブジェクト（親と呼び出し場所の木）にした。`Path` は Struct でなく普通のクラス
   （Struct だと `hash` が連鎖全体を辿る。プロファイルで `Struct#hash` が出て気づいた）。
3. **2 つの素な型の和はマージ**。Tuple も Symbol リテラルも含まない正規形 2 つの和は、整列済みの 2 列のマージで作る（`merge2`）。
   原子名の整列キーもキャッシュ。
4. **変わっていない実体化は評価し直さない**（`Inst`、`valid?`、`replay`）。これが 2 回目の主役。
   - 可変な状態を「セル」にした: 配列・Hash・Set のサイト、Struct のフィールド（とフィールド表全体）、`Kernel.once` の表、実体化のキー
     （戻り値と例外）。読み取りはサイトの getter / `read(cell)` で、評価中の実体化の読み取り集合に「初めて読んだときの GEN」を記録する。
     変更は `GEN` を進めて `CHANGED_AT[cell]` に記録する。
   - 実体化（関数 × 引数の型）ごとに、前回の評価で読んだセル、した副作用（検査・組み込みの結果・instantiated の印）、呼んだ実体化（キャッシュで
     済んだ呼び出しも含む）を残す。次の回に呼ばれたら、読んだセルが「読んだ後に変わっていない」かつ呼んだ実体化も全部そうなら、
     評価せず副作用を再生して `@returns` を返す。子の再生は、まだこの回で済んでいないものだけ。循環は検査中を「有効」と見なす（全員が自分の
     読み取りを確認するので健全）。
   - stage-6 の回ごと: 1 回目 0.26 s（831 実体化）、2〜4 回目 1.0〜1.6 s（新しい引数の型の実体化が 1,591 / 1,457 / 599 個）、5〜6 回目
     0.5〜0.8 s（ハブになるセル: `SortItem.keys` フィールド、`Array.map` / `Array.drop` のサイト、が毎回広がる）、7〜8 回目 0.09 s
     （49 実体化だけ評価、1,491 再生）。固定点の確認の回がほぼ無料になった。
   - IDE の `Recorder`（全ノードの評価を記録する）は `incremental?` を false にして、この仕組みを使わない。

### 間違えたこと（記録）

- 子の実体化を「新しく評価したとき」だけ記録していたら、キャッシュで済んだ呼び出しの先の検査が消えた（最初に評価した親が次の回に
  呼ばれない引数の型になると、誰も再生しない）。キャッシュの呼び出しも子として記録する。
- 子を再生するとき、子の例外を今のフレームに合流させていたら、親の `rescue` で捕まるはずの例外が未処理として 86 件増えた。
  親の `@raises` には抜けた例外だけが入っているので、子の再生は捨てるフレームの上で行う。
- `ruby -wc` に複数ファイルを渡すと最初の 1 本しか見ない（前回と同じ）。1 本ずつ渡す。
- 1 回目の pass 単位の無効化（「その回に変わったセルを読んでいたら無効」）は、評価の前に変わったものも数えて無駄が多かった。
  読んだときの GEN と変わったときの GEN を比べる形にした。

### Steep との比較（参考）

Sake 自体の Ruby 実装（`lib/` 7,458 行）に `rbs prototype rb` で署名を作り（672 箇所が `untyped`）、空いたマシンで `steep check --jobs=1`
を 2 回: 6.77 s、6.50 s。同じころの Sake stage-6（4,433 行）は 7.5 s（1 回目の表）、2 回目のあとで 5.7 s。行数あたりでは同じ桁。
署名が薄いぶん Steep の仕事は実際のプロジェクトより軽いので、目安以上の意味はない。

**撤回**: 上は別のプログラム同士の比較で、「同じ桁」以上を言えない。同じ SQL エンジンを Steep 向けに書いた run
（`2026-10-05-ai-writability/runs/p10-steep-{1,2}/stage-6`、署名は手書きで `untyped` なし）があったので、そちらで測り直した。
Steepfile はハーネス（`large/sql/run_tests.rb`）と同じ（`Steep::Diagnostic::Ruby.strict`）。

### YJIT

Ruby 4.0.2 の YJIT（ZJIT はこの Ruby に入っていない）。

**最初の測定は無効だった。** `ruby --yjit bin/sake ...` で測ったら差が出なかったが、`bin/sake` はスタックサイズの環境変数を付けて
自分を `exec` し直すので、コマンド行の `--yjit` は再実行側に渡っていなかった（`RUBYOPT=--yjit-stats` で統計が一切出ないことから気づいた）。
環境変数 `RUBY_YJIT_ENABLE=1` なら子に継承される。以下はそれで測った。

2026-10-09 05:08〜05:09 JST（初版の「20:08 JST」は UTC の写し間違い）、load 1.8〜2.0（それより前は別セッションの gcc で load 15〜30、待った）、交互に 5 回ずつ、stage-6:

| プログラム | YJIT なし | YJIT あり | 倍率 | RSS |
|---|---|---|---|---|
| sake-1 | 5.57 / 5.72 / 5.78 / 5.75 / 5.65 s | 4.51 / 4.53 / 4.49 / 4.51 / 4.48 s | 1.26 | 134 → 145 MB |
| sake-2 | 4.55 / 4.58 / 4.57 / 4.45 / 4.48 s | 3.67 / 3.68 / 3.64 / 3.59 / 3.57 s | 1.25 | 129 → 143 MB |

`--yjit-stats`（sake-1 stage-6）: iseq 582 本・ブロック 21,638 個をコンパイル、コンパイル時間 0.64 s（全体の 10%）、無効化 210 回、
side exit 2,101 回（ほぼ `cfunc_bad_splat_vargs`）、JIT 区間の平均 71.7 命令。exit がほとんど無いので Ruby 側のコードは JIT に乗っている。
伸びが 1.25 倍に留まるのは、時間の大半が Hash（同一性キー）の検索、Array の C 実装、GC だから。

`bin/sake` の再実行で `RUBY_YJIT_ENABLE=1` を付けるようにした（`RUBY_YJIT_ENABLE=0` で止められる）。5 本の `--types` 報告は
YJIT なしと同じ（sake-2 stage-6 の 3 行の順序の違いは前からあるもの）、テスト 201 件通過。

**計測の注意**: 負荷の高いときはユーザー CPU 時間も伸びる（sake-1 で 5.5 s → 11〜17 s）。SMT の相手や周波数の影響で、
CPU 時間を使っても負荷の影響は避けられない。空くのを待つしかない。
