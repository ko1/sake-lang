# AI による書きやすさの評価（設計）

状態: 設計のみ。まだ何も投入していない（2026-10-05）。

## 1. 何を測るか

「AI が Sake を書きやすいか」を、Ruby を基準にした相対値で、次の 4 つの問いに分ける。

| 問い | 主指標 |
|---|---|
| Q1 書けるか | 正答率（隠しテストに通る割合） |
| Q2 どれだけかかるか | 正答までのトークン数（入力・出力別）、実行回数、壁時計時間 |
| Q3 どこで間違い、誰が捕まえるか | 誤りの段階別分類、静的検出率 |
| Q4 道具が効くか | エラーメッセージ・ヒントごとの「次の試行で直った率」、ヒントを消したときの差 |

これまでの指標との関係: 2026-10-05-review の「AI トークン 1.07–1.12×」は、正しいプログラムを**書き写す**量の比にすぎない。ここでは、仕様から正しいプログラムに**たどり着く**までを測る。

## 2. 課題セット（4 層）

| 層 | 内容 | 数 | 採点 | 狙い |
|---|---|---|---|---|
| A 関数 | MultiPL-E の Ruby 版 HumanEval/MBPP を Sake 用に変換（シグネチャ・docstring・テスト呼び出し） | 約 560 | 呼び出しごとの `p(f(args))` 出力を、Ruby の参照解の出力と比較 | 外部の基準と比べられる。単純な関数での型の書きやすさ |
| B プログラム | 新規に書き下ろす。20 ドメイン × 3 題（クラス、nil、Hash、例外、パーサ、状態機械など）。仕様は I/O を厳密に書き、公開例 2 つと隠しテスト 10 個以上（stdin → stdout）を付ける | 60 | 隠しテストの完全一致 | Sake らしさ（型を操作に書く、フィールド、nil 検査）が効く規模 |
| C 改変 | 既存の sakelib（39 本）への機能追加・バグ修正 | 20 | 追加テストと既存テストの両方が Ruby と一致 | 読む書きやすさ。他人のコードの型に合わせられるか |
| D 翻訳 | corpus-v3 の `.rb` を渡して Sake に訳させる | 500（パイロットは 50） | `.out` と完全一致 | すぐ使える。Ruby からの移行コスト（ただし難度は最も低い） |

- **B を本命にする**: A は Ruby 側が事前学習で答えを覚えている恐れがある。D は Ruby の解が渡されるので易しすぎる。
- B は公開しない（held-out）。A は汚染の参考値として扱う。

## 3. 条件

| 因子 | 水準 | 備考 |
|---|---|---|
| 言語 | Sake / Ruby | 同じ課題、同じ道具、同じプロンプト雛形（言語名と資料だけ差し替え） |
| モード | 一発（道具なし） / エージェント（実行してよい、最大 8 回） | 一発は「知識だけで書けるか」、エージェントは「エラーから直せるか」 |
| Sake の strict | 0 / 1 / 2 | エージェントモードで、実行前の検査の強さが試行回数と誤答をどう動かすか |
| 資料 | guide のみ / spec+builtins / guide+few-shot 3 例 | 資料のトークンは固定費として別に数える |
| モデル | Sonnet 5.5（主） / Opus 5.5・Haiku 4.5（部分集合） | 小さいモデルほど新言語に弱いはず |
| 反復 | 1 セル 5 回 | 平均とブートストラップ 95% 区間で報告する。単発の結果は主張しない |

全組み合わせは大きすぎる。主グリッドは「B × {Sake, Ruby} × 2 モード × Sonnet × 5 回」とし、残りは第 7 節のアブレーションで足す。

## 4. 記録と派生指標

1 試行ごとに JSONL 1 行で記録する。項目は、課題、条件、反復番号、試行番号、コード、検査の診断（項目・行・ヒント）、実行結果、隠しテストの結果、トークン（入力・出力・キャッシュ）、所要時間。

派生指標:
- **正答率**: 一発の pass@1 と、エージェントの予算内解決率。
- **正答までのコスト**: トークン数の中央値と、実行回数。
- **誤りの段階**: 失敗した試行を最初に止めた段階で分類する。
  - 段階: 構文 / 名前・引数（レベル 0）/ type（1）/ nil・mixed（2）/ 実行時例外 / 出力違い / タイムアウト
- **静的検出率**: 誤った試行のうち、実行前の検査で止まった割合。Sake の主張そのものなので、検査レベル別に出す。
  - 対照: 同じ誤答を `--strict=0` で走らせて、実行時に初めて出るか確認する。
- **見逃し**: 検査を通って出力違いになった割合（型では捕まらない誤り）。
- **誤報の負担**: 検査に止められたが、`--strict=0` なら隠しテストに通っていた試行。
  - 書き手が無駄に回った回数として数える。
  - 2026-10-05-review の「レベル 1 誤報 38 本」を、書き手側から見た数字になる。
- **メッセージ修復率**: 診断（項目とヒントの種類）ごとに、次の試行でその箇所の診断が消えた割合。
  - 消え方は「直した」と「迂回した（コードを消したなど）」に分ける。後者は差分で判定する。
- **Ruby 癖率**: 試行あたりの「値へのメソッド呼び出し」「Proc の保持」など、Ruby の書き方を持ち込んだことを示す resolver エラーの数。試行番号が進むと減るか（学習曲線）も見る。

## 5. 統制と妥当性（測定を疑うための仕掛け）

- **正の対照**: 各課題の参照解（Sake と Ruby）が採点系で満点になること。
- **負の対照**: 参照解の変異版（境界値を 1 ずらす、nil 検査を消すなど）が落ちること。
- これらを流してから本番を投入する。
- **難度の較正**: Ruby 条件の正答率が極端（ほぼ 0 またはほぼ 100%）な課題は分析から外すか、別に報告する。
- **時間制限**: Sake インタプリタは遅いので、時間制限は言語別に「参照解の実行時間 × 10、最低 5 秒」とする。タイムアウトは独立の段階として数える。
- **資料の非対称**: Sake は資料が要り、Ruby は要らない。資料のトークンは固定費として分けて報告する。比較の主軸は「固定費を除いた正答までのコスト」と「正答率」。
- **汚染**: A の Ruby 側は記憶の可能性がある。B は新規・非公開。結論は B で出す。
- **処理系の固定**: Sake の commit を固定する。途中で lib を変えた場合はセルを分ける。
- **モデルの固定**: モデル ID と温度（既定値）を記録する。
- **共有環境**: 実行は sp3/sp4 ではなくローカルの隔離コンテナで行う（性能計測ではないため）。並列数の上限と多重起動の拒否は runner 側で持つ。

## 6. 実行系

- runner（Ruby）が API を直接呼ぶ。エージェントモードの道具は「ファイルを書く」と「`bin/sake --strict=N` / `ruby` で実行して出力を見る」の 2 つだけ。
  - Claude Code のサブエージェントでも回せるが、温度・道具・トークン計上の統制が弱い。本番は API にする。
- 採点は隠しテストを runner 側で流す。モデルには見せない。
- 出力先: `results-<日付>-<条件>/attempts.jsonl` と `summary.md`。失敗例のギャラリーは artifact にする。

## 7. 段階と費用の見積もり

| 段階 | 内容 | 規模 |
|---|---|---|
| P0 採点系 | 正・負の対照、B の 10 題 | モデル呼び出しなし |
| P1 パイロット | D 50 本 + B 10 題 × {Sake, Ruby} × 2 モード × Sonnet × 3 回 | 約 700 試行 |
| P2 本番 | B 60 題の主グリッド | 1,200 試行 |
| P3 アブレーション | (a) ヒントを消す（CLI の hint 行を落とす）→ ヒントの因果効果。(b) メッセージを「行番号だけ」にする。(c) strict 0/1/2。(d) 資料 3 水準。(e) Opus/Haiku を B 20 題で | 各 200〜600 試行 |
| P4 外部比較 | A（MultiPL-E 変換） | 560 題 × 2 言語 × 1 回 |

トークンは、エージェント 1 試行あたり 2〜5 万（資料込み、キャッシュが効く）と見て、P1 で実測してから P2 以降を決める。

## 8. 決めてほしいこと

1. API を直接使ってよいか（キーと予算）。だめなら Claude Code のサブエージェントで P1 まで進め、統制の弱さを明記する。
2. 外部データの取得（A 層の MultiPL-E。HumanEval は MIT、MBPP は CC-BY）。取得は外部へのアクセスになる。
3. B 層 60 題を誰が書くか。AI に書かせる場合、仕様と隠しテストを書く者と、解く者を分ける（同じ会話にしない）。参照解は Sake と Ruby の両方で採点系を通す。

# P2: 反復・題数・チートシート（2026-10-06 実施）

## 方法

- 処理系は 9e12065（P1 で見つけた 3 点を修正済み）。資料（docs/）は P1 と同じ版。チートシートは `cheatsheet.md`（規則約 3.2k + 操作一覧約 5k トークン。別エージェントが資料から作り、例はすべて `--strict=2` で実行して確認）。
- 反復: P1 と同じ 20 題 × {Sake, Ruby} × {一発, 実行あり} を 2 回（r2, r3）。1 体 5 題で 32 体。
- 題数: 実行ありで 1 体に 10 題（2 体）と 20 題（1 体）。Sake と Ruby の両方。
- チートシート: Sake・実行ありで、資料の代わりに `cheatsheet.md` だけを渡した（1 体 5 題 × 4 体）。
- プロンプトは `harness/make_prompt.sh` で生成（`prompts/p2-*`）。採点は `grade.rb`、使用量は `harness/usage.rb`（各エージェントの記録から）。集計は `harness/summarize_p2.rb` → `runs/summary-p2.txt`。

## 結果

**正答率（r2 + r3）**: 言語差もモードの差も見えない。

| 条件 | r2 | r3 | 平均 |
|---|---|---|---|
| Sake・実行あり | 14 | 16 | 15.0/20 |
| Sake・一発 | 15 | 14 | 14.5/20 |
| Ruby・実行あり | 16 | 13 | 14.5/20 |
| Ruby・一発 | 13 | 17 | 15.0/20 |

- 反復のばらつき（同じ条件で ±2）が条件間の差より大きい。題ごとに見ると、b07・b13・b16（と b10 の一部）は言語によらずほぼ全滅していて、仕様の落とし穴が効いている（`runs/summary-p2.txt` の題別表）。
- 1 体あたりの題数を変えても同じだった（10 題: Sake 17/20・Ruby 16/20、20 題: Sake 17・Ruby 16）。チートシートは 13/20 で、この差は反復のばらつきの範囲。

**コスト: 題あたりの費用は、題数を増やしても薄まらない**

| 条件（実行あり） | 1 体の題数 | 最終文脈長 | 出力/題 | 時間/題 |
|---|---|---|---|---|
| Ruby | 5 / 10 / 20 | 57k / 75k / 118k | 2.7k / 2.5k / 2.6k | 18 / 17 / 17 秒 |
| Sake（全資料） | 5 / 10 / 20 | 102k / 134k / 206k | 4.1k / 4.0k / 4.0k | 29 / 28 / 28 秒 |
| Sake（チートシート） | 5 | 85k | 4.0k | 29 秒 |

- **最終文脈長を題数に対して直線で当てはめた結果**（1 体の題数 5/10/20 の 3 点）:
  - Ruby は切片約 37k、傾き約 4.1k/題。
  - Sake は切片約 68k、傾き約 6.9k/題。
  - 切片の差（約 31k）が資料の固定費、傾きの比（約 1.7 倍）が題ごとの上乗せ。
- **出力トークンと時間は題あたりでほぼ一定**: Sake は Ruby の約 1.5〜1.6 倍で、1 体の題数が 5 でも 20 でも変わらない。固定費が薄まって追いつく、ということは起きない。
- **出力の上乗せのうち、コードそのものはわずか**: 解答コードは 1 題 Sake 約 1.2k・Ruby 約 0.95k トークン（P1）。残りは思考で、Sake は Ruby の約 1.65 倍。

## 解釈

- 正しさは Ruby と同じところまで届く（この 20 題・Sonnet 5.5 では、差はばらつきに埋もれる）。
- 代わりに、題ごとに約 1.5 倍の出力（≒思考）と時間を払う。
- これは資料の固定費ではない。題数を増やしても、資料をチートシートにしても減らなかった。モデルが Sake のコードを組み立てるときの上乗せと見るのが妥当（どの型の操作か、それがあるか、書き方が許されるか）。ただし「何を考えているか」は直接観測していない。
- 減らせるとすれば、モデルが迷う点を言語か資料の側で減らすこと。次の観測点は、Sake の思考の中身を分類すること（どの操作名を探したか、何を確かめたか）。
