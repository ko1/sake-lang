`bin/sake --strict=2 -c` が 4,400 行のプログラムで 190 秒かかっていた（P10 の SQL エンジン。
`experiments/2026-10-05-ai-writability/README.md` の「検査が遅い件」）。Ruby のまま直した。
対象 commit: この README と同じ commit の `lib/sake/typer*.rb`。

## 環境

### 結果は同じか

- `--types` の報告（全検査の判定と、全サイトの要素型）を直す前（`baseline/`、HEAD の素のコードで取った）と後（`after/`）で比べた。
- stage-2・3・4: **バイト単位で同一**。
- stage-6（2 本）: 検査の集合（判定・行・操作・引数）は**同一**（sake-1: 15 行、sake-2: 390 行。proven/partial/unknown の数も同じ）。
  報告の文面は変わる: 配列サイトの番号（`Array@L30#7` の `#7`）と、サイトの一覧。理由は下の「収束しなかった」。
- `test/` の 201 件は全部通る。

## 何が遅かったか

stackprof（cpu）で見た。

1. **型（ネストした配列）を値でハッシュしていた。** 型の和 `Typer.union` の memo、関数の実体化の表 `@done` / `@returns` のキー `[fn, args]`
   （`fn` は Struct で、`Struct#hash` は本体の AST まで辿る）、`compared_groups` の `seen`。`Array#hash` だけで 19%。
2. **`struct_hooks` を組み込み呼び出しごとに全部やり直していた。** 引数の型から到達できる Struct 型を、フィールド・要素・Tuple の位置を辿って集める
   歩きで、呼び出しのたびに同じ歩きを繰り返していた（累積 46〜58%）。
3. **固定点が収束しなかった（stage-6 だけ）。** 上限の 30 回まで回り、1 回 3.3 秒。毎回、配列サイトが 122 個、実体化が 219 個増えていた。
   原因: コンテナのサイトは「作る場所 × その関数の実体化（引数の型）」ごとに作る。引数が、この関数自身が作ったコンテナを含むときは共有する
   （再帰の歯止め）が、f が作った配列を g に渡し、g が作った配列を f に渡す、という往復は止まらず、毎回新しいサイトを作っていた。
   stage-6 では 2 つの場所がそれぞれ 882 個のサイトを持っていた（`compound.sake` の `unique(rows)` のあたり。
   `Query.compute` → 複合 SELECT → `unique` → `Query.compute` …）。

## 直したこと（`lib/sake/typer.rb`、`typer_eval.rb`、`typer_ext.rb`）

1. **型をインターンする。** 正規形（整列・frozen）1 つにつきオブジェクト 1 つ（`Typer.intern`、`CANON`）。等しい型は同一オブジェクトになり、
   同一性で比べられる。和の memo（2 引数は `UNION2`、それ以上は id の列）、実体化の表（`inst_key`: 関数と型の id）、
   `compared_groups` の `seen`、`@instantiated` などを同一性キーにした。単一原子の型は `one(a)`、原子の集まりは `of_atoms(atoms)`、
   Tuple は要素の id で memo、サイトの型は `site_type(kind, id)` で 1 つにする。
2. **`struct_hooks` を memo する。** キーは引数の型の id。歩きが読んだコンテナ（サイトの要素型・フィールドの表）と、そのとき持っていた型を
   `deps` として覚え、どれも同一（identity）なら再利用する。書き込みの世代 `GEN`（変化した書き込みだけ数える）が memo のときと同じなら
   deps も見ない。型ごとに固定な部分（Struct 原子、Tuple・Record の各位置の型）は `shape_of` で型ごとに 1 回だけ計算する。
3. **`add_check` の判定の合成を数で持つ。** 経路ごとの判定を毎回 reduce していたのを、判定ごとの件数から最悪を取る形にした。
   検査のキー（行・列・操作・引数・ファイル）はノードごとに 1 回作る。
4. **再帰の歯止めを「作った関数」から「文脈の連鎖の関数」に広げる。** サイトごとに、それを作った関数と、作ったときの実体化の引数が
   含んでいたコンテナの作り手（`makers`）を覚える。引数のコンテナの makers にこの関数が入っていれば共有サイトにする
   （`makers_of_args`）。往復（f→g→f）がここで止まり、連鎖の長さは関数の数で抑えられる。
   stage-6 は 8 回で収束（サイト 5,887 → 1,880）。検査の判定は変わらなかった（上の「結果は同じか」）。
   **README の Known issues にあった「`Array + Array` を使う相互再帰で止まらない」例もこれで止まる**（0.18 秒、答えは 6）。
5. 細かいこと: 和の正規化で原子の `inspect` を原子オブジェクトごとに 1 回にする（`SORT_KEYS`）。

## 計測の記録

- 直す前の `--types` 報告（`baseline/`）は、作業用のコードを読み込んだ可能性のある 1 本を捨て、`git archive HEAD` で取り出した素のコードで
  取り直した。
- 読み込み量の指標（P11）と同じく、最初は `ruby -wc` を複数ファイルに渡して最初の 1 本しか検査していなかった。構文エラーを 1 回見逃した。
- 同時に走らせた背景のジョブ（テスト、stage-6 × 2）があるときは、同じコードで 2.5 倍遅く出た（user 時間も）。表の数字は全部止めてから
  1 本ずつ測り直したもの。

## 残り

- stage-6 のプロファイル（直した後）: `compared_groups` の歩き 27%、`union` 18%、`deps_hold?` 9%、GC 8%。
  memo のミス（引数の型が新しい、または deps が変わった）ごとに Struct のフィールドを全部歩くのが残りの主因。Struct 型ごとの部分歩きを
  memo すれば減るが、グループの順序が変わって報告の文面（failing の並び）が変わりうるので、今回は手を付けていない。
- `--types` の報告の文字列作り（stage-6 で 15 秒余り）は、検査そのものには関係ないので放置。
