# rails_actioncontroller_view: ActionController on ActionView (third wave, part 11, 2026-10-20)

The controller side of ActionView (ActionView::ViewPaths, ActionView::Rendering, ActionView::Layouts) wired into
ActionController::Base, so actions render templates with layouts and partials as Rails does: implicit render of
the action's template, `render :edit, status: :unprocessable_entity`, `render "posts/new"`, `render template:`,
`render partial:`, `layout "admin", except: [...]`, `layout :method`, `layout false`, `render layout: false/true/"x"`,
`render_to_string`, `respond_to` choosing between an html and a json template; the view gets the controller's
fields as assigns, the RouteSet's url helpers, the controller's url_options (`_recall`), `params`, `flash`/`notice`,
`csrf_meta_tags` and form tokens, and the app's `helper_method`s. Also: encrypted cookies (and so Rails' default
CookieStore) on ActiveSupport::MessageEncryptor, ActionController::TestCase, and the first wave's workarounds the
built-ins now cover (Kernel.class_name, Regexp Hash keys). Builds on `rails_actioncontroller.md`,
`rails_actionview.md`, `rails_actionpack_dispatch.md`.

require "rails/actionpack/action_controller/base"
require "rails/actionview/action_view"

## The shape

### view_context: the app's one view class, the controller's fields as assigns

Rails builds a view class per controller (`view_context_class`: ActionView::Base with the routes' url_helpers and
the controller's `_helpers`) and calls `view_context_class.new(lookup_context, view_assigns, self)`, copying the
controller's instance variables into the view. Here the app has one view class (generated by actionview's
`view_class` generator, with every template compiled into it: one per controller would compile each template once
per controller), and the controller generator writes per controller:

```ruby
def PostsController.view_context(c)
  AppView.new(controller: c, lookup_context: lookup_context(c), request: request(c), routes: _routes(c), post: @post, posts: @posts)
end
def PostsController._view_paths(c) = AppView.compiled_view_paths   # the paths the templates were compiled from
```

The fields come from the controller's `attr_reader`/`attr_accessor` lines (and its parents'); a field the view class
does not declare (`assigns=`) is a check error at the `generate` line. Without `view=`, `view_context` is nil and
only `:plain`/`:html`/`:body` render (controller_base and the other controller tests).

### The view asks its controller: HelperMethods and module dispatch

`ActionView::Base` got Rails' `controller` field. Its type is the union of the app's controller classes (every
generated view_context stores itself there). `ActionController::Helpers::HelperMethods` (included by the view class)
is Rails' `_helpers` module plus ControllerHelper's `delegate ... to: :controller`; each function calls a module
that every controller includes, which dispatches on the controller's class:

```ruby
# Ruby (ActionView::Helpers::ControllerHelper, RequestForgeryProtection)   # Sake (action_controller/metal/helpers.sake)
delegate :params, :flash, :action_name, ..., to: :controller               def flash(v) = ActionController::Flash.flash(view_controller(v))
helper_method :form_authenticity_token, :protect_against_forgery?          def form_authenticity_token(v, form_options: nil) =
                                                                             ActionController::RequestForgeryProtection.form_authenticity_token(view_controller(v), form_options: form_options)
(RoutingUrlFor#url_options: controller.url_options)                       def url_options(v) = ActionController::UrlFor.url_options(view_controller(v))
```

Metal's and AbstractController::Base's own functions (`action_name`, `session`, `headers`, ...) are not in a module,
so `ActionController::Helpers` declares them as required functions, which the pasted class functions fulfil, and
`ActionController::Helpers.action_name(controller)` dispatches. An app's `helper_method :greeting` is generated:

```ruby
def AppView.greeting(v, word, **kw)          # `def greeting(c, word, name: current_user(c))`: a default may name the
  case AppView.controller(v)                 # controller's functions, so optional parameters go through *args/**kw
  in ::ApplicationController => c then ::ApplicationController.greeting(c, word, **kw)
  in ::PostsController => c then ::PostsController.greeting(c, word, **kw)
  ...
  else raise NoMethodError, "undefined method 'greeting' for an instance of AppView"
  end
end
```

### render_to_body through the layers (no super)

Rails: `Renderers#render_to_body` → `ActionController::Rendering#render_to_body` (`super || _render_in_priorities ||
" "`) → `ActionView::Rendering#render_to_body` (`_process_options`, `_process_render_template_options` (Layouts'
override adds the layout), `_render_template`). The Sake names: ActionController::Rendering calls
`view_render_to_body`, which Base defines as `view_rendering_render_to_body` (ActionView::Rendering's); Layouts'
`_process_render_template_options` calls `view_rendering_process_render_template_options` as its super.
ActionView::Rendering also overrides AbstractController's `_normalize_args` (`render :edit` → `action: "edit"`,
`render "a/b"` → `template:`), `_process_format` (respond_to's format into the lookup context) and `rendered_format`.
ActionView::ViewPaths overrides `formats`/`set_formats` (Rails delegates them to the lookup context), so
`rendering_process_action` sets the request's formats on the lookup context, as Rails.

### Layouts: Rails' Proc is a block, `_write_layout_method` is generated

`_layout_for_option(:default)` is `Proc.new { |lookup_context, formats, keys| _default_layout(...) }`, called by the
TemplateRenderer after it found the template (with the template's format first). Here the option is the Symbol
`:default` (`:require` for `layout: true`), and the renderer calls the caller's block, which ActionView::Rendering
gives: `Renderer.render_to_object(renderer, context, options) { |l, formats, keys, required| _default_layout(c, l, formats, keys, required) }`.

`layout` lines are class-body declarations; `action_view/generate/layouts.sake` writes Rails' generated `_layout` for
each level of the lineage as a function of the class (`__layout_0` for ApplicationController's level, ...), each
level's `super` being the one below:

```ruby
# PagesController: layout "admin", except: [:home]; AdminPagesController < PagesController: layout :choose_layout
def AdminPagesController.__layout_1(c, lookup_context, formats, keys)     # PagesController's level
  if !Array.include?(String[], action_name(c))                           # the conditions are AdminPagesController's ({})
    "admin"
  else
    ActionView::Layouts.find_implied(lookup_context, "pages", String["layouts"], keys, formats) || __layout_0(c, lookup_context, formats, keys)
  end
end
def AdminPagesController.__layout_2(c, lookup_context, formats, keys)
  layout = choose_layout(c)
  return ActionView::Layouts.find_implied(lookup_context, "admin_pages", String["layouts"], keys, formats) || __layout_1(c, lookup_context, formats, keys) if layout == nil
  ...
```

### Templates the controller renders: compiled before the program

`render c, partial: "fragment"` in a controller reaches a partial that no template renders; Rails compiles it on the
request. The view class generator now takes `controllers=FILE...` and compiles the partials of the controllers'
literal `render ..., partial: "x"` calls (without locals) into `_compiled`.

### Encrypted cookies

`cookies_encrypted.sake` (written against Rails' names by the first wave, required by nothing) now runs on part 10's
`ActiveSupport::MessageEncryptor` (OpenSSL::Cipher). As the signed jar, the jar serializes the value itself and
wraps it in Messages::Metadata's pre-7.1 envelope (Rails' jars use a NullSerializer); the encryptor only encrypts and
signs (`MessageEncryptor.encrypt`/`sign`, `verify`/`decrypt`). The envelope code is shared with the signed jar now
(`SerializedCookieJars#wrap_metadata`/`unwrap_metadata`). Rails' legacy rotation is ported (gcm reads cbc cookies and
rewrites them; cbc prepares for gcm), not `cookies_rotations`. `signed_or_encrypted` moved here, so CookieStore's
session is encrypted when secret_key_base is set (controller_view runs that way, as a Rails app does).

### ActionController::TestCase

A value made in each `Minitest.test` block, as the first wave's IntegrationTest: `TC.make(t, "notes",
ActionController::ControllerSet.new, routes)`, then `TC.get(tc, :show, params: Hash.of(id: 5), format: :json)`.
The request is built as Rails' TestRequest#assign_parameters does (routes' `generate_extras`: path parameters, the
rest in the query or the url-encoded/JSON body; test.host, "Rails Testing"), a TestSession Hash, the flash and the
cookies stay between requests, and the controller is reached through the generated ControllerSet (a new controller
per request; Rails recycles one). The ResponseAssertions of the first wave work on it.

### First-wave workarounds replaced

- The class-name parsers: ExceptionWrapper's `Kernel.inspect(e)` regexp, StrongParameters' and PolymorphicRoutes'
  `case`-built names ("Object") → `Kernel.class_name`; Instrumentation and Rescue no longer use ActiveSupport's
  Notifications.class_name (the tests neither). ParamBuilder's `class_name` stays: it names a params Hash
  "ActiveSupport::HashWithIndifferentAccess", which is what Rails' message says.
- The GTG grouped transitions by a regexp's spelling and kept regexp states as [regexp, state] pairs → grouped by the
  symbol and a Hash keyed by Regexp, as Rails' builder and TransitionTable.
- Encrypted cookies and the encrypted CookieStore, above.

## Left out, and why

- ActionView's LogSubscriber ("Rendered posts/index.html.erb within layouts/application"), template instrumentation:
  Rails' start/finish subscribers; time.
- `render partial:` / `render template:` with `locals:` from a controller: ActionView takes no run-time locals Hash
  (each partial is compiled for the keyword locals its call sites pass).
- Proc layouts (`layout -> { }`, a generate-time error), `layout` with a Class, `helper` modules and `helpers` as a
  memoized proxy (a new view each call), Streaming, `ActionController::Renderer` (`ApplicationController.render`
  outside a request), template digests/ETags (EtagWithTemplateDigest), variants beyond the lookup.
- TestCase: assigns/assert_template (rails-controller-testing), multipart uploads, xml params, Live, the executor;
  the request's env does not carry over between requests (Rails keeps PATH_INFO etc. in @request.env).
- `cookies_rotations` (key rotation lists) for encrypted cookies.

## Bugs (repros in experiments/2026-10-20-rails-scale/bugs/)

- `actionpack_controller_mixin_call_on_other_includer.sake`: `A.get(x)` for a mixin's function, with x possibly a B
  (another includer), passes the checker and runs A's copy on the B (prints "get from A" for a B). In the port,
  CookieStore's `Cookies::SignedKeyRotatingCookieJar.[](jar, key)` with jar = `signed_or_encrypted(...)` checked
  clean and failed at run time ("TypeError: argument 1 must be ActionDispatch::Cookies::SignedKeyRotatingCookieJar,
  got ...EncryptedKeyRotatingCookieJar") once the session was encrypted; it now calls `Cookies::AbstractCookieJar.[]`.
- Not filed: `Session.new(nil, req, delegate: data, loaded: true, exists: true)` (keywords naming private fields)
  is silently undone by Session's `initialize`, which sets `@delegate = Hash.new` and `@loaded = false`
  unconditionally; Ruby has no such constructor, so it is the port's, not the language's. The TestSession writes
  the data after `new`. RequestForgeryProtection's NullSession uses the same keywords (harmless: its data is empty).

## Friction (what I wrote first → the message → what I wrote instead)

1. Template.html escaping at construction, as Rails' Template::HTML → `render html: "<b>7</b>"` came out
   `&amp;lt;b&amp;gt;`: ActionController::Rendering escaped with `ERB::Util.html_escape`, which in Sake is
   sakelib/erb's (a String), while Rails' ActiveSupport prepends ERBUtil to ERB::Util (a SafeBuffer). The second wave's
   code had escaped an html_safe input twice too (`render html: x.html_safe`), unseen because no test passed one →
   `ActiveSupport::CoreExt::ERBUtil.html_escape`. No message: found by the side-by-side output.
2. `redirect_to c, post` → at run time `NoMatchingPatternError: no in branch matches Post` in full_url_for, whose
   `case` had no record branch (level 2 does not check a `case` without `else`) → the record/Array/Symbol branches
   Rails has.
3. `render c, partial: "fragment"` → at run time `_controller_views_pages__fragment_html_erb is not a compiled template
   of AppView`: nothing told the view generator the controller renders it → `controllers=` for the view generator.
4. MissingTemplate raised inside a template came out as MissingTemplate; Rails wraps it in Template::Error (the
   port's Template.render re-raised it on purpose) → wrapped, as Rails.
5. `layout :choose_layout` in a subclass of a controller with `layout "admin", except: [:home]`: my levels used each
   level's own conditions; Rails reads `self.class._layout_conditions` at every level, and `layout :x` resets them to
   {} → `/admin/home` rendered the application layout where Rails renders admin. Found only by the side-by-side output.
6. The helper_method generator copied the controller's signature `def greeting(c, word, name: current_user(c))`
   → `syntax error: unexpected 'case'` (my regexp stopped at the first `)`); with the parentheses balanced, the
   default `current_user(c)` would be evaluated in the view, where `c` does not exist → optional parameters are
   forwarded through `*args`/`**kw`.
7. `&.[](0)` in the generator (Ruby habit) → rejected; the session cookie value read through `hs["set-cookie"]` →
   `String.split: argument 1 must be String, but can be Array`: a header may be an Array here → a `case`.

What read well: the controller_view test matched Rails on the second run that type-checked (three differences, items
2-4), and the TestCase on the third. Module dispatch over the union of controller classes made HelperMethods a
plain mixin (a 15-line test showed it works before I wrote it), and the view's url helpers, form_with and
csrf_meta_tags of the second wave worked unchanged with the controller's url_options and tokens. A misspelled
helper in a template is a check error at the .erb line, and a controller field the view class lacks is one at the
controller's class line (`AppView has no field `extra``); Rails finds the first on the request and never the second. 6 controllers with 13 templates check in 5.4 s, less than actionview's own rendering test (9 s).
