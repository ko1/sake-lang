## 結果

### 1. 見直しで何が使われたか

全 500 本の出力は `.out` と一致（v3）。書き換わったのは 465 本。

| 機能 | v2 | v3（使った本数） |
|---|---|---|
| `attr_*` 行 | 204 | 981（414 本） |
| `Struct.new` | 748 | 28 |
| `class E < Exception` | 1 | 243（190 本） |
| `once` | 0 | 156（112 本） |
| `initialize` | 0 | 85（75 本） |
| `&b`（ブロックを渡す） | 0 | 39（15 本） |
| 省略できる引数 | 0 | 1 |
| キーワード引数・`x => T`・`class B < A`・`block_given?`・IO | 0 | 0 |

- 使われたのは「Ruby 版に対応するものがある」機能だけ。コーパスの Ruby 版（1 本 40〜250 行の慣用的なスクリプト）は
  キーワード引数・型の検査・継承・ブロック省略・IO をほとんど使わないので、**このコーパスはそれらの機能を測る材料にならない**。
  それらを使ったのは sakelib の見直し（`initialize` での検査と変換、`x => T`、キーワード引数、`class SHA384 < SHA512`）。
- 最も効いたのはクラスの書き方：Ruby の `class` + `attr_reader` がそのまま書けるようになり、例外クラスは
  Ruby の `initialize(msg, x); super(msg); @x = x` が `attr_reader x` 1 行になった（Ruby より短い）。

### 2. Ruby との比較

| | Sake v2 | Sake v3 | Ruby |
|---|---|---|---|
| 行数（空行・コメント除く） | 50,089（0.944） | 50,221（0.947） | 53,059 |
| トークン数 | 524,282（1.180） | 515,388（1.160） | 444,372 |
| 型名を書いた呼び出し `T.op` / 100 行 | 47.7 | 46.7 | 0 |
| そのための文字（ソースに占める割合） | 9.8% | 9.6% | — |
| ほかに型を書いた所（`T[]`、`in T`、`=> T`）/ 100 行 | 1.7 | 1.6 | 0 |

- **行数は Ruby より 5% 少なく、トークンは 16% 多い**。行は短く書けるが（例外クラス、`attr_*`）、1 行あたりの語が増える。増えた分のほとんどが型名。
- 型名を書いた呼び出し（v3、23,433 個）の内訳：組み込みの型の操作 67.9%（`Array.` 9,951、`String.` 2,190、`Hash.` 1,292 …）、
  **フィールドの読み書き 22.4%**（`T.get_x(v)` 20.9%、`T.set_x(v, w)` 1.5%）、自前の型・モジュールの操作 9.7%。
- 見直した 5 体が「Ruby の人が最初に気づく違い」として**全員**挙げたのは同じ点：`node.left` が `Node.get_left(node)`。
  宣言は Ruby と同じ形になったが、使う側は変わらない。属性を読む連鎖が多い木・リストのプログラムでは本体が 2〜3 倍に伸びる。
- その次に挙がった違い：インスタンスが明示の第 1 引数（`def +(a, b)`、`def peek(ps)`）、`self.make` のようなクラスメソッドと
  インスタンスの関数の見分けがつかない、`Array[...]` / `Hash[...]` / `Set[...]`（`[]` は Tuple、`{}` は Record）、
  `case/when` が無い（範囲・正規表現の `when` は `if` の連鎖）、`&:sym` が無い、列挙子の連鎖（`each_cons(2).map`）が無い。

### 3. 型がどれくらい曖昧なく決まるか

同じ処理系での v2 と v3（「決まった」= どこにも unknown を含まない。mono = 全体で 1 つの型）：

| 単位 | v2 mono | v3 mono | v3 nilable | v3 union | v3 決まった | TypeProf（Ruby 版）決まった |
|---|---|---|---|---|---|---|
| 式（変数の読み） | 80.7% | 80.6% | 13.3% | 5.3% | 99.4% | — |
| 式（呼び出しの結果） | 80.9% | 80.8% | 13.5% | 3.9% | 99.6% | — |
| 関数の引数 | 79.9% | 79.6% | 12.2% | 7.7% | 99.5% | 90.5% |
| 関数の返り値 | 77.2% | 76.8% | 15.2% | 6.9% | 99.0% | 91.5% |
| フィールド | 82.4% | 81.9% | 13.9% | 4.0% | 99.9% | 92.0% |

- **書き直しても型の決まり方はほとんど変わらない**（差は 0.5 ポイント以内）。型を書く場所が無いのだから当然とも言える：
  新しい機能は書き方を Ruby に近づけたが、推論に新しい情報を足したのは `initialize` の変換（`@celsius = Float(@celsius)`）と `x => T` だけで、コーパスではほとんど使われていない。
- 実行時の検査箇所のうち、静的に必ず通ると分かったもの（proven）：v3 で 49,950 / 53,733 = **93.0%**。残りは partial 3,692（型の和の一部だけ通る）、unknown 81、error 10。
- **型の和（union）の中身**（`union-v3.md`）。シグネチャ（引数・返り値・フィールド）の 801 個：
  - 数の混在（`Integer | Float` 108 など）：引数 54、返り値 74、フィールド 28。多くは型の無い関数を整数と小数で呼んだもの。具体化ごとには 1 つの型（推論は呼び出しの型の組ごと）で、和は「その関数がとる型」の正しい答え。
  - 自前の型の和（`Bin | Fn | Num | Var` などの構文木、`Box | Circle | Dot`）：147。代数的データ型として書かれた、意図した和。
  - スカラーの混在（`Integer | String` 49、JSON 風の `Array | Hash | Integer | String | true | false`）：437。解析中の値、設定値、動的なデータ。和が正しいものが多いが、`Integer | String` の一部は「数か、まだ数にしていない文字列か」で、Ruby でもそう動く。
  - 容器の要素の和：60。
- **nil**：シグネチャの 13〜15% が `nil | T`。2026-10-01 の分析どおり、ほとんどは Ruby でも nil になる値（`Array.max`、`Hash[]`、`String.match` の結果、未設定のフィールド）。
- **誤報（すべてのプログラムは正しく動くので、止めた分は全部誤り）**：

  | レベル | v2 | v3 |
  |---|---|---|
  | 1（型） | 52 本 / 162 件 | 53 本 / 164 件 |
  | 2（+nil） | 286 本 / 1,226 件 | 294 本 / 1,267 件 |

  v3 で level 2 に新しく止まった 11 本の原因（`strict-diff.txt`）：
  - 2 つの値の大きい方・小さい方を `Array.max(Array[a, b])` と書いた（Ruby の `[a, b].max` の直訳）。空かもしれない Array の max は `nil | T`：5 本。**2 引数の max/min が無いことが nil の誤報を生む**。
  - `attr_reader rcpts = nil` を `initialize` から呼ぶ関数で埋めた：2 本（関数に渡した時点で、フィールドは何でもあり得るとして扱う。安全側）。
  - 新しい組み込み（位置つき `String.index`、`MatchData.captures`）が `nil | T` を返す：3 本。
  - level 1 の 1 本は `Float.between?(f, lo, hi)` に Integer の上下限を渡した（Ruby では通る）。
  逆に 3 本は止まらなくなった。
- **健全性**：v2・v3 とも 500 本で違反 0（負の対照は 180 本で違反を出す）。sakelib のテストとサンプルとライブラリ実験の 160 本も違反 0（接続を待ち続ける 2 つのサーバーは除く）。

### 4. 見直しで見つかった処理系の問題（直した）

- **`initialize` の健全性の穴**（sakelib の見直しで 2 か所から報告）。`initialize` の中のフィールドを経路を区別しない 1 つの表で追っていたので、
  `@h = A.new unless @h` のように一部の経路だけで書くと、`new` が入れた値が型から消えた（`URI.scheme` が nil にならない）。
  フィールドを局所変数と同じく環境で追い、全部の出口（終わりと `return`）を合わせるようにした（e59938b）。
  その際、インスタンスを関数に渡したらフィールドは何でもあり得るとして扱う穴も塞いだ。`@x in T` / `if @x` で絞り込めるようにした。
- **`@x ||= Hash[]` が `nil | Hash` のまま**（hex_game）。`&&` / `||` の右を飛ばす経路を絞り込んでいなかった（84263e9）。v2 の結果は変わらない。
- **計測の不具合**：`measure.rb` が省略された引数で落ちた（truth_table）。引数ごとではなくパラメータごとに数えるよう直した。
  ほかに、私の手順の誤りが 2 つ：最初の計測で TypeProf の結果の置き場所（`results-v8` には無く `results-head` にある）を取り違えた。
  `corpus-v3` の `.rb` が相対パスのシンボリックリンクのまま写り壊れていた（見直し役は元のコーパスを読んで作業し、計測前に実体へ置き換えた）。

### 補足（2026-10-05）：AI のトークン数と level 1 の誤報の内訳

**AI のトークン数**（`ai_tokens.mjs` → `ai-tokens-v2.md`、`ai-tokens-v3.md`）。上の「トークン数」は Prism の字句（コメント・改行を除く）で、AI のトークンではない。
現行の Claude のトークナイザは公開されていないので、公開されている 2 系統で数えた（コメント行と空行を除いたコード）：

| トークナイザ | v2 Sake/Ruby | v3 Sake/Ruby |
|---|---|---|
| Anthropic の旧世代（Claude 2 時代、`@anthropic-ai/tokenizer`） | 1.129 | 1.118 |
| OpenAI o200k_base（`js-tiktoken`） | 1.074 | 1.065 |
| OpenAI cl100k_base | 1.076 | 1.067 |

v3 のプログラムごとの比（o200k）：中央値 1.07、四分位 1.04〜1.10、範囲 0.92〜1.26。文字数の比は 1.115。
字句の比（1.16）より小さいのは、型名（`String.`）が少ない AI トークンにまとまるため。正確な値は API の count_tokens でしか取れない（未実施）。

**level 1 の誤報の内訳**（v3、53 本 164 件、`level1-causes.txt`。報告の文面から機械的に分類）：

| 原因 | 件数 | 本数 |
|---|---|---|
| 容器・フィールドで別々の用途の値が混ざる | 126 | 31 |
| 数の型の取り違え（`Float.round` に `Integer \| Float`、`Rational.to_f` に `Integer \| Rational`） | 26 | 18 |
| `case/in` で合わない値があると判定（フィールドの型が型ごとに 1 つなので、別の所で作った値が混ざる） | 7 | 7 |
| 通らない経路の nil、数と nil の演算 | 5 | 4 |

最大の原因は、容器の要素の型を「作った場所」ごとに、フィールドの型を「型」ごとに 1 つにまとめること：
`def index_by_id(rows) = (idx = Hash[]; …)` を部署と社員の両方に使うと値が `Employee | Department` になる（employee_dept_join）、
`class Heap` の `initialize` の `@items = Array[]` を 3 種類のヒープで共有する（heap_scheduler）。ほかに、本当に型の混ざる配列
（行を `Array["Tokyo", 13_960_000, 2194.07, true, nil]` で持つ、インタプリタや JSON の値：lisp_interp・stack_vm・json_parser で 39 件）。
状態の型付けのサーベイ（`../2026-10-03-state-survey/`）で扱った汎用コンテナの問題そのもの。

## 結論

1. **仕様変更で、宣言は Ruby の形になった**（`attr_reader`、例外クラス、`initialize`、`once`）。見直しで 500 本中 465 本が書き換わり、行数は Ruby の 0.95 倍のまま。
   **使う側は変わらない**：型名を書いた呼び出しは 100 行に 47 個で、その 2 割強がフィールドの読み書き（`Node.get_left(node)`）。Ruby の人に一番目立つ違いはここに残る。
2. **型を書かずに、型は 99% 以上決まる**（式 99.4〜99.6%、シグネチャ 99.0〜99.9%、Ruby 版の TypeProf は約 91%）。決まらないのは 1% 未満。
   決まった型のうち 1 つの型（mono）は約 80%、`nil | T` が 13%、それ以外の和が 4〜8%。和の大部分は、数の多相や構文木の和のように「正しい答えが和」のもの。
   書き直しはこの数字をほとんど動かさない：**型の決まり方は書き方より、プログラムがどう値を流すかで決まる**。
3. 誤報の多くは nil（level 2 で 294 本）。新たに増えた分の半分は「2 値の max/min が無いので `Array.max(Array[a, b])` と書く」ことから来ていて、
   型の推論ではなく**組み込みの品揃え**で減らせる。
4. 新しい機能のうち、キーワード引数・`x => T`・`class B < A`・`block_given?`・IO はこのコーパスでは試されていない。
   評価には、それらを使う Ruby のコード（ライブラリ、アプリ）を材料にした別のコーパスが要る。

## 次の候補（判断待ち）

- 組み込み：2 値の `Integer.max(a, b)` 類、`Math.PI` のような定数の操作、`dup`、`loop`。
- 既定値を式にする（`attr_reader items = Array[]`、`new` ごとに評価）。リテラルに限った理由（値の共有）を `initialize` で評価する形にすれば解ける。
- フィールドへの `+=`：`o.T.x += 1` のような書き方。
- `private`、`new` へのキーワード引数、`next` などの予約語をフィールド名に使う方法。
- 新しい機能を使う Ruby コードを材料にしたコーパス。
