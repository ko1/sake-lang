# Specification issues found while writing the stage 2 tests

SQLite 3.46.1 through `harness/sql_oracle.py` (STRICT tables). No test depends on any point below.

## Disagreements between SQLite and the specification

### 1. The INTEGER PRIMARY KEY is checked for uniqueness before other columns are converted (2.1)

```sql
CREATE TABLE u (id INTEGER PRIMARY KEY, age INTEGER);
INSERT INTO u VALUES (1, 30), (2, 40);
INSERT INTO u VALUES (1, 'old');
UPDATE u SET id = 1, age = 'old' WHERE id = 2;
```

SQLite prints `Error: UNIQUE constraint failed: u.id` for both statements. Spec 2.1 says the order is
"NOT NULL of each column ...; then storage conversion of each column ...; then uniqueness: the
INTEGER PRIMARY KEY first", so it expects `Error: cannot store TEXT value in INTEGER column u.age`.
NOT NULL still comes first in SQLite: `(1, NULL)` into a NOT NULL `age` gives the NOT NULL error.
Other UNIQUE and PRIMARY KEY constraints do follow the spec. For example, with `a INTEGER UNIQUE,
b REAL`, the statement `INSERT ... VALUES (1, 'x')` reports the storage error first.

### 2. A value that is not an integer, stored in an INTEGER PRIMARY KEY (1.5, 2.1)

```sql
CREATE TABLE q (id INTEGER PRIMARY KEY, v TEXT);
INSERT INTO q VALUES ('abc', 'c');
INSERT INTO q VALUES (1.5, 'c');
```

SQLite prints `datatype mismatch`, which is not in the spec's catalogue. Spec 1.5 gives
`cannot store TEXT value in INTEGER column q.id` and `cannot store REAL value in INTEGER column q.id`.
(Text that is a whole number, such as `' 40 '`, `'5.0'` or `8.0`, is stored as the spec says.)

### 3. UPDATE that sets an INTEGER PRIMARY KEY to NULL (2.1, 2.2)

```sql
CREATE TABLE q (id INTEGER PRIMARY KEY, v TEXT);
INSERT INTO q VALUES (-5, 'a'), (-4, 'b');
UPDATE q SET id = NULL WHERE v = 'a';
```

SQLite prints `datatype mismatch` and leaves the row as it was. Spec 2.1 says "when a row is stored with
NULL there ... it gets one more than the largest value in the column", and 2.2 says UPDATE stores with
1.5 and checks with 2.1. So the spec expects id -3 (or the "largest" is meant to exclude the row
being updated; the spec does not say).

### 4. `x IN (...)` uses only x's affinity (2.3)

```sql
CREATE TABLE t (i INTEGER, s TEXT, r REAL);
INSERT INTO t VALUES (12, '12', 12.0);
SELECT 12 IN (s), '12' IN (i), '12.0' IN (r), 12 = s, '12' = i FROM t;
```

SQLite prints `0|0|0|1|1`. Spec 2.3 says IN is "1 if `x = ei` for some i (affinity as for `=`, between
x and each ei)", which gives `1|1|1|1|1`. SQLite gives the same result as the spec when x is a column
or a CAST (it converts each ei by x's affinity). The two differ only when x has no affinity and an ei
has one. The tests use only cases where both agree.

### 5. An INTEGER PRIMARY KEY that is also declared NOT NULL (2.1)

```sql
CREATE TABLE p (id INTEGER PRIMARY KEY NOT NULL, v TEXT);
INSERT INTO p VALUES (NULL, 'b');
```

SQLite gives the row the next key and prints nothing. Spec 2.1 checks "NOT NULL of each column" first.
That suggests `NOT NULL constraint failed: p.id`, but the INTEGER PRIMARY KEY rule says a NULL there
gets a key. The spec does not say which rule wins.

### 6. DEFAULT on an INTEGER PRIMARY KEY (2.1)

```sql
CREATE TABLE d (id INTEGER PRIMARY KEY DEFAULT 5, v TEXT);
INSERT INTO d (v) VALUES ('a');
SELECT * FROM d;
```

SQLite prints `1|a` and ignores the DEFAULT. Spec 2.1 has two rules for this row: "DEFAULT v: a column
not given a value by an INSERT gets v", which gives 5, and the INTEGER PRIMARY KEY rule ("or without a
value for it" gets the largest plus one), which gives 1. The spec does not say which one applies.

### 7. ORDER BY term out of range is numbered by the term's position (1.7, stage 1)

```sql
CREATE TABLE t (a INTEGER, b INTEGER);
SELECT a, b FROM t ORDER BY 5;
SELECT a, b FROM t ORDER BY 1, 0;
```

SQLite prints `1st ORDER BY term out of range - should be between 1 and 2` and
`2nd ORDER BY term out of range - should be between 1 and 2`. Spec 1.7 says "a term that is an integer
literal `k` ... outside 1..n is the error `<k-th> ORDER BY term out of range`", which reads as `5th` and
`0th`. This is a stage 1 point. The one stage 2 test that uses this error (hidden 056) writes the bad
literal as the 5th term with value 5, so both readings print `5th`.

## Rules that are unclear

- **`max`/`min` with one argument (2.4).** The table says "two or more arguments". It does not say
  what a stage 2 program does with `max(3)`: `wrong number of arguments to function max()`, or
  something else? SQLite treats it as the stage 3 aggregate and prints `3`. No test uses it.
- **`max`/`min` among equal values of different types (2.4).** "The largest / smallest" does not pick
  between `2` and `2.0`. SQLite returns the first: `max(2, 2.0)` is the INTEGER 2, `max(2.0, 2)` is
  the REAL 2.0. No test has such ties.
- **How far BETWEEN's bounds extend (2.3).** The spec says BETWEEN binds like `=` and that the `AND`
  belongs to BETWEEN. It does not say at what precedence `b` in `x BETWEEN a AND b` is parsed, so
  `1 BETWEEN 0 AND 2 IN (1)` could be `(1 BETWEEN 0 AND 2) IN (1)` = 1 (SQLite) or
  `1 BETWEEN 0 AND (2 IN (1))` = 0. Left associativity on level 6 suggests SQLite's reading. The
  tests only use bounds made of operators that bind tighter than level 6 (such as `0 + 1`).
- **Temporary conflicts in UPDATE (2.2).** The spec says tests avoid them. Note that SQLite rejects
  even a swap: `UPDATE w SET v = 3 - v` on the values 1 and 2 of a UNIQUE column, and `UPDATE w SET
  id = id + 1` on keys 1 and 2, both print `UNIQUE constraint failed`. An implementation that checks
  only the final state would print nothing. The tests avoid both.
