# Stage 6 (windows): specification issues

Found while writing the stage 6 tests and checking them with SQLite 3.46.1 (STRICT tables, via
`harness/sql_oracle.py`). No test depends on any point below.

## Disagreements between SQLite and the specification

1. **A frame whose start is after its end, written statically** (6.2: "A frame whose start comes
   after its end is empty").
   `SELECT a, sum(a) OVER (ORDER BY a ROWS BETWEEN CURRENT ROW AND 1 PRECEDING) FROM t;`,
   `... ROWS BETWEEN 1 FOLLOWING AND CURRENT ROW ...`, `... ROWS 2 FOLLOWING ...` (start alone),
   `... RANGE 2 FOLLOWING ...`: SQLite prints `Error: unsupported frame specification` (not in the
   catalogue). Frames that are empty because of their offsets with the same kind of bound
   (`ROWS BETWEEN 1 PRECEDING AND 2 PRECEDING`, `ROWS BETWEEN 2 FOLLOWING AND 1 FOLLOWING`,
   `RANGE BETWEEN 2 FOLLOWING AND 1 FOLLOWING`) are empty as the spec says; the tests use only those.

2. **A window call inside a scalar function's arguments** (6.2: "anywhere else (... inside another
   call's arguments) is `misuse of window function <name>()`").
   `SELECT a, abs(row_number() OVER (ORDER BY a)) FROM t ORDER BY a;` runs in SQLite and prints
   `1|1`, `2|2`, ... Only an aggregate or window call's arguments give the misuse error
   (`sum(row_number() OVER (...)) OVER ()`, `max(rank() OVER (...))`). The tests use only those.

3. **Negative RANGE offset** (6.2: "A negative offset is `frame starting offset must be a
   non-negative integer` ..."). `SELECT a, sum(a) OVER (ORDER BY a RANGE BETWEEN -2 PRECEDING AND
   CURRENT ROW) FROM t;` gives `Error: frame starting offset must be a non-negative number`
   ("number", not "integer"). Under ROWS the message is as specified. Tests use negative offsets
   with ROWS only.

4. **A result alias of a window call used in WHERE** (1.7 lets WHERE use a result column's alias;
   6.2 makes a window call in WHERE `misuse of window function <name>()`).
   `SELECT a, row_number() OVER (ORDER BY a) AS rn FROM t WHERE rn > 2;` gives
   `Error: misuse of aliased window function rn` (not in the catalogue). The spec would give
   `misuse of window function row_number()`. Not tested.

5. **ntile with a non-integer argument** (6.3: "n not a positive integer is `argument of ntile must
   be a positive integer`"). `ntile(1.5)` runs (as 1 bucket), `ntile(2.0)` runs as 2, and
   `ntile('2')` runs as 2; only 0, negative numbers and NULL give the error. Tests use integer
   arguments (literals and integer expressions such as `ntile(1 - 3)`).

6. **Quoted window names** (1.2: a quoted identifier is an identifier; names are case-insensitive).
   `SELECT who, rank() OVER "w1" FROM run WINDOW w1 AS (ORDER BY km DESC);` gives
   `Error: no such window: "w1"` (quotes kept), and `WINDOW "w1" AS (...)` is not found by `OVER w1`.
   `OVER ("w1")` as a base fails the same way. Unquoted names match case-insensitively
   (`OVER W1` finds `WINDOW w1`). Tests use only unquoted window names.

## Unclear or unspecified points (not tested)

7. **lag/lead with a negative or NULL k.** `lag(a, -1)` acts as `lead(a, 1)` in SQLite; `lag(a, NULL)`
   gives NULL. 6.3 says only "k positions earlier". `k = 0` (the row itself) is tested.
8. **Which row lag/lead's default d is evaluated on.** `lag(a, 1, a * 10)` uses the current row's a
   in SQLite. 6.3 says only "or d". Tests use a constant d.
9. **nth_value with n <= 0.** SQLite: `second argument to nth_value must be a positive integer` (not
   in the catalogue). 6.3 does not say.
10. **Integer literals and result aliases in a window's ORDER BY / PARTITION BY.** In SQLite,
    `OVER (ORDER BY 2)` orders by the constant 2 (not the 2nd result column, as 1.7 would suggest),
    and a result alias there is `no such column`. 6.1/6.2 do not say how names and integer literals
    are resolved inside a window-spec.
11. **A fractional frame offset** (`ROWS 1.5 PRECEDING`): SQLite gives `frame starting offset must
    be a non-negative integer`; the grammar says n is an integer literal, so it could equally be a
    syntax error.
12. **Two windows of the same name in one WINDOW clause.** SQLite accepts it (one of them is used);
    the spec does not say.
13. **Errors for cases the spec says tests avoid, which are not in the catalogue**: a non-window
    function with OVER (`upper(b) OVER (...)`: `upper() may not be used as a window function`);
    `DISTINCT` in a window aggregate (`DISTINCT is not supported for window functions`); overriding a
    base window's PARTITION BY / ORDER BY (`cannot override PARTITION clause of window: w`,
    `cannot override ORDER BY clause of window: w`); a frame start of UNBOUNDED FOLLOWING or end of
    UNBOUNDED PRECEDING (`syntax error`). A builder cannot know what to print for these.
14. **WINDOW in a compound select.** Each simple-select has its own WINDOW clause in SQLite; a window
    defined in the last simple-select is not visible in the first (`no such window: w`). 6.1 places
    WINDOW in the SELECT grammar but 5.1 does not mention it.
