変更できる状態に、注釈なしで型を付ける

Sake のフィールドの型をどう決めるかについて、言語理論・プログラム解析の先行研究を調べた。結論：「値と一緒に動く型」と「生成箇所ごとの型」の 2 つを組み合わせる方向に、確立した手がある。前者は、作った後に変えないフィールドの型を値の型に含める（ML の型引数を、宣言なしでやる形）。後者は、変えるフィールドの型を、生成箇所と 1 段の文脈で分ける（Self と Java で研究された「データの多相」）。Sake の推論器はすでに関数について後者と同じ形（CPA）をしているので、データにも同じ形を広げるのが自然だ。

1 · 問題

getter の結果の型は、どこにも書かれていない

class Box < {reader: [item]}
end
a = Box.new("text")
b = Box.new(42)
String.upcase(Box.get_item(a))     # 正しいが、今は「Integer かもしれない」と報告される

組み込みの操作は、結果の型を操作自身が決めている（String.upcase は String）。Box.get_item の結果の型は書かれておらず、推論器はフィールドの型をプログラム全体で 1 つに集めている。だから、同じ型を中身を変えて使い回すと union にぼやける。ライブラリ試作で一番多かった誤報がこれだった。

理論の言葉に直すと、問いは 3 つになる。(1) フィールドの型を、型ごとではなく値ごとに区別できるか（データの多相）。(2) 型が時間とともに変わるフィールド（nil で始めて後で埋める）を扱えるか（強い更新）。(3) 分からないところで何を報告するか。

3 · 各系統

何が分かっているか

A. 型引数を宣言し、具体化は推論する

ML 系では type 'a box = {mutable item: 'a} のように、フィールドが型引数であることだけを宣言する。具体化は推論するので、{item = "text"} は string box、{item = 42} は int box になる。変更できる参照と多相が同居すると不健全になるので、値の制限（value restriction）で一般化を止める。Crystal は Ruby に近い構文で同じことをしていて、class MyBox(T) と宣言すれば MyBox.new(1) は MyBox(Int32) と推論される。

Sake から見ると、getter の型が Box(T) → T と操作の側で決まり、「型は操作に書く」と揃う。代わりに、型引数を型の宣言に書くことになる。

Wright, "Simple Imperative Polymorphism", Lisp and Symbolic Computation 8(4), 1995（値の制限）。Crystal: Type inference、Crystal: Generics。

B. 生成箇所と文脈で分ける（データの多相）

型注釈の無い言語の型推論で、まさにこの問題が研究されてきた。関数の多相は「引数の型の組ごとに関数を解析する」で解ける。Agesen の Cartesian Product Algorithm（CPA）がそれで、Sake の推論器は今この形をしている。データの多相（入れ物が中身によって違う型になること）は、CPA だけでは解けない。そこで次の研究がある。

  • Plevyak と Chien（1994）: オブジェクトを生成箇所で分け、中身の型が混ざるところだけを繰り返し分割して精度を上げた。
  • Wang と Smith の DCPA（2001）: CPA にデータの多相を足した。生成箇所に、それを作った呼び出しの文脈を加えて区別する。Box.make のような作る関数を経由しても、呼び出しごとに別の Box になる。
  • Java の points-to 解析: 同じ考えが「オブジェクト感応（object sensitivity）」として成熟した。Milanova、Rountev、Ryder（2002、2005）が提案した。Smaragdakis らの "Pick your contexts well"（2011）は、どの文脈を何段持つかで精度と費用がどう変わるかを整理した。1〜2 段の文脈で、汎用の入れ物の多くを区別できる。

Sake では、Array が生成箇所ごとに要素型を持つので、半分はもう入っている。Struct のフィールドにも同じ扱いを広げ、作る関数の呼び出し 1 段を文脈に加えるのが、DCPA に当たる。注釈は要らない。代わりに、解析の費用と、再帰的な構造（連結リスト）での打ち切りが課題になる。

Agesen, "The Cartesian Product Algorithm", ECOOP '95。Plevyak & Chien, "Precise Concrete Type Inference for Object-Oriented Languages", OOPSLA '94（関連）。Wang & Smith, "Precise Constraint-Based Type Inference for Java", ECOOP 2001。Milanova, Rountev, Ryder, "Parameterized Object Sensitivity for Points-to Analysis for Java", TOSEM 14(1), 2005。Smaragdakis, Bravenboer, Lhoták, "Pick Your Contexts Well: Understanding Object-Sensitivity", POPL 2011。

C. 型が変わる状態：強い更新、typestate、別名の制御

「nil で作って、後で埋める」フィールドは、時間とともに型が変わる。これを正確に扱うには、ある時点でそのオブジェクトを指しているのが 1 つだけだと分かる必要がある（強い更新）。

  • typestate（Strom と Yemini 1986、DeLine と Fähndrich 2004）: オブジェクトの状態を型に含める。
  • alias types（Smith、Walker、Morrisett 2000）と Rust の所有権: 別名を型で制御して、強い更新を可能にする。
  • recency abstraction（Balakrishnan と Reps 2006）: 注釈なしの解析の側の手。生成箇所の「最新の 1 個」だけを別に持ち、作った直後の初期化を強い更新で扱う。

Sake の誤報の分類で「nil で初期化して後で埋める」に当たる部分には、recency abstraction が効く見込みがある。所有権の型は、言語を大きく変えるので候補から外す。

Strom & Yemini, "Typestate", IEEE TSE 12(1), 1986。DeLine & Fähndrich, "Typestates for Objects", ECOOP 2004。Smith, Walker, Morrisett, "Alias Types", ESOP 2000。Balakrishnan & Reps, "Recency-Abstraction for Heap-Allocated Storage", SAS 2006。

D. 状態を限る：不変のデータと、明示の可変セル

ML の流儀では、レコードは基本的に不変で、変わるものは ref セルとして明示する。Erlang や Elixir では、状態はプロセスのループの引数に置く。Clojure では、不変のデータに atom を足す。どれも「変わる場所を少なく、明示する」ことで、型も推論も単純にしている。

Sake の実測とよく合う。Struct.new のフィールドの 82% は、作った後に書き換えられていなかった。変わらないフィールドの型は、値の型そのものに含められる。Sake の Tuple や Record がすでにそうしていて、[1, "a"] の型は位置ごとの型を持つ。試作で validate の書き手が「Record にしたら汎用の入れ物の問題が消えた」と書いていたのは、このためだ。Struct の変わらないフィールドを同じように扱えば、宣言なしで A の精度が手に入る。Box.new("text") の型は、item が String の Box になる。

Leroy 他, The OCaml system（可変フィールドと ref）。Elixir、Clojure の言語資料。

E. 分からないところで何を報告するか

soft typing（Cartwright と Fagan 1991、Wright と Cartwright の Soft Scheme 1997）は、動的型の言語に推論をかけ、証明できない箇所には実行時の検査を残す。Sake の「各操作が実行時に検査し、推論が証明できたところだけ省ける」は、この系譜にある。

Erlang の Dialyzer が使う success typing（Lindahl と Sagonas 2006）は逆に、「必ず失敗する」と言えるときだけ報告して、誤報を出さない。Sake の level 1（型が確実に合わないときに止める）は、この考えに近い。精度を上げきれない場所では、level の設計で受け止める道がすでにある。

Cartwright & Fagan, "Soft Typing", PLDI 1991。Wright & Cartwright, "A Practical Soft Type System for Scheme", TOPLAS 19(1), 1997。Lindahl & Sagonas, "Practical Type Inference Based on Success Typings", PPDP 2006。

F. Ruby・動的言語での先例

DRuby（Furr ほか 2009）は、インスタンス変数の型をクラスごとに 1 つ推論した。汎用のコンテナは注釈で型引数を書かせた。TypeProf もフィールドをクラスごとに扱う（今の Sake と同じ）。Crystal は A の形で、型引数を宣言し、new の引数から推論する。どれも「型ごとに 1 つ」か「宣言した型引数」のどちらかで、宣言なしに値ごとに分ける例は、B・D の研究側にしか見当たらなかった。

Furr, An, Foster, Hicks, "Static Type Inference for Ruby", SAC 2009。

4 · Sake への提案

変わらない部分は値の型に、変わる部分は生成箇所に

  1. 変わらないフィールドを、値の型に含める（D）。作った後に誰も書き換えないフィールドの型を、Tuple や Record の位置の型と同じように、値の型に持たせる。Box.new("text") は item が String の Box、Box.new(42) は item が Integer の Box になる。getter の結果の型は、渡された値の型から決まる。宣言は要らない。「変わらない」ことを言語で保証するなら、作った後に書き換えられない設定（たとえば value: [item]）を足すか、reader: の意味をそこまで強める。後者なら、今のクラス内での @x = v を禁じることになる。
  2. 変わるフィールドは、生成箇所と 1 段の文脈で分ける（B）。accessor: や、クラス内で書き換えるフィールドの型は、new を書いた場所に、作る関数の呼び出し 1 段を加えて区別する（DCPA と 1 段のオブジェクト感応に当たる）。Array の要素型とも揃う。
  3. 作った直後の初期化は、最新の 1 個で扱う（C の recency abstraction）。nil で作ってすぐ埋める形の誤報を減らす。2 の後に効き目を測ってから決める。
  4. 宣言（A）は、どうしても書きたい人のための逃げ道に回す。型引数を書かせる仕組みは、1 と 2 で足りないことが測定で分かってから考える。

確かめ方: 1 と 2 を推論器に入れ、ライブラリ試作 8 本の誤報（汎用の入れ物に由来するもの）と、コーパス 500 本の level 1・2 の本数、健全性の違反（0 のままか）、解析時間を、今の推論器と比べる。1 は推論器の変更が小さく、Tuple の扱いを流用できるので先に試せる。
