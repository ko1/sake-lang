Sake の Rust バックエンド: マイクロベンチマーク

2026-10-10 (JST) · sp4（16 コア、専用）· Ruby 4.0.6 +YJIT · rustc 1.93.1 · experiments/2026-10-10-rust-backend

bin/sabic（錆 + c）は Sake のプログラムを Rust に変換してネイティブにする。loops / fib / levenshtein の 3 本で、生成コードは Ruby 4.0 (YJIT) の 3〜21 倍、JIT なしの Ruby の 8〜53 倍速く、手書き Rust の 0.9〜1.6 倍以内。mixin のディスパッチ（Shape.area(s)）は 1 回 0.12 ns で、Rust の dyn Trait（1.03 ns）より速く、手書きの enum（0.19 ns）と同じ桁。matz の Spinel（Ruby → C）とは loops・levenshtein で同じ速さ、shapes では 8 倍速い。

方法

  • 変換: 検査済みの SakeAST を入力に、関数を引数の型ごとに単相化して Rust を出し、rustc -O -C overflow-checks=on で実行ファイルにする。Integer は i64（溢れたらエラー）、nil は Option、Array とオブジェクトは Rc<UnsafeCell<…>>（Sake の値は参照なので共有する）、合併型は enum、mixin 呼び出しは match、yield だけのブロックは &mut impl FnMut、Array.each などのブロックはループに展開。対象外は行番号付きで断る。
  • 比較: Ruby（--yjit と --disable-yjit）、Sake インタプリタ、Sake → Rust、手書き Rust。同じアルゴリズムを同じ形で書き、出力の一致を確かめた。各 3 回の中央値（インタプリタは 1 回）、壁時計。
  • 入力: loops は 10,000 × 100,000 回、fib は 38（インタプリタは 32）、levenshtein は 40 文字 × 100 語の全組、shapes は 1,000 個 × 1,000,000 round（インタプリタは 10,000 round）。

  • インタプリタは Ruby(YJIT) の 150〜760 倍遅い。 AST を歩く Ruby のインタプリタで、1 操作ごとに型タグを検査している。
  • fib の差が 2.7 倍にとどまるのは Ruby 4.0 の YJIT が速いから。 約 1.3 億回の再帰呼び出しを 0.5 秒。基本ブロック内では一度 guard した型を使い回し、残る費用はメソッド呼び出しのフレームと戻り値の guard。
  • 手書き Rust との差（loops 9%、levenshtein 1.6 倍）は Ruby の意味論を保つ検査の分: Array.fetch の負の添字の正規化と範囲検査、a[i] = v の「末尾なら push」の分岐。床除算は原因ではない（手書きを床除算にしても 1.161 秒、切り捨てで 1.162 秒）。

結果: mixin ディスパッチ（shapes、109 回、秒）

Circle・Rect・Tri を 1,000 個混ぜた Array をなめて Shape.area(s) を足す。対照の shapes_mono は全部 Circle（呼び出し先が静的に決まる）。109 回なので「増分の秒数 = 1 回あたりの ns」。

  • Sake の mixin ディスパッチは enum の match になる。 include している型の集合が静的に閉じているので、vtable は要らず、本体（3 * r * r）が呼び出し側に展開される。Rust の dyn Trait は呼び出し先が決まらないので展開できず、約 8 倍の費用。
  • 最初の生成器が手書きより 1.2 秒遅かったのは、ディスパッチではなく Rc の参照カウント。 生成コードを手で直して切り分けた: ディスパッチ引数の clone を借用にすると 1.65 → 1.18、Array.each の要素取り出しも借用にすると 0.477。1 反復に 2 組あった参照カウントの増減で 1.15 秒、残り 0.07 秒が Rc 経由の間接参照。
  • 生成器を直した。 本体で再代入されない非 Copy の引数（オブジェクト・配列・文字列）は &T で渡し、Array.each の要素も借用で取り出す。shapes は手書き enum と同じ 0.60 秒、shapes_mono は手書きの 1.16 倍。

C バックエンド ceec（秒）

bin/ceec は同じ型推論の上で C を出す（gcc 15.2 -O2）。Array・String・オブジェクトはポインタの共有（解放しない、GC なし）、nil | T は {bool some; T v;}、クラスの合併は tag と switch、整数演算は溢れを検査する。手書き C は溢れ検査なし。

ベンチSake → CSake → C（溢れ検査なし）手書き CSake → Rust手書き Rust
loops（109 回）1.3871.3561.3551.2691.162
fib 380.1860.0650.0640.1860.206
levenshtein 100 語0.0320.0300.0150.0340.021
shapes（109 回、3 型）0.6740.6070.4710.5960.606
shapes_mono（109 回）0.4810.4060.3540.4790.408
  • Sake → C と Sake → Rust はほぼ同じ速さ。 loops は gcc と LLVM の差（手書き同士でも C 1.355 対 Rust 1.162）。
  • fib の手書き C との 3 倍の差は、すべて整数の溢れ検査。 検査を外すと 0.065 で手書き C と同じ。検査ありの手書き Rust も 0.206 で、どちらの言語でも検査が再帰の展開を止める。Sake の Integer は溢れないのが意味論なので外せない。
  • levenshtein の 2 倍は Ruby の配列の意味論を保つ検査（負の添字、範囲、末尾への書き込みは push）。shapes の残り 0.14 ns/反復は未切り分け。
  • 書きやすさ。 Rust 版で手間だった所有権と参照カウントが C には無く、型推論は 1 行も足していない。代わりにメモリを解放しない。

Spinel（matz の Ruby AOT コンパイラ）との比較（秒）

Spinel は Ruby の大きな部分集合を全プログラム型推論で C に落とす（世代別 GC 付き）。同じ Ruby 版のプログラムをそのまま入力にして、同じ sp4 で測った（dd29ea35、gcc 15.2、既定の -O2。--warn-widen の警告は利用者のコードには無し）。

fib 380.4960.006*0.1850.205
levenshtein 100 語0.3180.0380.0340.021
shapes_mono（109 回）18.04.450.4770.41
shapes（109 回、3 型）20.04.580.5960.60

* Spinel の README 自身が注意している通り、gcc が再帰を定数畳み込みしたもので比較には使えない。

  • 整数と配列だけの loops・levenshtein は同じ速さ。 どちらも型を全部決めてネイティブの整数演算に落としている。
  • shapes は Spinel が 8〜9 倍遅い。 ディスパッチの増分は Spinel も 0.13 ns と小さく、差は 1 反復あたり約 4 ns の定数部分（GC 管理のヒープ上のオブジェクトとブロック呼び出し。生成 C を読んでの切り分けは今後）。
  • 解析器の大きさは桁が違う。 Spinel は解析 107,000 行 + コード生成 141,000 行 + ランタイム 41,000 行の C。Sake は resolver 1,600 行 + 生成器 1,100 行の Ruby。Spinel が Ruby の意味論をコンパイラ側で引き受けているのに対し、Sake は言語の側で削っている。性能が同じなら、残る問いは「どちらが書きやすいか」。

限界

  • 対象は部分集合。Hash・Set・Regexp・rescue・(A|B).f・Thread・Tuple/Record のパターンは未対応で、sakelib の移植のような普通のプログラムはまだ通らない。
  • 型推論は typer とは別に生成器の中に書いた小さなもの。typer が式ごとの型を保持するようになれば置き換える。
  • Integer は 64 ビット。Rc は循環を回収しない。
  • マイクロベンチマーク 4 本だけ。文字列処理や Hash の多いプログラムでは別の結果になる。
