# ぱっと見の見やすさ: Ruby と Sake（2026-10-14、準備）

ko1 の仮説: AI が書いたコードのレビューは流し読み（ザッピング）が中心になる。そうなると効くのは、精読したときの分かりやすさより「ぱっと見て見やすいか」。これを人に答えてもらうページを作った。

## 方法

- 題: 12 問。どれも 2〜4 行のコードで、Ruby 版と Sake 版がある。
  - 仕様どおりか（R1〜R6）: 仕様の 1 文とコードを見て「仕様どおり / 誤りがある」を選ぶ。誤りは R1（`<=` と `<`）、R2（整数の割り算）、R4（古い順の先頭 3 件）の 3 つで、どれも型の検査を通る論理の誤り（ko1: 誤りは型検査が通る前提）。
  - 何をするか（G1〜G6）: 4 択（表示のたびに並べ替える）。
- 1 人は各題を一方の言語でだけ見る。参加者を無作為に 2 群に分け、題の番号の偶奇で言語を入れ替える（各人 Ruby 6 問、Sake 6 問）。題の順も無作為。
- 測るもの: 正答、答えるまでの時間（コードを表示してから選ぶまで）、答えたあとの「ぱっと見の見やすさ」（1〜5）。
- 最後に R3・R5・G2・G6 を 2 つの書き方で左右に並べ（左右は無作為）、どちらがぱっと見て見やすいかを 5 段階で選ぶ。
- 背景: Ruby の経験、Sake を見たことがあるか。

## コード

- `check/all.rb` と `check/all.sake` が、走らせて確かめたプログラム（データの準備と出力を含む）。両者の出力は一致する（`diff <(ruby check/all.rb) <(bin/sake check/all.sake)`）。Sake 版は既定の検査（レベル 1）を通る。`--strict=2` では G6 の `Array.zip` の nil で止まる（Ruby 版も同じ値になりうる）。
- ページに出すコードは、`build.rb` がこの 2 つから準備と出力の行を除いて取り出す。`items.json` は仕様の文、誤りの有無、選択肢（先頭が正解）。`template.html` → `glance.html`。
- Sake 版は、Ruby がメソッドの連鎖で書くところは連鎖の形（`xs.Array.select { }.Array.map { }`）、そうでないところは `Array.tally(words)` の形で書いた。演算子（`*`、`/`、`<=`）は両方同じ。

## 記録

- 回答は artifact の db に 1 人 1 文書（`responses/<viewer id>`）で保存する。読めるのは作成者（ko1）だけ（rules: `responses` は owner のみ、`responses/{self}` は本人が書ける）。
- **db に書けるのは、ko1 の組織のメンバーで、Contributor 以上の権限がある人だけ。** 組織の外の人（公開リンクで来た人を含む）は書けない。その場合、ページは回答を JSON の文字列で表示し、送ってもらうよう頼む。
- 作成者がページを開くと「集計を見る」で、言語 × 題の種類ごとの正答率・時間の中央値・見やすさの平均と、並べた比較の平均（Sake 寄り +）が出る。

## 限界（投入前に分かっているもの）

- 参加者は Ruby に慣れていて、Sake は初見。見やすさの評価は慣れに強く引きずられる。
- 題が短い（2〜4 行）。流し読みの対象としては現実より小さい。
- Sake の導入の説明を読んでから答えるが、Ruby には説明がない。
