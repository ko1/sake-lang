AI 向け言語 Sake の評価

2026-10-06 ・ Claude Sonnet 5.5 に Sake と Ruby で書かせ、直させた結果（P1〜P4、解く側 106 体）

  1. 正しさは Ruby と同じ。事前学習で一度も見ていない言語なのに、新しく書く 20 題でも、既存のプログラムを直す 20 題でも、Ruby と同じ正答率に届いた。
  2. ただし毎回約 1.5 倍のコストを払う。新しく書くと出力トークン 1.6 倍・時間 1.65 倍、直すと 1.4 倍・1.75 倍。反復を足しても同じ値が出た。
  3. その上乗せは、見える誤りには出てこない。存在しない API はほぼ 0、検査に止められるのは 10 試行に 1 回程度で、止められても次で直る。モデルは書く前に、見えないところで Sake の書き方を確かめている。
  4. 型検査は、この規模では正しさを上げなかった。変更の題でも、直し忘れを検査が止めた試行は 0 回だった。止めたのは Sake の書き方の誤りで、残った誤りは型では捕まらないものだった。

何を確かめたか

Sake は Ruby の構文で、すべての操作に型を書く言語（String.upcase(s)）。変数や引数に型は書かず、実行前に検査器が型を追う。問いは「AI にとって書きやすく、直しやすいか」。

  • 新しく書く題（P1〜P3）: AI が新たに書いた中規模の 20 題（ログ集計、在庫、経路探索、小さなインタプリタなど）。仕様、公開例 2、隠しテスト 12〜19。参照解が満点を取り、わざと壊した解が落ちることを先に確認した。
  • 直す題（P4）: 上の 20 題それぞれに、プログラムの複数箇所を流れるデータの型か形を変える変更要求を 1 つ付けた（端数を持つようになる、欠けうる値になる、1 つが複数になる、など）。変更前の参照解を渡し、その場で直させる。
  • 解く側: Sonnet 5.5 のサブエージェント。Sake（資料 tutorial・spec・builtins を読ませる）と Ruby（資料なし）。一発で書く条件と、公開例で最大 8 回まで試せる条件。新しく書く題は 5 反復、直す題は 2 反復（試行ありのみ）。
  • 採点: 隠しテストの出力完全一致。P3 からは、解答と試行の記録から次も機械的に数えた。
    • 試行の回数
    • 検査に止められた回数とその理由
    • どこにもない API の呼び出し
    • 出力トークン

同じ条件でも反復ごとに 12〜17 とぶれ、条件間の差（最大 1.6）はその中に収まる。落ちる題はほぼ決まっていて、原因は言語によらない仕様の読み違いだった。例えば b14 は、名前の誤った問い合わせを bad query とするか not found とするかで、全条件が同じ隠しテストを落としている。

直す題（P4、20 題 × 2 反復）も同じだった。Sake 37/40、Ruby 37/40。

P1 は処理系の修正前で、Sake・一発の 1 題を検査の誤報で失っている（その後修正）。P2 以降、検査を外せば通ったはずの題を検査のせいで落とした例はない。

結果 3: 思考はどこで増えたか

記録には思考ブロックが残っているが、本文は伏せられている。そこで、呼び出しごとに「出力トークン − 見えている出力（書いたコード、コマンド、本文）」を思考量とし、その呼び出しが何をしたかで振り分けた。P2 の 1 題あたりの値。

  • 資料は書いている途中にはほとんど引かれない。最初に全部を読み、あとは覚えたまま書いている。

見えている出力のトークンは Claude 2 世代のトークナイザで数えた近似。思考量はその差なので、同じ近似を含む。

結果 4: 見える誤りには出てこない

思考の中身は見えない。そこで P3 では、上乗せが誤りとして外に出ているかを、解答と試行の記録だけから数えた。もし Sake の上乗せが「迷って誤る」ことの表れなら、どこかの数字に Sake 側の誤りが積み上がるはず。

P3・試行あり（各 40 題）試行/題検査で停止どこにもない API実行時の名前エラー
Sake1.186 / 47 試行00
Ruby1.220 / 49 試行00
  • 存在しない API はほぼ書かない。P2・P3 の全試行を通じて、どの型にもない名前を書いたことは一度もない。別の型にはある名前を書いたのが 3 回（3 回とも Array.slice）。最終解答では 0。
  • 検査に止められるのは 10 試行に 1 回程度で、6 回とも次の試行で通った。理由は次のとおり。
    • 値へのメソッド呼び出し 2（c.abs）
    • 未定義名 1（Array.slice）
    • 引数の数 1
    • 型 1（nil になりうる値の割り算）
    • 構文 1
    半分は Ruby の書き方の持ち込みで、P1・P2 と同じ種類だった。
  • 試行の回数も同じ（1.18 対 1.22）。Sake だから試して直す回数が増える、ということはない。

つまり、Sake で払う 1.5 倍は、外から見える誤りのどれにも対応していない。結果 3 と合わせると、モデルは書く前に「この操作はどの型にあるか、この形は許されるか」を確かめてから書き、だから誤りが外に出ない、と読むのが筋が通る。ただし、これは観測ではなく推定である。

結果 5: 直す作業でも型検査は直し忘れを止めなかった

型を操作に書くことの利点として期待していたのは、変更の場面だった。値の型が変わると、それを扱う操作の型が合わなくなるので、直し忘れた箇所を検査器が指すはずだ、という読みである。P4 はこれを試した。

P4（20 題 × 2）正答試行/題検査で停止そのうち直し忘れ書き換えた行（平均）
Sake37/401.182 / 47 試行028.6
Ruby37/401.050 / 42 試行—21.7
  • 検査が止めた 2 回は、どちらも直し忘れではなかった。新しく書いたコードで、タプル（[a, b, c]）を Array.fetch に渡したもの。うち 1 回は、Array.any? で nil を除いた後でも、要素の型が nil を含んだままだったことも重なっている。Ruby なら配列で済むところで、タプルと配列を区別する Sake の摩擦が出た。
  • 落ちたケースの大半は、変わらないはずの振る舞いの崩れだった。変更前のプログラムなら通るケースを、直した後で落としたもの。Ruby 5 件中 4 件、Sake 4 件中 3 件。どれも検査を通った解の誤りで、型の誤りとしては現れない。
  • ただし天井に近い。どちらの言語でもほとんどの題が 1 回目の試行で公開例に通った。プログラムは 40〜150 行、変更は 20〜30 行で、Sonnet が変更の行き先を見落とす規模ではなかった。検査器の出番がそもそも少ない。

どう読むか

学べる言語にはなっている。事前学習ゼロで、新しく書くのも直すのも Ruby と同じ正しさに届く。Ruby の構文と Ruby の名前（String.upcase）を借りた設計が効いていると考えられる。存在しない API をほとんど書かないのも、名前が Ruby と同じだからだろう。

しかし、AI にとって安く書ける言語にはなっていない。同じ結果に毎回約 1.5 倍の出力と時間を払う。その上乗せは、コードを書く直前の思考に集中していて、誤りとしては外に出ない。モデルは Sake を「知っている言語で書く」のではなく、毎回「どの型の何という操作か、それはあるか」を確かめてから書いている、と読める。

型を書く利点は、まだ観測できていない。新しく書く題では、落ちた原因は仕様の読み違いで、型は助けなかった。変更の題でも、この規模では直し忘れが起きず、残った誤りは型の外にあった。利点が出るとすれば、次の場面だろう。

  • 変更が離れた箇所まで流れ、書き手が行き先を見落とすほど大きなコード
  • 書き手より弱いモデルが書く場合
  • 人や道具がコードを読む作業

どれも今回の試験の外にある。

言語の側で減らせそうな点は、モデルが書く前に迷う点そのもので、見える誤りから少し拾える。

  • 値へのメソッド呼び出し（Ruby の癖）
  • タプルと配列の区別
  • あるはずと思われる操作（slice）

ただし、これらは 10 試行に 1 回の頻度で、1.5 倍の大部分を説明する量ではない。

限界

  • モデルは Sonnet 5.5 だけ。題は新しく書く 20 と直す 20 で、どれも中規模（40〜150 行）。API ではなくサブエージェントで回したので、温度やトークン計上は細かく揃えていない。
  • Ruby は事前学習で知っている言語なので、この比較は「新しい言語」と「慣れた言語」の比較でもある。
  • 題も変更要求も AI が書いた。仕様の曖昧さは、どの言語にも同じように効いている。
  • 出力トークンは題ごとには分けられない（エージェントが複数の題をまとめて読み書きするため）。エージェント単位で数え、題数で割っている。
  • P4 では Ruby の 2 体が、解答の編集をスクリプトで当てていた。プログラム自体は所定の手段以外で走らせていない。うち 1 体はスクリプトの誤りで 1 試行を無駄にした。

次に測ること

思考の中身を見る。書く前に「使う操作と型、迷った点」を短く書き出させる条件を足して比べる。

取り下げた（P3 の設計時）。書き出させると、測りたい「書く過程」そのものが変わる。代わりに、見える結果だけを数える形にした（結果 4）。

  • 大きいプログラムで直させる。複数ファイル・数百行で、型の変わる値が離れた箇所まで流れる変更。直し忘れが実際に起きる規模で、検査器が指すかを見る。
  • 読む作業で比べる。
    • 実行せずに出力を当てさせる。
    • 誤りを仕込んだコードを渡して、誤っている行を当てさせる。
  • モデルを替える。小さいモデルほど新しい言語の差が出て、検査器の出番も増えるはず。
