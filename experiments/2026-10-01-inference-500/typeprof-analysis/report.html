TypeProf 0.31.1 · Ruby 4.0.2 · rbs 3.10.0 · 2026-10-01/02

TypeProf 500 本の検査結果

型注釈の無い Ruby のプログラム 500 本（どれも正しく動く）に typeprof --show-errors をかけた。結果を出せなかった 49 本は、3 つのバグですべて説明できた。誤報 3,331 件の約 6 割は、数行で再現できるバグか未対応の機能から来ている。どの項目にも最小の再現例を付けた。

要点
451 / 500

完走

120 秒・3 GB の上限で。結果を出せなかった 49 本は、時間切れ 38、メモリ超過 9、内部エラー 2。

45 / 49

1 つのループが原因

引数 2 つのブロックで max_by などを呼ぶと、SplatBox が作り直され続けて止まらない。{"a"=>1}.max_by { |k, v| v } だけで再現する。

3,331

誤報

391 本に出た。全部の本が正しく動くので全部誤報。約 970 件はバグ、約 710 件は未対応の絞り込みや機能、850〜1,000 件は nil に対して保守的という設計どおりのもの。

9.5%

引数が untyped

untyped を含む引数のうち 95% は、実際に実行されたメソッドにあった。module_function と a, b = ary が目立つ原因。

1 · 何をしたか

コーパスと計測

  • コーパス：Sake という別言語の実験のために、AI（Claude）が 20 分野 × 25 課題を書いたもの。各課題に Sake 版と Ruby 版があり、ここで使ったのは Ruby 版（合計 60,493 行、1 本あたりおおむね 60〜250 行）。どれも ruby X.rb で終了コード 0 で走り、Sake 版と同じ出力を出す。
  • 書き方の制約：レコード型は Struct / Data ではなく、attr_reader / attr_accessor と initialize の普通の class で書かせた（TypeProf 0.31 が Struct.new を扱わないため）。それ以外は慣用的な Ruby（ブロック、max_by、a, b = ...、module_function など）。
  • 実行：typeprof --show-errors FILE.rb を 1 本ずつ、timeout 120 とアドレス空間 3 GB の上限で実行。上限を外すと、15 分以上・9 GB 超になるものがあった。
  • 型の決まり具合：完走した 451 本で、引数の 90.5%、返り値の 91.5%、属性の 92.0% は untyped を含まない型に決まった。
2 · 結果を出せなかった 49 本

3 つのバグで全部説明できる

A. 引数 2 つのブロックで SplatBox が作り直され続ける（45 本）

45 本（時間切れ 36 + メモリ超過 9）再現：timeout/repros/r1_max_by_pair.rb、crash/b1_*.rb
終わらない（上限を 600 秒・8 GB に上げても、時間切れかメモリ切れ）
p({"a" => 1, "b" => 2}.max_by { |k, v| v })
[[4, 1]].max_by { |_, c| c }
[[1, 2]].filter_map { |a, b| a }
{"a" => 1}.sort_by { |k, v| v }
終わる
p({"a" => 1, "b" => 2}.max_by { |kv| kv[1] })
[[4, 1]].max_by { |_, c| -c }
[[4, 1]].max_by { |(_, c)| c }
[[4, 1]].group_by { |_, c| c }

起きる条件：(1) 1 つの値を yield するメソッドに、引数 2 つ以上のブロックを渡す（SplatBox ができる）。(2) ブロックが引数をそのまま返す（v、k if v。-v や [-v, k] では起きない）。(3) ブロックの返り値が、RBS の上でクラスの型と照合される（max_by / min_by / sort_by の Comparable | Array[untyped]、filter_map、flat_map、配列の to_h）。ユーザが書いた RBS でも、返り値が Integer なら起き、U や untyped なら起きない（r3_custom_rbs.*）。

仕組み（観測したもの）：ChangeSet#add_splat_box の memo は 1 回の実行の中だけで効き、reinstall が前回の箱を壊す。そのため、呼び出しが再実行されるたびに新しい SplatBox と新しい ret の vertex ができる。数え上げのパッチを入れると、36 本すべてで同じ SplatBox が 10 秒に 256〜31,804 回作り直されていた（完走した本では 0 回）。壊した SplatBox は読んでいた vertex から外されず、GC の後も生きているので、メモリも増え続ける。

ループが閉じる理由（コードを読んだ推定。計装はしていない）：ブロックの返り値をクラスの型と照合することで、その呼び出しが自分の出力を購読する。返り値が Integer を失っては得ることを繰り返し、そのたびに呼び出しが起きる（6 秒で約 19,000 回、SplatBox 約 38,000 個）。

漏れだけを直す（壊すときに外す）実験では増え方は止まったがループは続いた。ループが根本で、漏れだけ直すとメモリ超過が時間切れに変わるだけ。完走した本のうち 58 本にも同じ形のブロックがあり、うち 2 本（n_queens、email_domains）では SplatBox が 1 回しか作られずループが始まらない。その理由はまだ分かっていない。

C. Enumerator[Elem, Return = void] の既定値が埋まらない（2 本）

2 本（triage_partition.rb、access_log.rb）再現：crash/a1_enumerator_default_return.rb
[1].chunk_while { true }.each { }
sig_type.rb:819:in 'TypeProf::Core::AST::SigTyVarNode#covariant_vertex0': unknown type variable: Return (RuntimeError)

chunk_while / slice_when / slice_before / slice_after は RBS で Enumerator[Array[Elem]]（型引数 1 つ）を返す。TypeProf は既定値 Return = void を埋めないので Return が nil に対応し（box.rb:740-744）、Enumerator#each の返り値 Return で落ちる。.map や .to_a では落ちない。コーパスでこれらのメソッドを使う 7 本のうち、結果に .each を呼ぶ 2 本だけが落ちた。

3 · 誤報 3,331 件

原因ごとの件数

メッセージだけでは原因が分からない（nil#+ は、find の結果のことも、絞り込まれない .nil? のことも、多重代入のバグで nil のままの変数のこともある）。そこで、疑う原因ごとに「その原因だけを取り除くスイッチ」（TypeProf への monkey patch か、行と列を保ったソースの書き換え）を作り、累積で V1〜V11 と足していって、各エラーが最初に消えた段に帰属させた。スイッチなしの V0 は元の結果を 391 本すべてで完全に再現する。

原因種類件数本数
  • 自動で分類したのは 79%（反実仮想）＋ 4%（構文の検出）。残り 449 件（13%）は 50 件を無作為に選んで手で分類した（内訳は errors/findings.md）。
  • 自動の分類から 116 件を選んでソースで確かめた：104 件は確認、2 件は妥当だが追えず、8 件は「ライブラリの T?」に入っていたもので不明 6・誤り 2（String#scan）。そのため「ライブラリの T?」の 559 件は上限。
  • スイッチを 1 つずつ単独で試す計測は、時間の都合で 11 個中 5 個まで。済んだ分は累積の数字とほぼ一致した（例：sort_by のキーの漏れは単独で 110、累積で 100）。
4 · 誤報の再現例

バグと思われるもの

RBS の interface を名前で照合している（252 件）

puts 42
p 1, 2
Math.sqrt(2.0)
# (1,0)-(1,4):wrong type of arguments
# (2,0)-(2,1):failed to resolve overloads
# (3,5)-(3,9):wrong type of arguments

SigTyInterfaceNode#typecheck が typecheck_for_module を呼ぶので、_ToS・Math::double・_Each・_Inspect を満たせるのは、組み込みの shim でそれらを include すると宣言してある String・Array・Hash だけになる。誤報の内訳は puts 61、Math.sqrt 35、Math.exp 25、Set#& 22、…

a, b = ary（ary : Array[T]）で配列全体が a に入る（231 件、型の誤り）

def from_call(s)
  a, b = s.split(",")
  a
end
p from_call("x,y")   # => "x"
def from_call: (String) -> Array[String]

推論した型が実行時の型と違う（実際は String）。右辺が Tuple 型（[1, "a"] を返すメソッドや String#partition）なら正しい。MAsgnBox#run0 が Tuple しか扱っていない（"TODO: call to_ary?"）。後続の untyped や誤報の起点にもなる（a, b, km = line.split の後の Edge#a が untyped、など）。

後で代入される外側のローカルと同じ名前のブロック引数が nil になる（204 件）

[1, 2].each { |v| p v + 1 }
v = "done"
# (1,22)-(1,23):undefined method: nil#+

当てはまる overload の返り値を全部 union する（137 件）

r = 2026 % 100
p r / 4
# undefined method: Numeric#/

Integer#% の最後の overload が (Numeric) -> Numeric。resolve_overloads は当てはまる overload 全部の返り値を足すが、RBS の意味では最初に当てはまったものが選ばれる。

sort_by / min_by / max_by の配列のキーの型が、要素の型に漏れる（100 件）

pts = [Pt.new(1, 2), Pt.new(0, 5)]
p pts.sort_by { |pt| [pt.x, pt.y] }.first.x
# undefined method: Integer#x   （3 件）

GlobalEnv#get_instance_type を通る 2 つの検索（Enumerable で sort_by を探すときと、ブロックの値を Comparable | Array[untyped] と照合するとき）が、Array の include Enumerable[Elem] の同じ RBS の節点 Elem を具体化する。ChangeSet#new_covariant_vertex が RBS の節点ごとにしか vertex を memo しないので、両者が 1 つの vertex を共有し、キーの要素の型が Elem に流れ込む。受け手の型引数ごとに memo するパッチで消える。

その他のバグ

  • 入れ子の分解の引数（47 件以上）：def sum_pair((a, b)) = a + b、{ |(x, y), i| ... } で nil#+。
  • トップレベルの自己呼び出し：distance(3, 1) が、無関係な class の attr_reader :distance に解決される（wrong number of arguments (2 for 0)）。
  • &:sym のブロックへの yield が Symbol#call を呼ぶ扱いになる。

5 · untyped はどこから来るか

実行されたメソッドなのに untyped

500 本を TracePoint 付きで実行し、どのメソッドが実際に呼ばれたかを記録して、TypeProf の結果と突き合わせた。

単位数untyped を含む呼ばれなかったメソッド呼ばれたメソッド
引数4,51642822406
返り値3,5503015296
attr2,2991840184

確かめた原因は 3 つ。module_function（913 個の untyped のうち 85 個、11 本）、a, b = ary（上のバグ。下流の untyped の起点）、map(&:sym)（要素が untyped になる）。

module M
  module_function
  def twice(x) = x * 2
end
module N
  def self.twice(x) = x * 2
end
p M.twice(3), N.twice(3)
module M
  def twice: (untyped) -> untyped
end
module N
  def self.twice: (Integer) -> Integer
end

残りの untyped の大半は、原因をまだ追っていない（サンプルは untyped/report.md）。

6 · 直したときの効果の見込み

効果の大きい順

  1. SplatBox のループ（A）：完走できない 49 本のうち 45 本。反実仮想の計測でも 13 本が途中で止まっていて、同じ原因と思われる（未確認）。
  2. .nil? / == nil での絞り込み：誤報 425 件。
  3. interface の照合：誤報 252 件（puts 42 という最も普通の行で出る）。
  4. 多重代入：誤報 231 件。加えて型の誤りと untyped の起点。
  5. ブロック引数の名前の衝突：誤報 204 件。
  6. overload の union：137 件。module_function：誤報 119 件と untyped 85 個。
注意
  • コーパスは 1 種類の AI が書いたもので、人の書いたコードとは傾向が違いうる（たとえばブロックの引数 2 つの max_by を多用している）。件数はこのコーパスでの頻度。
  • マシンは共有で負荷が高かった（load average 3〜45）。時間の数字は負荷の低いときの CPU 時間を使った。
  • パッチはすべて原因を確かめるための診断用で、修正案ではない。TypeProf の gem とコーパスは変更していない。
材料はすべて Sake-lang リポジトリの experiments/2026-10-01-inference-500/ にある。コーパスは corpus/*/*.rb、TypeProf の結果は results-head/typeprof.jsonl.gz。
