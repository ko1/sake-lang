# ぱっと見の見やすさ: Ruby と Sake（2026-10-14、準備）

ko1 の仮説: AI が書いたコードのレビューは流し読み（ザッピング）が中心になる。そうなると効くのは、精読したときの分かりやすさより「ぱっと見て見やすいか」。これを人に答えてもらうページを作った。

## 方法

- 題: 12 問。どれも 2〜4 行のコードで、Ruby 版と Sake 版がある。
  - 仕様どおりか（R1〜R6）: 仕様の 1 文とコードを見て「仕様どおり / 誤りがある」を選ぶ。誤りは R1（`<=` と `<`）、R2（整数の割り算）、R4（古い順の先頭 3 件）の 3 つで、どれも型の検査を通る論理の誤り（ko1: 誤りは型検査が通る前提）。
  - 何をするか（G1〜G6）: 4 択（表示のたびに並べ替える）。
- 1 人は各題を一方の言語でだけ見る。参加者を無作為に 2 群に分け、題の番号の偶奇で言語を入れ替える（各人 Ruby 6 問、Sake 6 問）。題の順も無作為。
- 測るもの: 正答、答えるまでの時間（コードを表示してから選ぶまで）、答えたあとの「ぱっと見の見やすさ」（1〜5）。
- 最後に R3・R5・G2・G6 を 2 つの書き方で左右に並べ（左右は無作為）、どちらがぱっと見て見やすいかを 5 段階で選ぶ。
- 背景: Ruby の経験、Sake を見たことがあるか。

## コード

- `check/all.rb` と `check/all.sake` が、走らせて確かめたプログラム（データの準備と出力を含む）。両者の出力は一致する（`diff <(ruby check/all.rb) <(bin/sake check/all.sake)`）。Sake 版は既定の検査（レベル 1）を通る。`--strict=2` では G6 の `Array.zip` の nil で止まる（Ruby 版も同じ値になりうる）。
- ページに出すコードは、`build.rb` がこの 2 つから準備と出力の行を除いて取り出す。`items.json` は仕様の文、誤りの有無、選択肢（先頭が正解）。`template.html` → `glance.html`。
- Sake 版は、Ruby がメソッドの連鎖で書くところは、最初を `T.op(x)` にして後を連鎖にした（`Array.select(xs) { }.Array.map { }`、ko1）。v1 は `xs.Array.select { }.Array.map { }` の形だったが、ko1 が「x.T.op は読みづらい」として v2 で直した（回答が入る前）。そうでないところは `Array.tally(words)` の形。演算子（`*`、`/`、`<=`）は両方同じ。

## 記録

- 回答は artifact の db に 1 人 1 文書（`responses/<viewer id>`）で保存する。読めるのは作成者（ko1）だけ（rules: `responses` は owner のみ、`responses/{self}` は本人が書ける）。
- **db に書けるのは、ko1 の組織のメンバーで、Contributor 以上の権限がある人だけ。** 組織の外の人（公開リンクで来た人を含む）は書けない。その場合、ページは回答を JSON の文字列で表示し、送ってもらうよう頼む。
- 作成者がページを開くと「集計を見る」で、言語 × 題の種類ごとの正答率・時間の中央値・見やすさの平均と、並べた比較の平均（Sake 寄り +）が出る。

## 限界（投入前に分かっているもの）

- 参加者は Ruby に慣れていて、Sake は初見。見やすさの評価は慣れに強く引きずられる。
- 題が短い（2〜4 行）。流し読みの対象としては現実より小さい。
- Sake の導入の説明を読んでから答えるが、Ruby には説明がない。

## AI に答えさせた pilot（2026-10-14、ko1:「問題、AI に答えさせたら何か優位な差は出るだろうか」）

人の調査の前に、同じ 12 問を AI に答えさせた。人の仮説（流し読み）を検証するものではなく、AI がレビュアーのときに差が出るかを見る。

- 方法: `ai/run.rb MODEL N OUT`。`claude -p --tools "" --strict-mcp-config`、system prompt は「あなたはコードレビュアーです。質問に簡潔に答えてください。」。問題文・仕様・選択肢はページと同じ（選択肢は回ごとに並べ替え）、「型の誤りは入っていない」の注意も同じ。条件は Ruby / Sake / Sake＋ページの入門 3 行。各条件 × 12 問 × 10 回、並列 8。
- 通常版: 「最後の行に OK か BUG（A〜D）だけを書いてください」。理由を書くかは任せる。
- 答えだけ版（`GLANCE=1`）: 「説明は書かず、OK か BUG（A〜D）だけを答えてください」。人のぱっと見に近づける試み。ただし Haiku の表に出ない思考は止められなかった（`MAX_THINKING_TOKENS=0`、`alwaysThinkingEnabled:false` でも `thinking_tokens` が出る）。そこで思考トークン数（`think_tokens`）を記録した。
- 集計: `ai/summary.rb`（`CONDS=` で条件名）。

### 結果（正答数 / 回数、出力トークンの平均）

| | Ruby | Sake | Sake＋入門 |
|---|---|---|---|
| Sonnet 仕様どおりか | 59/60 (111t) | 60/60 (139t) | 60/60 (128t) |
| Sonnet 何をするか | 60/60 (116t) | 60/60 (133t) | 60/60 (114t) |
| Haiku 仕様どおりか | 56/60 (464t) | 60/60 (724t) | 59/60 (751t) |
| Haiku 何をするか | 56/60 (103t) | 60/60 (265t) | 60/60 (223t) |
| Haiku 答えだけ・仕様どおりか | 47/59 (298t) | 60/60 (507t) | 60/60 (537t) |
| Haiku 答えだけ・何をするか | 43/60 (9t) | 57/60 (93t) | 58/60 (108t) |

- Sonnet は両言語とも天井で、差は無い。
- Haiku は **Ruby のほうが悪い**。答えだけ版では大きく、Ruby 対 Sake の Fisher の正確検定で p = 0.001（何をするか）、p = 0.0001（仕様どおりか）。通常版の「何をするか」の 56/60 対 60/60 は p = 0.12 で、有意ではない。
- **差の正体は読む手間の量で、見やすさではない。** 答えだけ版の「何をするか」で、思考トークンが 0 だった回は Ruby で 54/60、Sake で 15/60、Sake＋入門で 5/60。Ruby の誤答はほぼすべて思考 0 の回にある（思考 0 の Ruby の正答は 37/54）。通常版でも、Ruby の「何をするか」の 25/60 回は理由を書かずに記号だけ答え、誤答 4 件はすべてその中にある（Sake は 1/120 回）。知らない書き方だと Haiku は考えてから答え、知っている Ruby は即答して外す。
- 仕様どおりかの誤りの多くは R6（Ruby 答えだけ版で 7/10 が BUG）: 整数除算 `* 9 / 10` の切り捨てを誤りとした。仕様に丸め方を書いていない、題の作りの穴。R3（ソートの安定性）、R5 の誤検出も Ruby 版だけで出た。

### 計測の訂正

- 最初の採点は最後の行から答えを拾っていた。Sonnet が末尾に MCP の認証についての注意を付けた 2 回（どちらも Ruby）で「MCP」の C を答えとして拾い、誤答に数えていた。答えだけの行を探すように直し（`answer_line`）、`--strict-mcp-config` を足し、保存した本文から全回答を採点し直した（`ai/rescore.rb`。変わったのはその 2 回だけ）。上の表は直した後のもの。
- 答えだけ版の Haiku は 1 回、答えの行が無い応答で runner が止まり、359 回になった。

### 読み

- AI がレビュアーなら、Sake で差が出るのは弱いモデルが手を抜く場面だけで、向きは Sake が有利。理由は見やすさではなく、見慣れない書き方が精読を誘うこと。強いモデルでは差が無い。
- 人の流し読みでも同じことが起きるかは分からない。起きるなら、人の調査では Sake の時間が長く、正答率が高く出るはずで、ページの時間の記録で区別できる。

## 型を引き継ぐ連鎖の版（2026-10-17）

ko1 が「`T.op(x).T.op.T.op` はやっぱりわかりづらいと言われた」（理由は、T が多いことと、x.y.z に慣れていること）。そこで、連鎖の型を省いた段が最後に名乗った型を引き継ぐ規則を入れた（DESIGN.md「型を省いた段は、連鎖が最後に名乗った型を引き継ぐ」）。

- `check/all.inherit.sake` は、`check/all.sake` の連鎖をこの形にしたもの（7 か所）。出力は Ruby 版と同じ（`diff <(ruby check/all.rb) <(bin/sake check/all.inherit.sake)`）。型が変わる段（R3 の `.Hash.transform_values` と `.Array.each`、R6 の `Cart.items(cart).Array.sum`）は名乗ったまま。
- ページを v3 としてこの形に差し替えた（2026-10-17、回答 0 件の時点。ko1 の了承）。`build.rb` は `check/all.inherit.sake` から取る。導入の対応表にも 1 行足した（`xs.group_by { }.keys` → `Array.group_by(xs) { }.Hash.keys`、型が変わる段だけ書き直す、の説明付き）。v2 の形は `check/all.sake` に残す。
