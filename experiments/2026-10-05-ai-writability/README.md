| 段階 | 作業 | 節 |
|---|---|---|
| P1 | 新しく書く（パイロット、20 題 × 2 言語 × 一発/試せる） | パイロット P1 |
| P2 | 新しく書く（反復、1 体の題数、チートシート、思考の配分） | P2 |
| P3 | 新しく書く（見える結果だけで測る: 検査の停止、存在しない API） | P3 |
| P4 | 既存のコードを変える（型や形が変わる変更要求 20） | P4 |
| P5 | 読む（出力の予測 20、1 行の誤りの修正 20） | P5 |

まとめ: 評価ページ（artifact）`sake-ai-evaluation.html` → https://claude.ai/artifact/NaxNc5iropLucuvhawKETD（P6 まで反映）

### 量と単位（この README と評価ページで共通）

- **出力トークン**: モデルが生成したトークンの数。思考（量だけが記録に残る）、本文、道具への入力（書いたコード、コマンド）を含む。Claude Code の記録の各呼び出しの `output_tokens` を、エージェント 1 体の全呼び出しで足したもの（`harness/usage.rb`）。「/題」は担当した題の数で割った値、「/体」はエージェント 1 体の合計。k は 1,000 トークン。
- **作業時間**: エージェント 1 体の記録の最初から最後までの壁時計時間。道具の実行と、Sake の検査・テストの実行を待つ時間を含む。
- **検査時間**: `bin/sake --strict=2 -c` を 1 回走らせて終わるまでの時間。
- **最終文脈長**: 1 体の最後の呼び出しの入力と出力のトークン数の和（読んだ資料・仕様・コードとやりとりをすべて含む）。出力トークンとは別の量。
- **X 倍**: 断りがなければ、同じ作業・同じ条件での「Sake の値 ÷ Ruby の値」。
- **上乗せ**: Sake の出力トークンが Ruby より多い分。
- **思考トークン**: 呼び出しごとの「出力トークン − 見えている出力のトークン」。見えている出力は Claude 2 世代のトークナイザで数えた近似。

## 1. 何を測るか

「AI が Sake を書きやすいか」を、Ruby を基準にした相対値で、次の 4 つの問いに分ける。

| 問い | 主指標 |
|---|---|
| Q1 書けるか | 正答率（隠しテストに通る割合） |
| Q2 どれだけかかるか | 正答までのトークン数（入力・出力別）、実行回数、壁時計時間 |
| Q3 どこで間違い、誰が捕まえるか | 誤りの段階別分類、静的検出率 |
| Q4 道具が効くか | エラーメッセージ・ヒントごとの「次の試行で直った率」、ヒントを消したときの差 |

これまでの指標との関係: 2026-10-05-review の「AI トークン 1.07–1.12×」は、正しいプログラムを**書き写す**量の比にすぎない。ここでは、仕様から正しいプログラムに**たどり着く**までを測る。

## 2. 課題セット（4 層）

| 層 | 内容 | 数 | 採点 | 狙い |
|---|---|---|---|---|
| A 関数 | MultiPL-E の Ruby 版 HumanEval/MBPP を Sake 用に変換（シグネチャ・docstring・テスト呼び出し） | 約 560 | 呼び出しごとの `p(f(args))` 出力を、Ruby の参照解の出力と比較 | 外部の基準と比べられる。単純な関数での型の書きやすさ |
| B プログラム | 新規に書き下ろす。20 ドメイン × 3 題（クラス、nil、Hash、例外、パーサ、状態機械など）。仕様は I/O を厳密に書き、公開例 2 つと隠しテスト 10 個以上（stdin → stdout）を付ける | 60 | 隠しテストの完全一致 | Sake らしさ（型を操作に書く、フィールド、nil 検査）が効く規模 |
| C 改変 | 既存の sakelib（39 本）への機能追加・バグ修正 | 20 | 追加テストと既存テストの両方が Ruby と一致 | 読む書きやすさ。他人のコードの型に合わせられるか |
| D 翻訳 | corpus-v3 の `.rb` を渡して Sake に訳させる | 500（パイロットは 50） | `.out` と完全一致 | すぐ使える。Ruby からの移行コスト（ただし難度は最も低い） |

- **B を本命にする**: A は Ruby 側が事前学習で答えを覚えている恐れがある。D は Ruby の解が渡されるので易しすぎる。
- B は公開しない（held-out）。A は汚染の参考値として扱う。

## 3. 条件

| 因子 | 水準 | 備考 |
|---|---|---|
| 言語 | Sake / Ruby | 同じ課題、同じ道具、同じプロンプト雛形（言語名と資料だけ差し替え） |
| モード | 一発（道具なし） / エージェント（実行してよい、最大 8 回） | 一発は「知識だけで書けるか」、エージェントは「エラーから直せるか」 |
| Sake の strict | 0 / 1 / 2 | エージェントモードで、実行前の検査の強さが試行回数と誤答をどう動かすか |
| 資料 | guide のみ / spec+builtins / guide+few-shot 3 例 | 資料のトークンは固定費として別に数える |
| モデル | Sonnet 5.5（主） / Opus 5.5・Haiku 4.5（部分集合） | 小さいモデルほど新言語に弱いはず |
| 反復 | 1 セル 5 回 | 平均とブートストラップ 95% 区間で報告する。単発の結果は主張しない |

全組み合わせは大きすぎる。主グリッドは「B × {Sake, Ruby} × 2 モード × Sonnet × 5 回」とし、残りは第 7 節のアブレーションで足す。

## 4. 記録と派生指標

1 試行ごとに JSONL 1 行で記録する。項目は、課題、条件、反復番号、試行番号、コード、検査の診断（項目・行・ヒント）、実行結果、隠しテストの結果、トークン（入力・出力・キャッシュ）、所要時間。

派生指標:
- **正答率**: 一発の pass@1 と、エージェントの予算内解決率。
- **正答までのコスト**: トークン数の中央値と、実行回数。
- **誤りの段階**: 失敗した試行を最初に止めた段階で分類する。
  - 段階: 構文 / 名前・引数（レベル 0）/ type（1）/ nil・mixed（2）/ 実行時例外 / 出力違い / タイムアウト
- **静的検出率**: 誤った試行のうち、実行前の検査で止まった割合。Sake の主張そのものなので、検査レベル別に出す。
  - 対照: 同じ誤答を `--strict=0` で走らせて、実行時に初めて出るか確認する。
- **見逃し**: 検査を通って出力違いになった割合（型では捕まらない誤り）。
- **誤報の負担**: 検査に止められたが、`--strict=0` なら隠しテストに通っていた試行。
  - 書き手が無駄に回った回数として数える。
  - 2026-10-05-review の「レベル 1 誤報 38 本」を、書き手側から見た数字になる。
- **メッセージ修復率**: 診断（項目とヒントの種類）ごとに、次の試行でその箇所の診断が消えた割合。
  - 消え方は「直した」と「迂回した（コードを消したなど）」に分ける。後者は差分で判定する。
- **Ruby 癖率**: 試行あたりの「値へのメソッド呼び出し」「Proc の保持」など、Ruby の書き方を持ち込んだことを示す resolver エラーの数。試行番号が進むと減るか（学習曲線）も見る。

## 5. 統制と妥当性（測定を疑うための仕掛け）

- **正の対照**: 各課題の参照解（Sake と Ruby）が採点系で満点になること。
- **負の対照**: 参照解の変異版（境界値を 1 ずらす、nil 検査を消すなど）が落ちること。
- これらを流してから本番を投入する。
- **難度の較正**: Ruby 条件の正答率が極端（ほぼ 0 またはほぼ 100%）な課題は分析から外すか、別に報告する。
- **時間制限**: Sake インタプリタは遅いので、時間制限は言語別に「参照解の実行時間 × 10、最低 5 秒」とする。タイムアウトは独立の段階として数える。
- **資料の非対称**: Sake は資料が要り、Ruby は要らない。資料のトークンは固定費として分けて報告する。比較の主軸は「固定費を除いた正答までのコスト」と「正答率」。
- **汚染**: A の Ruby 側は記憶の可能性がある。B は新規・非公開。結論は B で出す。
- **処理系の固定**: Sake の commit を固定する。途中で lib を変えた場合はセルを分ける。
- **モデルの固定**: モデル ID と温度（既定値）を記録する。
- **共有環境**: 実行は sp3/sp4 ではなくローカルの隔離コンテナで行う（性能計測ではないため）。並列数の上限と多重起動の拒否は runner 側で持つ。

## 6. 実行系

- runner（Ruby）が API を直接呼ぶ。エージェントモードの道具は「ファイルを書く」と「`bin/sake --strict=N` / `ruby` で実行して出力を見る」の 2 つだけ。
  - Claude Code のサブエージェントでも回せるが、温度・道具・トークン計上の統制が弱い。本番は API にする。
- 採点は隠しテストを runner 側で流す。モデルには見せない。
- 出力先: `results-<日付>-<条件>/attempts.jsonl` と `summary.md`。失敗例のギャラリーは artifact にする。

## 7. 段階と費用の見積もり

| 段階 | 内容 | 規模 |
|---|---|---|
| P0 採点系 | 正・負の対照、B の 10 題 | モデル呼び出しなし |
| P1 パイロット | D 50 本 + B 10 題 × {Sake, Ruby} × 2 モード × Sonnet × 3 回 | 約 700 試行 |
| P2 本番 | B 60 題の主グリッド | 1,200 試行 |
| P3 アブレーション | (a) ヒントを消す（CLI の hint 行を落とす）→ ヒントの因果効果。(b) メッセージを「行番号だけ」にする。(c) strict 0/1/2。(d) 資料 3 水準。(e) Opus/Haiku を B 20 題で | 各 200〜600 試行 |
| P4 外部比較 | A（MultiPL-E 変換） | 560 題 × 2 言語 × 1 回 |

トークンは、エージェント 1 試行あたり 2〜5 万（資料込み、キャッシュが効く）と見て、P1 で実測してから P2 以降を決める。

## 8. 決めてほしいこと

1. API を直接使ってよいか（キーと予算）。だめなら Claude Code のサブエージェントで P1 まで進め、統制の弱さを明記する。
2. 外部データの取得（A 層の MultiPL-E。HumanEval は MIT、MBPP は CC-BY）。取得は外部へのアクセスになる。
3. B 層 60 題を誰が書くか。AI に書かせる場合、仕様と隠しテストを書く者と、解く者を分ける（同じ会話にしない）。参照解は Sake と Ruby の両方で採点系を通す。

# パイロット P1（2026-10-06 実施）

## 方法

- お金をかけないため、API ではなく Claude Code のサブエージェント（Sonnet 5.5）で回した。温度・トークン計上の統制は API より弱い（トークンはエージェント 1 体分の合計しか取れない）。
- 題: 新規 20 題（b01–b20）。エージェント 2 体が `brief-tasks.md` に従って作成した（解く側とは別の会話）。各題は仕様、公開例 2、隠しテスト 12〜19、参照解（Sake・Ruby）からなる。
  - `harness/validate.rb` で、参照解が全件通ること（Sake は `--strict=2`）と、1 演算子の変異を隠しテストが殺すことを独立に確認した（`validate-b11-b20.jsonl` ほか。殺した率 10/12〜12/12）。
- 解く側: 1 体あたり 1 言語 × 1 モード × 5 題で、計 16 体（20 題 × {Sake, Ruby} × {一発, 実行あり} × 各 1 回）。指示は `brief-solve.md`、`mode-*.txt`、`lang-sake.txt`（`prompts/` に実物）。
  - Sake 側が読める資料は tutorial・spec・builtins だけ。Ruby 側は資料なし。
  - 実行ありの条件では `harness/try.rb` だけが実行手段（最大 8 回）。毎回、版と診断と公開例の結果を記録する。
- 採点: `harness/grade.rb`。隠しテストの完全一致、Sake は `--strict=1`。検査を外した `--strict=0` の結果と、1 件ごとの壁時計時間も取る。
- 処理系: 0ac75e7（パイロット中は lib を変えない）。マシンは共有のローカル機。
- 反復は 1 回なので、差は雑音と区別できない（下の結論はその前提で読む）。

  - 1 回ずつの比較で、差は雑音の範囲。
- **コストは Sake が約 2〜2.5 倍**（トークン、時間とも）。資料（tutorial・spec・builtins）を読む固定費を含み、1 体 5 題で割ると題あたり約 2 倍。

  - Rational と nil/String の演算（正しい指摘）
  - b13 で 3 回続けて、配列を含む Tuple の `<`（下記）
  - `m.to_f`（値へのメソッド呼び出し。Ruby の癖）

  - 例外は b13 の Sake 解。探索が重く、1 件最大 6 秒（Ruby は 0.1 秒未満）。
- **写しの確認**: 解答と参照解の一致行の割合は最大 0.23、平均で Sake 0.10・Ruby 0.15。写した形跡はない。

## ねらい

P4・P5 は題が小さく（40〜150 行）、正答率が天井に張り付いた。数十ファイル・1 万行規模では、全体を一度に読めないので、「探して、全部の箇所に行き届かせる」が試験に入る。

Sake に固有の仮説:
- 操作が型付きで書かれる（`Account.balance(a)`）ので、grep で型ごとの呼び出し元が正確に見つかるはず。Ruby の `.balance` では、どの型のものか区別できない。
- 型を変えると、別ファイルの呼び出し元を検査器が指すはず。

この 2 つが効くなら、次の数字に差が出るはず:
- 直し忘れの数
- ファイルを開いた回数・grep の回数
- 読んだ量（入力トークン）
- 正答率

いきなり 1 万行ではなく、まず 3,000 行・10 ファイル程度で、次の 3 点を確かめる。
- 天井が外れるか
- 両言語で同じ振る舞いだと保証できるか
- 1 回あたりの費用はどれくらいか

## 題材: Mini インタプリタ（`large/mini/`）

  - Ruby 版にも「Sake に移せること」という制約がかかっている。

## 移植の知見（Ruby → Sake）

移植そのものは評価の対象ではないが、Ruby のコードを Sake に移すときに何が起きるかの記録として貯める。移植エージェントの報告と、移植版の中身を見て分かったことをここに書く。

### 結果（2026-10-06）

- 移植版（`large/mini/sake/`）: 14 ファイル・2,571 行（Ruby 2,540 行の 1.01 倍）。
  - ファイルごとの行数もほぼ同じ（parser 551→559、interpreter 372→376、resolver 292→301 など）。
  - `--strict=2 -c` に通り、全 298 テストで Ruby と同じ出力を出す（自分で確認、1 分 46 秒）。`--tokens`/`--ast` の出力も Ruby と一致した（移植エージェントの報告）。
- 1 対 1 に移せなかった箇所（移植エージェントの報告）:
  - 名前: 構文木の型 `Index` は Sake の予約名なので `IndexExpr` にした。
  - 定数: `once` を使う関数にした。`ARITY` は名前が衝突するので `arity_table`。
  - 例外の型: `message` を最初のフィールドにする必要があり、引数の順を入れ替えた。
  - `private` がない。
  - 配列のパターン（`case args in [...]`）がないので if/elsif にした。
  - `case/in` は、Ruby なら素通りする場合にも `else nil` を書いた。
  - `value.class` は `Kernel.inspect` で代えた。
  - 値へのメソッド呼び出しは、`Array.last` → `xs[-1]`、添字 → `Array.fetch` のように書き換えた。
  - 型の組ごとに分岐を分けた（`Operators.add`・`compare`）。
- `--strict=2` に通すための絞り込み（`x => T` やフィールドのローカル変数への写し）が要った。エージェントの申告では 18 行。`=> 大文字` の出現を数えると 26 か所。
- **検査時間が書き方で大きく変わる**（空いたマシンで 3 回ずつ）:
  - 移植版 24.0〜24.2 秒、スクラッチ版 3.2 秒。行数はほぼ同じで 7.5 倍の差。

## 仕様の検証で直したこと（2026-10-08）

- テスト作成 6 体と参照実装 6 体が、仕様と SQLite の食い違いを合わせて約 60 件記録した（`large/sql/spec-issues/`）。大半は「テストはその点を使わない」と書き足すか、SQLite の挙動を仕様に書き足して直した。例:
  - ORDER BY 範囲外エラーの「1st」は項の位置で、書いた数ではない（最初の版は誤っていた）。
  - 集約だけを HAVING や ORDER BY に置いても集約問合せにならない。`sum('3')` は INTEGER。
  - 制約の検査順（INTEGER PRIMARY KEY の値 → NOT NULL → その一意性 → 型の変換 → 他の一意性を後ろから）。
  - `x IN (...)` は x の affinity だけ、`x IN (SELECT ...)` は両側の affinity。
  - 複数列のサブクエリを比較に置くと `row value misused`。
- テストを直したもの: 予約語を列名に使っていた 5 本、オラクルのコメント除去の誤り 1 本（`/* -- */`）、仕様が「どの行でもよい」とする値を当てにしていた 1 本、1 文に 2 つの誤り 1 本、仕様と食い違う 1 文 1 本。
- 本計測は段階 N の参照実装が通ってから段階 N を流した。段階 1 の作り手は、段階 2 以降の検証で直した段階 1 の文言（空白の扱いなど）の前の版を読んでいる。隠しテストはどの採点でも最終版を使った。

## Sake の不具合: 互いに呼び合う関数の `Array + Array` で検査器が止まらない（P10 で発見、未修正）

- Sake-1 の段階 4 で、検査器が `stack level too deep` で落ちた。エージェントは `a + b` を `Array.concat(Array.dup(a), b)` に書き換えて回避し、37 分かかった（他の段階の 2〜7 倍）。
- 最小の再現（別のエージェントが切り出し、トレースで原因を確認）:
  ```ruby
  def f(n, row) = n == 0 ? row : g(n - 1, row + Array[n])
  def g(n, row) = f(n, row + Array[n])
  puts Array.size(f(3, Array[]))
  ```
  `-c`（既定の段階 1）でも素の実行でも落ちる（bin/sake の 256MB スタックでは 15 分以上終わらない）。`--strict=0` は検査を飛ばすので通る。
- 原因: `typer.rb` の `call_user` は `[関数, 引数の型]` で結果を覚えるが、`row + Array[n]` は呼び出しの文脈ごとに新しい配列の生成箇所 ID を持つ型になり、キーが二度と一致しない。P6 の検査の打ち切りと同じ種類の、型の計算が収束しない不具合。
