仕様変更のあと、全部のコードを書き直してみた

500 本のコーパスと sakelib を、この 3 日の仕様変更（attr_reader、initialize、once、キーワード引数、x => T …）で見直し、Ruby とどれだけ同じ形になったか、型を書かずに型がどれだけ決まるかを測った。

何をしたか

  • 2026-10-01 のコーパス（各課題に Sake 版・慣用的な Ruby 版・期待出力）を写し、5 体の書き手エージェントが 4 分野ずつ見直した。基準は Ruby 版：新しい機能で Ruby の書き方に近づく所だけ直す。
  • 見直しは --strict=0（型の検査なし）で行い、検査の結果は見せていない。検査器に合わせたコードにしないため。
  • sakelib（18 ライブラリ）と 2026-10-03 のライブラリ実験は別の 1 体が見直した（こちらは検査を見てよい）。
  • v2（見直し前）と v3（見直し後）を同じ処理系で測った：出力の一致、strict の各レベルの報告、型の分類、健全性（負の対照つき）、Ruby 版との大きさと型名の数。

使われたのは「Ruby 版に対応するものがある」機能だけだった。コーパスの Ruby 版は 1 本 40〜250 行の慣用的なスクリプトで、キーワード引数や型の検査や継承をほとんど使わない。このコーパスは、それらの機能を評価する材料にならない。それらは sakelib の見直しで使われた（Date の initialize での検査、Logger の段階の変換、class SHA384 < SHA512 など）。

見直した 5 体が「Ruby の人が最初に気づく違い」として全員挙げたのは同じ点だった：node.left が Node.get_left(node) になる。宣言は Ruby と同じ形になったが、使う側は変わらない。属性を読む連鎖が多い木やリストのプログラムでは、本体が 2〜3 倍に伸びる。

その次に挙がった違い：インスタンスが明示の第 1 引数になる（def +(a, b)）、クラスメソッドとインスタンスの関数の見分けがつかない、Array[…]／Hash[…]（[] は Tuple、{} は Record）、case/when が無い、&:sym と列挙子の連鎖が無い。

v3 で新しく level 2 に止まった 11 本のうち 5 本は、2 つの値の大きい方を Array.max(Array[a, b]) と書いたもの（Ruby の [a, b].max の直訳）。空かもしれない Array の max は nil | T になる。2 値の max/min が組み込みに無いことが、nil の誤報を生んでいる。残りは = nil で宣言したフィールドを initialize から呼ぶ関数で埋めたもの 2 本、新しい組み込みが nil | T を返すもの 3 本。逆に 3 本は止まらなくなった。

見直しで見つかった処理系の問題

  • initialize の健全性の穴（sakelib の見直しで 2 か所から報告）。@h = A.new unless @h のように一部の経路だけで書くと、new が入れた値が型から消えていた（URI.scheme が nil にならない）。フィールドを局所変数と同じく経路ごとに追い、全部の出口を合わせるように直した。インスタンスを関数に渡した後の扱いも安全側に直した。
  • @x ||= Hash[] が nil | Hash のまま。|| の右を飛ばす経路を絞り込んでいなかった。v2 の結果は変わらない。
  • 計測スクリプトが省略された引数で落ちた。直して README に記録した。

結論

  1. 宣言は Ruby の形になった。使う側は変わらず、Ruby の人に一番目立つ違い（Node.get_left(node)）はそこに残る。
  2. 型を書かずに、型は 99% 以上決まる。1 つに決まらないものの大部分は、数の多相や構文木のように和が正しい答えのもの。書き直しはこの数字をほとんど動かさない。
  3. 誤報の主因は nil で、増えた分の半分は組み込みの品揃え（2 値の max/min）で減らせる。
  4. キーワード引数・x => T・class B < A などは、このコーパスでは試されていない。それらを使う Ruby のコードを材料にした別のコーパスが要る。
