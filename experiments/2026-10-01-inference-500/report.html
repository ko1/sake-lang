Sake 型推論 500 本

型を一切書かない Sake のプログラム 500 本に、操作に書いた型だけからの推論がどこまで届くかを測った。同じ課題を Ruby で書いたものに対する TypeProf とも比べた。

結論：ほぼ全部（99% 以上）の式と関数の型が決まり、8 割は 1 つの型に決まる。TypeProf より決まり具合は高い。ただし、そこに至るまでに推論器の健全性の穴を 7 つ見つけて直した。また、実行前の検査をそのまま使うと、正しいプログラムの 36% を止めていた（8 節の決定を入れた後は 22%、誤報を 1 件ずつ解析して推論器の誤りを直した後は 12%。10 節）。

要点
99.5%

型が決まった

変数の読み・呼び出しの結果・関数の引数・返り値・フィールドのどれも、99% 以上で unknown を含まない型になった。うち約 8 割は単一の型。

99.9 vs 90.5

TypeProf との比較（引数）

同じ課題の Ruby 版を TypeProf にかけると、引数の型が決まったのは 90.5%。TypeProf は 500 本のうち 49 本で、時間かメモリの上限に達して結果を出せなかった。

585 → 0

健全性の違反

実行時の型を推論した型と突き合わせると、元の推論器は 585 件の取りこぼしがあった。7 つの穴を直して 0 件。壊した推論器では 1,734 件出るので、確認の仕組みは働いている。

180 → 58 / 500

正しいのに止められた

実行前の検査（strict level 1）で止められた正しいプログラム。最大の原因は、Symbol の値に対する case/in に else が無いこと（112 件）。決定を入れた後は 108 本（8 節）、推論器の誤り 6 つを直した後は 58 本（10 節）。

1 · 何を測ったか

500 本のプログラムと、型の分類

20 の分野（文字列処理、Hash の集計、数論、浮動小数の数値計算、整列と探索、連結構造、木、グラフ、動的計画法、盤面とパズル、状態を持つシミュレーション、パーサ、多相と演算子、例外と検証、データの集計、日付、符号化、集合と範囲、状態機械、業務アプリ）× 25 課題。書き手は分野ごとに 1 体の AI で、Sake の文書だけを読み、同じ課題を Sake と Ruby の両方で書いた。両方の出力が 1 バイトも違わないことを確かめてある。合計で Sake 56,376 行、Ruby 60,493 行。

書き手には実行前の型検査を切った --strict=0 で動かさせた。推論器の出力を見て書き直すと、測りたいものに合わせたコーパスになってしまうため。

推論した型は、悪い方から次のように分類した。「決まった」は、unknown をどこにも含まないもの（mono・nilable・union）を指す。

3 · TypeProf との比較

Ruby 版に TypeProf をかけると

TypeProf 0.31.1 は、注釈なしの Ruby から各メソッドのシグネチャを推論する。TypeProf が完走した 451 本に絞って、同じプログラムどうしで比べた。

Sake：monoSake：nilable・unionTypeProf：monoTypeProf：nilable・union
0%50%100%
  • 49 本は TypeProf が結果を出せなかった（120 秒で打ち切り 38、メモリ 3 GB 超 9、内部エラー 2）。上限を外すと 15 分以上・9 GB 超になるものがあった。これらを除いているので、比較は TypeProf に有利な選び方。
  • TypeProf は 391 本で 3,331 件のエラーを報告した。プログラムはすべて正しく動くので全部誤報。上位は wrong type of arguments（403）、failed to resolve overloads（386）、nil へのメソッド呼び出し（nil#[] 181 など）。
  • 単位は 1 対 1 に対応しない（TypeProf は呼ばれないメソッドも報告し、Sake は数えない）。割合の比較として読んでほしい。

なぜ差が出るか（解釈）：Sake では String.upcase(s) のように操作が型を名指しするので、引数が来た時点で型が分かり、その先は表を引くだけで結果の型が決まる。Ruby の s.upcase は、s の型が分からないと何が呼ばれるかも結果の型も分からない。この説明は設計の意図どおりだが、差のうちどれだけがこの理由によるかは、まだ分けて測っていない。

4 · 健全性

推論が正しいかを、実行して確かめた

500 本を実際に動かし、検査箇所ごとに観測した型が、推論した型に含まれているかを確かめた（含まれていなければ違反）。推論器を 3 つの版で測った。

baseline · 今朝の推論器585

違反。決まり具合 98.3%（式）。

HEAD · 試作で見えた弱点を修正173

17 本に違反。決まり具合 99.8%。

fixed · 健全性の穴を修正0

違反なし。決まり具合 99.5%。

見つかった穴は 7 つで、どれも今日より前からあった。

  1. Set どうしの | & - の結果を、要素の型を持たない Set としていた。
  2. 空の配列の sum が Integer の 0 になることを見ていなかった（Float の配列でも結果は Integer | Float）。
  3. Array[...] の要素の型が、最初に解析したときの分しか残らなかった（同じ関数を別の型で呼んだ分が抜ける）。
  4. 引数 2 つのブロックに渡す要素が Tuple 以外の型も含むと、分解をやめていた。
  5. Tuple[...]（型を宣言した配列）の要素の中身を持っていなかった。
  6. while の中の break / next の直前に書いた変数の型が、ループの後に伝わらなかった。
  7. 型が unknown の値に対する case/in が、どの枝にも当てはまらないとして全部飛ばしていた。

教訓：7 つとも「型が空（どの値も来ない）になり、その先を解析しない」形をしていた。解析されなかったコードは unknown として数えられないので、穴があるほど決まり具合の数字が良く見えた。修正後に unknown が 295 から 621 に増えたのは、それまで隠れていたコードが解析されるようになったため。決まり具合の数字は、健全性の確認と組にしないと信用できない。

負の対照：算術の結果を常に Integer と答えるよう壊した推論器では、違反が 1,734 件出た。確認の仕組み自体は、壊れた推論を捕まえられる。

5 · 実行前の検査

正しいプログラムを、どれだけ止めてしまうか

500 本はすべて正しく動くので、実行前の検査で止められたものはすべて誤報になる。strict のレベルごとに数えた。

0250500 本

level 1（既定）の診断 453 件の内訳：

原因件数例

8 · この結果を受けて決めたこと（2026-10-01 夜に追記）

決定と、入れた後の測り直し

採用した決定（すべて実装済み）

  • 網羅性の検査を分けた。型の漏れは level 1 のまま、値の集合が開いた型（String など）の値の漏れは新しい項目 exhaustive（level 3）。推論器は Symbol のリテラルを値として追跡するので、case op in :add … in :sub は網羅を証明できる。
  • (A|B).f(x) を入れた。Struct 型も列挙できる。列挙した型に f が無ければ静的エラー。nil は列挙できない。
  • Tuple・Array・Set・Hash・Record は中身で ==、Tuple と Array は辞書順で比べられる。sort_by { [a, b] } が書ける。
  • Array からの多重代入（k, v = String.split(s, "=")）。長さが違えば実行時エラーで、nil で埋めない。
    2026-10-02 に撤回：「配列に入れてから取り出しても結局 nil」という指摘で、Ruby に合わせて足りない要素は nil、余りは捨てるに変えた。推論器はその nil を x[k] と同じ index-nil として扱う（9 節）。
  • 単項演算子：-x は Arithmetic.-@、!x は x ? false : true。
  • 値の定数は入れない（変えない）。

同じ 500 本で測り直した結果（コーパスは新しい機能を使っていない）：

9 · 書き直しと、残りの機能を入れた後（2026-10-02 に追記）

書き手が挙げた難点を全部入れて、測り直した

8 節の決定の後、書き手に 500 本を新しい機能で書き直させた（corpus-v2。337 本が変わった）。単項演算子 167 箇所、!x 102 箇所、Tuple のソートキー 83 箇所が使われ、回避策の 0 - x は 115 → 1、x == false は 130 → 0 になった。書き手が残った難点として挙げたものは、その後すべて入れた：

  • 多重代入とブロックの分解を Ruby に合わせる（足りない要素は nil）、要素の入れ替え a[i], a[j] = a[j], a[i]、|(a, b), i|
  • Array の + - *、Array.new(n, v) と Array.new(n) { }、2 引数の添字 s[i, n]
  • ブロックの中の break（ブロックを渡した呼び出しを抜け、その値になる）
  • splat：first, *rest = xs、|k, *vs|、組み込みの可変長引数への *xs。ユーザ関数への f(*args) と zip への splat は、推論の精度を落とすので静的エラーのまま。
  • 型の違う値の == は false、Struct・Array・Hash・Set を Hash のキーに、Comparable の == は <=> が 0

v4 で mono が 1 ポイント下がったのは、多重代入を Ruby に合わせたため。Array から取り出した変数は、要素が足りなければ nil になるので nil | T になる。v3 で mono・v4 で nilable になった変数の読み 668 箇所のうち 517 箇所は分解の変数そのもの、残り 151 箇所はその値を入れた Hash のキーなどへの伝播だった。x[k] と同じ扱いにするという決定どおりで、推論が弱くなったのではない。level 3 の増加（+6 本）も同じ理由。

v4 のコーパスはまだ新しい機能を使っていない（v3 と同じ corpus-v2）。level 1 の診断は 307 → 280 件に減ったが、どの変更が効いたかの内訳は取っていない。

10 · 誤報を 1 件ずつ解析した（2026-10-02 に追記）

level 1 の誤報 280 件の出どころと、推論器の修正

v4 で level 1 に止められた 106 本・280 件の診断を、1 件ずつコードを読んで「実行時には来ない型がどこから来たか」で分けた。プログラムはどれも正しいので、全部が誤報。

直した推論器の誤り（それぞれ小さな再現で確かめてから直した）

  • ブロックの中で外側の変数を狭めていなかった（57 件減）。Array.each の中の best == nil || x < best が nil の報告になった。while の中なら狭まる。
  • Struct の自前の <=> を、無関係な型を相手に解析していた（26 件減）。p(L.new(1, Money.new(1))) だけで Money#<=>(Money, L) を解析し、Money.get_cents に L が来ると報告した。
  • ループの初回の「必ず失敗」が残っていた（7 件減）。変数がちょうど nil の初回の判定を、収束後の T | nil より優先していた。同じ呼び出し経路なら「失敗しうる」（level 2）にまとめる。
  • in true | false が Boolean を網羅しない、rescue の「送出されない」を呼び出しごとに判定（あわせて 8 件減）。

残り 182 件への提案（未着手）：関数の中で作る Array / Hash を関数の具体化ごとに分ける（68 件）、タグ付き Tuple を混ぜずに保ち case kind in :copy で絞る、Array.sum(xs, 0.0) を入れる（23 件）。相関の 19 件と、JSON・Lisp の値の多くは書き方の問題として残す。

制限と訂正
  • 書き手は 1 種類の AI。人が書いたプログラムではなく、課題も書き手が選んだ。
  • Sake 版は Sake の制約に合わせて書き換えられている。Ruby 版と出力は同じだが、構造まで同じとは限らない。
  • 計測ツールの誤りを途中で 5 つ直した。主なもの：並列で書いた結果の行が混ざって 34 行壊れた／受け手のクラスの計測が、C のメソッドの呼び出しを 1 段外側の行に数え、さらに C のメソッドが内部で呼ぶ C のメソッドまで数えていた（(Regexp|String).match が 107 箇所と出たが実際は 0）。どれも小さな例で正解を確かめてから流し直し、数字はすべて直した後のもの。
