A. 誤報（型の精度）正しいプログラムを止めてしまう報告

level 1（型）の 164 件の内訳：容器・フィールドで混ざる 126 件（31 本）、数の型の取り違え 26 件（18 本）、case/in 7 件、その他 5 件。level 2（nil）は 294 本。

A1. 関数の中で作った容器が、呼び出しが違っても 1 つにまとまる 推奨

課題
def index_by_id(rows)
  idx = Hash[]                      # この Hash は「作った場所」1 つとして扱われる
  Array.each(rows) { |r| idx[yield(r)] = r }
  idx
end
depts  = index_by_id(departments) { Department.get_id(it) }
by_emp = index_by_id(emps)        { Employee.get_id(it) }
Department.get_name(depts[id])     # 値が Employee | Department →「Employee かもしれない」

推論器は関数を引数の型の組ごとに別々に解析している（上の 2 回の呼び出しも別の解析）のに、その中で作る配列や Hash は、ソース上の場所 1 つにまとめている。employee_dept_join など、汎用の補助関数を書いたプログラムで起きる。

対策
配列・Hash・Set を作った場所を、関数の解析単位（引数の型の組）ごとに分ける。プログラムの書き方は何も変わらない。解析単位はもともと有限なので止まる。コストは「関数の具体化の数 × 中で作る容器の数」で、計測して確かめる。
効果
A の 126 件のうち、この形のものが消える。何件かは実装して数える（未計測）。

A2. インスタンスのフィールドに入れた容器が、型ごとに 1 つにまとまる 判断

課題
class Heap
  attr_reader items = nil
  def initialize(h) = @items = Array[]
end
ints = Heap.new; jobs = Heap.new     # Integer 用と Job 用のヒープ
# Heap.items は全インスタンスで 1 つの型 → 要素が Integer | Job | String、比較が混ざる

フィールドの型は「型」ごとに 1 つ。インスタンスごとに分けるのは状態の型付けのサーベイで見た「データの多相」で、コストが高く精度も出にくい（以前の議論どおり）。

対策

案 1（勧める）：class B < A（定義の写し）を「型引数の無い総称型」として使う。写すごとにフィールドの型も、写した initialize の中で作る容器の場所も、写し先のクラスごとに分ける。

class IntHeap < Heap
end
class JobHeap < Heap
end                                  # それぞれの items が別々に型付けされる

今は写した先でも容器を作る場所が共有され、sakelib の見直しで誤報が 0 → 3〜8 件に増えた。これを直せば、型を書かずに「用途ごとの型」を作る書き方になる。

案 2：インスタンスごとの型付け（データの多相）。高コストなので勧めない。

案 3：受け入れる。用途の違うヒープは別の型にしてもらう（ドキュメントで案内）。

A3. 本当に型の混ざる配列（行、動的なデータ）推奨

課題
rows = Array[Array["Tokyo", "Japan", 13_960_000, 2194.07, true, nil], …]
r[5] = Float.round(r[2] / r[3], 1)   # 要素の型は全部の和。「この位置は数」は推論に見えない

Ruby でよくある「型の違う値を並べた行」。インタプリタや JSON パーサの値（lisp_interp・stack_vm・json_parser で 39 件）も同じで、こちらは和が正しい答え。

対策
処理系は変えず、書き方を案内する。行は Tuple ["Tokyo", 13_960_000, …]（位置ごとに型が残り、同じ型なら t[i] = v で書き換えられる）か Record、動的な値は case/in で分ける。報告のヒントに「位置ごとの型を残すなら Tuple」と出す。

A4. 数の型の取り違え 判断

課題

Float.round(x) に Integer | Float、Rational.to_f(x) に Integer | Rational。Ruby の x.round はどの数でも動くので、書いた人は型を区別していない（26 件 / 18 本）。

対策

案 1（勧める）：演算子と同じく、数の共通の操作をモジュールに置く。Numeric.round(x, 1)、Numeric.to_f(x)、Numeric.abs(x) が x の型の操作に振り分ける（Arithmetic.+ と同じ仕組み）。Float.round は「Float だけ」の意味のまま残す。報告のヒントで Numeric.round を案内する。

案 2：Float.round などが Integer も受け付ける。簡単だが、「操作名の型が値の型」という読み方が崩れる。

A5. nil の誤報（level 2 で 294 本）

課題

ほとんどは Ruby でも nil になる値（Array.max、Hash[]、String.match、未設定のフィールド）。見直しで増えた 11 本のうち 5 本は Array.max(Array[a, b])、2 本は = nil で宣言して initialize の補助関数で埋めるフィールド。

対策

済 Tuple.max([a, b]) / min / minmax（aa5a7df）。

B2（式の既定値）と B3（非公開フィールド）で、= nil を置く理由がなくなる。

残りは「Ruby でも nil」なので level 2 の役目どおり。fetch 系を案内する。

B. Ruby より書きにくい所見直し役 6 体の記録から、多い順

B1. フィールドの読み書きが長い：Node.get_left(node) 判断

課題

型名付きの呼び出し 23,433 個のうち 22%（4,900 + 345）がフィールドの読み書き。見直し役全員が「Ruby の人が最初に気づく違い」として挙げた。木やリストのプログラムでは本体が 2〜3 倍に伸びる。

対策

案 1：get_ を外す。Node.left(node)、連鎖なら node.Node.left。型名は残るので原則どおり。書き込みは Node.set_left(n, v) のまま、または B4 の形。

案 2：@x を第 1 引数以外にも使えるようにする（other@x のような記法）。新しい記法が要る。

案 1 が最小の変更で効果が大きい。ただし同名の関数（def left(n)）と衝突するので、その場合はエラーにする。

B2. 既定値がリテラルだけ 推奨

課題

[] やオブジェクトで始まるフィールドは items = nil と書いて initialize で埋める（全分野で最多の摩擦、27 回）。nil の誤報の原因にもなる。

対策
attr_reader items = Array[] を許し、式は new のたびに評価する（Ruby の initialize の中の @items = [] と同じ）。リテラルに限っていたのは値の共有を避けるためで、毎回評価すればその問題はない。既定値は型を決めないので、原則とも合う。

B3. 内部の状態も attr_reader で公開され、new の引数になる 判断

課題

Ruby では initialize の中の @pos = 0 は外から見えない。Sake では attr_reader pos と宣言するので外から読め、new の引数の並びにも入る（11-simulation、15-data など）。

対策

案 1（勧める）：initialize の中で代入しているだけのインスタンス変数を、非公開のフィールドとする。new の引数にならず、getter も無い。Ruby の書き方そのまま。

class Parser
  attr_reader tokens               # new(tokens)
  def initialize(p) = @pos = 0     # @pos は非公開のフィールド
end

案 2：private のような宣言を足す。

B4. 外からフィールドに += できない 判断

課題

Ruby の stats.swaps += 1 が Stats.set_swaps(s, Stats.get_swaps(s) + 1)（23 回）。

対策
s.Stats.swaps += 1 を許す（連鎖の形の読みと書き。Prism はこの形を読める）。B1 の案 1 と組み合わせると読み書きが揃う。

B6. そのほか 判断

課題と対策
  • new にキーワードを渡せない（Logger.new(io, level: :warn)、21 回）：既定値のあるフィールドをキーワードでも渡せるようにする。
  • 可変長引数 *args / **opts（sakelib：URI.join、csv のキーワードの繰り返し）：呼び出し先が静的に決まるので、キーワード引数と同じ方法で入れられる。
  • attr_reader next が構文エラー（予約語をフィールド名にできない）：予約語に限り attr_reader :next を許す、または next_node などに改名を案内。
  • &:sym（8 回）：Array.map(xs, &:name) を、要素の型の name の操作として解決する。要素の型が 1 つに決まるときだけ許す。
  • x => T の失敗を rescue できない（Ruby は ArgumentError や TypeError）：プログラムの誤りとして扱う今のままにする（勧める）。

C. 評価の穴

C1. 新しい機能がコーパスで使われていない 推奨

課題

キーワード引数・x => T・class B < A・block_given?・IO は 500 本で 0 回。コーパスの Ruby 版（1 本 40〜250 行のスクリプト）が使わないため、これらの機能の効果も誤報も測れていない。

対策
それらを使う Ruby のコード（gem の一部、CLI ツール、小さなアプリ）を材料に、2 つ目のコーパスを作る。sakelib の 18 本はその種になる。
